# M-2 の調査 — 着色した I ビームが「空のカーソル」になる

- 作成日: 2026-08-09
- 作成: Claude Code（AI モデル: claude-opus-5[1m]）／実機での再現・確認: オーナー
- 対象: [受け入れ M-2](../03_acceptance-checklist.md#8-対話ハーネスの記録)（v0.8）、[ADR 0067](../decisions/0067-ime-cursor-color.md)（IME をマウスカーソルの色で示す）、[ADR 0072](../decisions/0072-cursor-keeps-tint-when-state-unknown.md)
- 公式: [`SetSystemCursor`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setsystemcursor)、[`SystemParametersInfo` (SPI_SETCURSORS)](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-systemparametersinfow)、[`LoadImage`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-loadimagew)

> **この文書は原因の特定までは到達していない。** 到達したのは「症状の正体」「否定できた筋」「確定した欠陥 2 件」「直す方向」である。v0.9 で直すときの出発点として残す。

---

## 1. 症状の正体 — 空のカーソルが入っている

2026-08-09 11:06、症状が出ている最中に**システムに登録されている I ビームを直接測った**（[`measure-cursor.ps1`](#6-使った道具)）。

```
id 32513 (I ビーム): colour 32x32, ホットスポット (9,10)
                     マスク AND=1 が 1024/1024（全面透明）
                     アルファ 0 が 1024/1024、RGB が黒でない画素 0
id 32512 (矢印)    : 正常
```

**素の I ビームはマスクだけのカーソル**（32×64・下の画面を反転して描く）である。入っていたのは**カラーカーソル 32×32 で、ホットスポットは I ビームのもの** — つまり `tinted()` が作った出力で、その中身が**完全に空**だった。「色が消える」のではなく「何も描かれない」という観測（2026-08-04・08-08）と一致する。

**正常なときの同じ測定**（同日 11:12、作り直し直後）:

```
id 32513: マスク AND=1 が 934/1024、アルファ 255 が 90、RGB 非黒 90、ホットスポット (8,9)
id 32512: マスク AND=1 が 846/1024、アルファ 255 が 130・中間 48
```

この 934／846 は [`probe-ime-cursor.ps1`](../../../tests/acceptance/probe-ime-cursor.ps1) が「正常」として測る値と同じである。

---

## 2. なぜ「一度消えると戻らない」のか — 自己再生産

[`src/cursor.rs` の `from_color()`](../../../src/cursor.rs) は、元カーソルにアルファが無ければ **AND マスクを見て**「透明」と言う画素を捨てる。

**空のカーソルはアルファが全部 0 で、マスクも全面「透明」**である。これを元にもう一度着色すると、**また空になる**。`tinted()` は現在のシステムカーソルを元に作るので、**一度空が入ると作り直すたびに空が再生産される**。IME を切り替えても戻らなかった理由がこれである。

---

## 3. 確定した欠陥 2 件

### 3.1 `restore()` の 1 段目が、この Windows では一度も動いていない

```
LoadImageW(user32, IDC_ARROW, IMAGE_CURSOR, 0, 0, LR_SHARED) -> 0  (GetLastError=1814)
LoadImageW(user32, IDC_IBEAM, IMAGE_CURSOR, 0, 0, LR_SHARED) -> 0  (GetLastError=1814)
LoadImageW(NULL,   IDC_ARROW, ...)                           -> 0x10003  (成功)
LoadImageW(NULL,   IDC_IBEAM, ...)                           -> 0x10005  (成功)
```

`1814` は `ERROR_RESOURCE_NAME_NOT_FOUND`。[`src/cursor.rs:86-90`](../../../src/cursor.rs) のコメントは「`IDC_*` のアトムは user32 内のこのカーソルのリソース ID でもある」と書いているが、**Windows 11 26200 ではその前提が成り立たない**。失敗は `continue` で黙って捨てられる。

**したがって復元は `SPI_SETCURSORS` の 1 段だけで回っている。** ADR 0067 の「[`SPI_SETCURSORS`] だけでは戻らないことがある（既定スキームではレジストリの値が空）」という認識のもとに用意した 2 段構えが、**丸ごと外れていた**。

この機械のレジストリはまさにその状態である:

```
HKCU\Control Panel\Cursors:  IBeam = (空)   Arrow = C:\WINDOWS\cursors\aero_arrow.cur
```

**矢印だけが壊れないのは、矢印にはレジストリに実体があり `SPI_SETCURSORS` で確実に戻るから**という説明が付く。

> なお、実測では `SPI_SETCURSORS` 単独でも空の I ビームは素に戻せた（同日 3 回確認）。**1 段目が無くても戻る場合はある**が、それに依存した設計にはなっていない。

### 3.2 作った結果も、元にする対象も、誰も検査していない

`tinted()` は結果を検査せず、`apply()` は元カーソルを検査しない。**空を作れば空を入れ、空を元にすれば空を作る。** §2 の自己再生産はここから来ている。

## 4. 否定できた筋（すべて実測）

| # | 筋 | 実測 |
|---|---|---|
| 1 | 他プロセスが握っているカーソルのハンドルが宙に浮く | **否定**。別プロセスで先に `LoadCursor` したハンドルは、`SetSystemCursor` を繰り返しても 16 秒間ずっと有効。`SetSystemCursor` はハンドルではなく**中身**を入れ替える |
| 2 | `SPI_SETCURSORS` が、レジストリの `IBeam` が空だから I ビームを消す | **否定**。打っても 26 画素のまま |
| 3 | 繰り返しの `SetSystemCursor` が中身を壊す | **否定**。4 回続けて差し替えても毎回 144 画素、復元も正常 |
| 4 | Zed の IME 状態が常に「オフ」と読まれる（2026-08-04 の観測） | **取り下げ**。Zed で IME をオンにすれば「オン」と読めている（ログで確認）。08-04 の観測は、Zed 側で IME をオンにしていなかったためと考えられる |
| 5 | カーソルの種類を変えている（マスクだけ → カラー）から Zed が描けない | **否定**。Zed が前面・IME オン・着色済みの状態で、オーナーに I ビームが見えている |
| 6 | 素の I ビームから空が作られる | **否定**。素の状態から作り直させたら正常な 90 画素ができた（同日 11:12） |

**自動再現は 2 通り試して、どちらも出なかった** — メモ帳 ↔ Zed を 20 往復する版と、日本語を打って変換中にしてから往復する版（各 10 巡）。**壊れた 4 回はいずれも実作業の最中**である。

## 5. 残っている手掛かり — ホットスポットが違う

| | ホットスポット |
|---|---|
| 壊れていた空のカーソル | **(9,10)** |
| 正常に作られたもの | **(8,9)** |

`tinted()` は元カーソルのホットスポットをそのまま引き継ぐ。**壊れたほうは、いまと違う元から作られている。** 「素の I ビームから空を作った」のではなく、**別の何かを元にした結果が空だった**。その「別の何か」が何かは特定できていない。

**次に捕まえるときに見るべきもの**: 壊れた瞬間の**ホットスポット**と、その直前の `カーソル:` のログ行（`作り直し` が付いているか）。

## 6. 使った道具

`--debug` のログに**カーソルの差し替えを毎回書く**ようにした（この調査で追加。`apply()` が何をしたかを返し、呼び出し側が書く）。

```
11:12:27.512 [IME]   カーソル: 着色した — 差し替え 2・作り直し
11:12:32.537 [IME]   カーソル: 着色を外した
11:12:33.081 [IME]   カーソル: 着色した — 差し替え 2
11:12:38.798 [IME]   カーソル: 着色し直した（すでに着色済み） — 差し替え 2
```

`失敗 n` が付けば `CopyIcon` か `SetSystemCursor` が落ちたことを意味する。**この調査中、失敗は 1 件も出ていない** — 壊れているのは呼び出しの成否ではなく、渡している中身である。

受け入れの検査にも項目を 1 つ足した（`the-i-beam-on-screen-is-the-tinted-one`）。**それまでの項目はシステムに登録されたカーソルしか読んでおらず、画面に描かれているものを見ていなかった** — M-2 はまさにそこが割れる症状で、8/8 通過の日に人の目には壊れて見えていた。

常駐にログを取らせる形（窓を開かない）:

```powershell
Start-Process "$env:LOCALAPPDATA\Programs\WinRemap\winremap.exe" `
  -ArgumentList '-c', "$env:APPDATA\winremap\personal-ja.toml", '--debug' `
  -RedirectStandardOutput "$env:LOCALAPPDATA\winremap-logs\debug.log"
```

**壊れたときの応急処置**（WinRemap を止めずに戻せる）:

```powershell
Add-Type -Namespace F -Name C -MemberDefinition '[DllImport("user32.dll")] public static extern bool SystemParametersInfoW(uint a, uint b, IntPtr c, uint d);'
[void][F.C]::SystemParametersInfoW(0x57, 0, [IntPtr]::Zero, 0x02)   # SPI_SETCURSORS
```

ただし**着色が入り直すとまた空になる**（§2）ので、根治までは WinRemap 自体を起動し直すこと。

## 7. v0.9 での直し方（案・未承認）

1. **起動時に、汚れる前の素のカーソルを複製して持つ。** 復元はそこから行う。いまの「user32 から読み直す」方式は §3.1 のとおり前提から成立しておらず、`SPI_SETCURSORS` だけに頼っている
2. **作った着色カーソルに可視画素が 1 つも無ければ、入れない**（ログに残す）。これだけで**利用者から見える症状は消える**
3. **元にするカーソルが空なら、作らない。** §2 の自己再生産を断つ
4. `restore()` の失敗を**黙って捨てない**（いまは `continue` と `let _ =`）。ログに出す
5. `probe-ime-cursor.ps1` に**「着色 → 復元 → 着色」を何度も繰り返す項目**を足し、繰り返しの中で空にならないことを見る

**「直った」と言う前に、再現の経路を検査に足すこと**（[受け入れ §7 の 2026-08-08](../03_acceptance-checklist.md#7-記録欄散文)）。人の目に頼るかぎり、この項目の判定は揺れ続ける。

## 8. この調査でこちらが踏んだ失敗

- **オーナーに見てもらう前に、その機能が有効な設定で動いていることを確かめていなかった。** A〜D の切り分けを頼んだとき、「WinRemap は私が起動します」と書いておきながら起動しておらず、**カーソルの色が無効な設定のまま 4 つとも確かめてもらった**。同じ日の H-1 とまったく同じ形である
- **オーナーが切り替えた設定を、ログ取りのための再起動で上書きした。** トレイから `personal-ja.toml` を読み込んで使っておられたのを、`%APPDATA%\config.toml`（メモ帳のみ）で起動し直してしまった。**常駐を入れ替える前に、いま何が読まれているかをログで確かめること**
