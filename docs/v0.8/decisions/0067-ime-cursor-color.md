# ADR 0067: IME の状態をマウスカーソルの色で示す（`SetSystemCursor` と、異常終了の検出）

- 作成日: 2026-08-02
- 作成: Claude Code（AI モデル: claude-opus-5[1m]）
- ステータス: 採用（**オーナー決定 2026-08-02**「マウスカーソルの色は `SetSystemCursor` で」、**異常終了時の扱いも同日決定** — 痕跡ファイルは置かず、§「決定」4 の「その場で見て分かる形」を採る）
- 関連: [ADR 0033](../../v0.2/decisions/0033-ime-status-across-input-threads.md)（IME 状態をスレッドをまたいで取る）、[ADR 0016](../../v0.1/decisions/0016-debug-key-logging.md)（フックからは Win32 を呼ばない）、[ADR 0031](../../v0.2/decisions/0031-notify-module-unsafe-allowlist.md)（`unsafe` の隔離先を増やすときの前例）、[ADR 0061](../../v0.6/decisions/0061-packaged-config-path.md)（パッケージ版の書き込み先）、[ADR 0065](../../v0.7/decisions/0065-foreground-window-from-the-event.md)（前面ウィンドウの通知経路）
- 公式: [`SetSystemCursor`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setsystemcursor)（**渡したカーソルの所有権を取り、破棄する**）／[`SystemParametersInfoW`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-systemparametersinfow)（`SPI_SETCURSORS` はレジストリからカーソル一式を読み直す）／[`CopyIcon`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-copyicon)／[`SetUnhandledExceptionFilter`](https://learn.microsoft.com/en-us/windows/win32/api/errhandlingapi/nf-errhandlingapi-setunhandledexceptionfilter)／[`HandlerRoutine`](https://learn.microsoft.com/en-us/windows/console/handlerroutine)（`CTRL_CLOSE_EVENT` は拒否できない）

## 背景

IME のオン・オフは、既存のインジケーター（キャレット付近の小さな表示）で示している。オーナーの要望は**マウスカーソルの色**でも分かるようにすることである。

`SetSystemCursor` は**セッション全体のカーソルを差し替える** API である。これは長所と短所が表裏になっている。

- **効果が確実**：本物のカーソルが変わる。オーバーレイのような追従の遅れが無く、**管理者権限のウィンドウの上でも効く**（UIPI に阻まれない数少ない部分）
- **プロセスの外に残る状態**：差し替えはシステム側の状態であり、**WinRemap が死んでも元に戻らない**

したがって設計上の主題は「色をどう変えるか」ではなく、**残った状態をどう畳むか**である。

## 決定

1. **`SetSystemCursor` で差し替える。** 対象は `OCR_NORMAL`（矢印）と **`OCR_IBEAM`（テキストの I ビーム）の 2 つ**を最低限とする。**IME を気にする場面はまさに文字を打っている最中**であり、そこで出ているのは I ビームだからである。矢印だけを変えると「入力欄の上では色が変わらない」という中途半端な機能になる
2. **復元は `SystemParametersInfoW(SPI_SETCURSORS, 0, NULL, SPIF_SENDCHANGE)` で行う。** 元のハンドルを取っておいて戻すことはできない — `SetSystemCursor` は**渡したハンドルを破棄する**ので、保存した「元のカーソル」は差し替えの時点で無効になる。レジストリから読み直すのが唯一の正しい戻し方であり、**利用者が独自のカーソルテーマを使っていてもそのテーマに戻る**

### 異常終了への備え（**この ADR の本題**）

3. **プロセス内で走れる終了経路は、すべて復元を通す。**

   | 経路 | 手当て |
   |---|---|
   | トレイの「終了」・通常終了 | 終了処理で復元 |
   | Rust の panic | `std::panic::set_hook` で復元してから既定のハンドラへ落とす |
   | 未処理の構造化例外（アクセス違反など） | `SetUnhandledExceptionFilter` で復元してから既定へ渡す |
   | サインアウト・シャットダウン | **何も要らない**（下記） |
   | `--debug` のコンソールが閉じられた | 既存の `CTRL_CLOSE_EVENT` 経路で復元（[ADR 0062](../../v0.6/decisions/0062-detach-console-when-resident.md)） |

   **サインアウト・シャットダウンは手当てが要らない**（実装時に確認、2026-08-02）。`SetSystemCursor` が変えるのは**そのセッションのウィンドウステーションの状態**で、レジストリには書かない。Windows はログオンのたびに `HKCU\Control Panel\Cursors` からカーソルを読み直すので、**残った色はセッションと一緒に消える**。`WM_ENDSESSION` を拾うには自前のウィンドウが要る（トレイアイコンのウィンドウは `tray-icon` クレートのもの）ので、**要らない手当てのために構造を足すことになる**。

4. **強制終了（`TerminateProcess`、タスクマネージャー、電源断）は、プロセス内では何も走らない。** ここは**「その場で見て分かる形」で畳む**（オーナー決定 2026-08-02）。

   > **カーソルの色が変わったままで、トレイに WinRemap が居ない。** これが「異常終了した」という意味である。

   これが一意に読めるように、**既定の状態のカーソルは差し替えない**。IME オフは素のカーソルのまま、オンのときだけ色付きにする。**残るとしたら必ず「色付き」**なので、正常時の見た目と混同されない。この読み方を README とヘルプサイトに書く。

   プロセスが消えたあとに何かを表示する手段はプロセス内に無い以上、**利用者が自力で判断できる状態にしておくことが答えになる。**

5. **起動時に、機能が有効なら無条件で `SPI_SETCURSORS` を打つ。**

   前回どう終わったかを**知る必要はない** — 復元は「レジストリの設定を読み直す」だけで、差し替えられていなければ何も起きないからである。これで**次に WinRemap を起動した時点で必ず元に戻る**。

   打つのは**設定でこの機能を有効にしている場合だけ**とする。無効な人のカーソルに、WinRemap が起動のたびに触る理由がない。

## 却下した代替案

- **カーソルに追従するオーバーレイ**: プロセスが死ねば必ず消えるので安全だが、追従が遅れて見え、**管理者権限のウィンドウの上に出せない**。ADR 0065 で直したばかりの「前面が絡む処理」をもう 1 つ増やすことにもなる
- **監視プロセスを常駐させて、WinRemap が消えたら復元する**: 確実だが**プロセスが 2 つになる**。単一インスタンスの仕組み（`hook::acquire_single_instance`）と噛み合わず、「常駐ツールが増えた」という利用者の印象も悪い。得られるのは「強制終了直後に自動で戻る」だけで、決定 5 の次回起動時復元との差は**次に WinRemap を起動するまでの間だけ**である
- **カーソルテーマ一式（十数個）を差し替える**: 見た目の一貫性は上がるが、用意する画像と復元の失敗面が増える。**まず 2 つで足りるかを実際に使って確かめる**（足りなければ足す）
- **痕跡ファイルを置いて、次回起動時に「前回は異常終了しました」と知らせる**（当初案。**オーナーが決定 4 を選択したため不採用**）: カーソルを差し替えた瞬間に空ファイルを作り、復元時に消す。次回の起動時に残っていれば異常終了と断定できる、という案だった。**復元そのものには不要**（決定 5 のとおり、前回の状態を知らなくても復元はできる）で、得られるのは「知らせられる」ことだけである。その代わりに**ディスク上の状態を 1 つ抱え、それが常に正しいことを保証し続ける**必要が生じる。決定 4 が同じことを状態の見た目だけで達成するので、割に合わない

## 実装で分かったこと（2026-08-02、実装・実測）

- **`SPI_SETCURSORS` だけでは戻らない場合がある。** これはレジストリ（`HKCU\Control Panel\Cursors`）から読み直す API で、**既定のカーソルスキームではその値が空**である。読み直す先が無いので、置き換えたままになりうる。したがって復元は 2 段構えにした — **①`user32.dll` に埋め込まれている標準カーソルを入れ直し、②そのあと `SPI_SETCURSORS`**。独自スキームの人は②が①を上書きするので、どちらの環境でも正しく戻る
- **古典的な I ビームは「画面を反転して描く」カーソルだった**（実測）。マスクのみのカーソルは AND/XOR の 2 ビットで 4 通りの描き方を指定するが、標準の I ビームは **AND 面が全画素 1**で、可視の 26 画素はすべて **AND=1・XOR=1（下の画面を反転）**である。明るい背景でも暗い背景でも見えるのはこのためである。当初の実装はこの組み合わせを「塗る色が無い」として透明に落としていたので、**カーソル全体が透明**になった。そして **32bpp でアルファが一様に 0 のビットマップを、Windows は「アルファ無し」と解釈する** — AND マスク（ここでは全面不透明）に切り替え、真っ黒な色ビットマップをそのまま描く。結果が**黒い四角**である（オーナー報告 2026-08-02）。反転の画素は**塗る画素として扱う**（色を乗せる）ことで直した。反転が失われる分、同系色の背景の上では標準の I ビームより見つけにくくなるが、**色が付いていること自体が伝えたい情報**なので割り切る
- **`CreateIconIndirect` がアルファを見るのは DIB のときだけ。** `CreateBitmap` で作った**デバイス依存**ビットマップを渡すとアルファは無視され、上と同じ「AND マスクへの転落」が起きる。色ビットマップは `CreateDIBSection` で作る
- **着色だけでは暗いアプリで見失う。白い縁を合成して足す**（オーナー報告 2026-08-02、**方式はオーナー決定**）。原因は算術である — 着色は白い本体を指定色に落とすが、`#0078d4` の明るさは白の約 **37%**。**画面でいちばん明るかったものが中くらいの明るさになる**ので、白い紙の上では読めても黒いエディターの上では消える。**明るさが正反対の 2 色で作れば、背景が何であれどちらかが必ず立つ**（Windows 自身のポインターの色のカスタム設定も同じ考え方）。
  **縁は「色を塗り替える」のではなく「形から合成する」。** 塗り替える対象が無いからである — この機械の標準の矢印には**黒い輪郭が 1 画素も無い**（実測: 不透明な白 77 画素と、半透明の落ち影 67 画素だけ）。I ビームにも輪郭は無い。したがって**アルファ 128 以上の画素を「本体」とし、それに隣接する透明な画素を不透明な白にする**。元の落ち影は捨てる（白い縁の外側に暗い暈が残るため）
- **形はアルファと AND マスクの両方に書く。** Windows がカーソルを画面に出す経路は 1 つではなく、**アルファを読まない経路がある**。アルファだけで形を表し AND マスクを全ゼロ（＝全面不透明）にしていると、その経路では**塗りつぶしの四角**が描かれる。**Zed がまさにその経路だった**（オーナー報告 2026-08-02。色が付いた状態で Zed にマウスオーバーすると黒い四角、クリックすると直る）。アルファが 0 の画素は AND マスクでも 1（透過）にし、**同じ形を 2 回言う**。アルファを読む経路ではアンチエイリアスの縁も残る。検査に**両者が一致していること**を見る項目を足した（矢印 880/880、I ビーム 998/998）
- **注入したキーで IME が動くかどうかは、その時々で違った。** 実装時は 半角/全角 を 4 回送っても状態が変わらず、翌る検査では毎回トグルした。どちらを前提にしても**測っている状態が反転して静かに間違う**（実際、I ビームの検査が「色の付いていないカーソル」を見て一度通ってしまった）。検査は**キーがトグルするかどうかを最初に 1 回実測**し、それに合わせて `IMC_SETOPENSTATUS` の狙いを 1 つずらす形にした。キー送出の役目は「WinRemap に見直させる」ことである（WinRemap が IME を読み直すのは**トグル候補キーか前面ウィンドウの変化**のときだけ）
- **IME の状態はウィンドウごと。** したがって検査は**前面ウィンドウを固定しなければ意味がない** — WinRemap は前面のウィンドウの IME を読むので、前面が流れると無関係なウィンドウの状態を測ることになる。実際に 2 回連続で別々の項目が落ちた（2026-08-02）。測定のたびに対象ウィンドウを前面に入れ直し、WinRemap を起動する前に IME を既知の状態へ倒す形にした
- **注入キーへの依存はやめ、前面変化を合図にした。** 注入した 半角/全角 で IME が動くかどうかは、**同じ機械の同じ午後の中で変わった**（朝は 4 回押しても不動、午後は毎回トグル、その後また不動）。実行ごとに 1 回測って狙いを合わせる作りにしても、**実行の途中で変われば静かに逆の状態を測る**。合図は前面の変化にした — WinRemap が IME を読み直すもう 1 つの経路であり、決定的である
- **前面を「変えたつもり」でいちばん危ない。** `SetForegroundWindow` は**前面でないプロセスからは黙って拒否される**。バックグラウンドのセッションから走らせると前面が 1 度も動かず、以降の測定は全部別のウィンドウのものになる（2026-08-02、8 項目中 5 項目が落ちる形で表面化。原因は WinRemap 自身のデバッグログに `[window]` 行が 1 本しか無いことで判明した）。**前面ウィンドウの入力キューに `AttachThreadInput` で相乗り**して取り、**取れなければ検査を落とす**。以前のキー注入版が動いて見えていたのは、キーを注入すること自体が前面を取る権利を与えていたためである
- **同じウィンドウの最小化・復元では前面変化にならない。** WinRemap は `EVENT_SYSTEM_FOREGROUND` を見ており、既に対象になっているウィンドウは読み直さない。第 2 のウィンドウが要る。Windows 11 の Notepad は 2 つ目の起動が**タブ**になってウィンドウハンドルを返さず、コンソールウィンドウ（`cmd`）は `MainWindowHandle` が 0 だった。使えたのは `winver`（素の Win32 ウィンドウ。Explorer はシェル面として意図的に読み飛ばされる — ADR 0023）
- **非同期の状態は待って読む。** カーソルを戻すのは別プロセスで、こちらの操作への反応である。1 回だけ読むと「まだ」と「ずっと」が区別できず、実際 3 回に 2 回落ちた。**期待する状態になるまで読み直す**形にすると、通る場合は 1 回で済み、落ちる場合だけ待ち時間を払う
- **カーソルのハンドルはプロセスごとにキャッシュされる。** `LoadCursor` が返すハンドルは、`SetSystemCursor` の変化には追随するのに、復元（新しいカーソルオブジェクトが入る）には追随しない。**同じプロセスで 2 回読むと「復元されていない」と誤読する。** 検査は 1 回の測定ごとにプロセスを分けて回避した（**この誤読を追いかけて 1 時間使った**）
- **フックの経路も直した。** トグルキーの検知（`notify_keydown`）が `enabled`（パネル）だけを見ていたので、**パネルを出さずカーソルだけ**の設定だと IME キーで再照会が走らなかった

## 影響・補足

- **`unsafe` の隔離先が 1 つ増える。** 新しいモジュール（`src/cursor.rs` を想定）に閉じ込め、[AGENTS.md 不変条件 3](../../../AGENTS.md) の許可リストへ追加する。前例は [ADR 0031](../../v0.2/decisions/0031-notify-module-unsafe-allowlist.md)（`notify.rs`）で、**同じ理由・同じ形**である
- **フックからは呼ばない。** 差し替えは IME 状態の変化を受け取っている既存の経路（メッセージループ側）で行う。[不変条件 2](../../../AGENTS.md) は変わらない
- **`SetSystemCursor` に渡すハンドルは複製にする。** 自前のカーソルリソースをそのまま渡すと破棄され、2 回目の差し替えで無効なハンドルを渡すことになる。`CopyIcon` した複製を毎回渡す
- **受け入れに項目が増える。** 実際に殺して（`Stop-Process -Force`）、①**色付きのカーソルが残ること**、②**トレイに居ないことと合わせて異常終了と読めること**、③**次に起動すると戻ること**を確かめる。これは v0.8 の対話式受け入れハーネスの最初の顧客になる
- **既定はオフにする。** システム全体のカーソルを触る機能なので、設定で明示的に有効にした人にだけ働く
- **設定の名前は `change_cursor_color`**（`[ime_indicator]` の中。色は `cursor_color`）。当初は `cursor` としたが、**何が起きる設定なのか読めない**というオーナー指摘（2026-08-02）で改めた。`true` にすると何が変わるのかが名前だけで分かることを優先する
- **既定の色は `#0078d4`**（WinRemap のアイコンの青。オーナー決定 2026-08-02）。当初はオレンジ（`#e05a2b`）にしていたが、**どのアプリの仕業か分かる色**である方がよい — カーソルはセッション全体のものなので、見慣れない色が出たときに「これは WinRemap だ」と読めることに意味がある
