# ADR 0069: 受け入れテストの対話ハーネス（チェックリストを読み、チェックリストへ書く）

## 背景

v0.7 の受け入れは全項目を通ったが、**記録に 3 つの穴が空いた**。ハーネスの要件は、この 3 つそのものである。

1. **配列の記録が空のまま残った。** S-1〜S-5 は通ったのに、「どの機械のどのキーで確かめたか」が書かれていない。記号キーは**機械によって答えが変わる機能**（[ADR 0063](../../v0.7/decisions/0063-symbol-keys.md)）なので、この記録が無い受け入れは次の版で根拠として使えない。チェックリスト側は §8 で「US 101 の `;`（`VK_OEM_1`）で効いた、の粒度で書くこと」と**依頼していた**。依頼しても書かれなかった
2. **測れない項目と、やらなかった項目が同じ「未実施」になった。** P-8・P-9 の Store 経路は認定通過後にしか測れない。S-6 は別配列のキーボードが無い。どちらも**後で埋まる**種類で、「今回はやらないと決めた」項目とは意味が違う
3. **手順とチェックリストと記録欄が別々の場所にある。** 人が写す作業が発生し、写し漏れる

## 決定

### 1. 項目はチェックリストの Markdown から**読む**。ハーネスに写さない

§2〜§4 の表（`| **S-1** | 何を見るか | 手順 | 通過条件 | 由来 |`）をそのまま解析し、提示する。**チェックリストが正本のまま**であり、項目を足す・直すときに触る場所は 1 つだけになる。

これは背景 3 への直接の答えである。**ハーネスに項目定義を持たせた瞬間、「手順が 2 か所にある」状態が復活する** — それは今の問題そのものなので、採らない。

### 2. 記録は同じ Markdown に**直接書き戻す**。中間ファイルを挟まない

`<!-- harness:begin -->` … `<!-- harness:end -->` の間に、**実行 1 回につき見出し 1 つ＋表 1 つ**を追記する。

```markdown
#### 2026-08-02 — キーボード: 日本語 106/109（00000411） / WinRemap 0.8.0 / Windows 11 (26200)

| 項目 | 結果 | 記録 |
|---|---|---|
| S-1 | 通過 | US 101 の `;`（VK_OEM_1）で 1 文字消えた。ログも `C-;` と出た |
```

**成果物を 1 つに保つ**ための決定である。中間の JSON を置いて後から描画する形も考えたが、**正しさを保証し続ける対象が 2 つになる**（§「却下した代替案」）。

**追記のみで、行の書き換えはしない。** 同じ項目を後日もう一度やったら、新しい実行の表に新しい行が増える。「測れない → 認定通過後に通過」という**経緯が読める**ほうが、最新の結果だけが残るより価値がある。これはチェックリスト §8 の「埋まっていない空欄がどこにあるかが分かることのほうが、埋まったふりより価値がある」と同じ判断である。

### 3. 結果は 4 値。**「測れない」には「何が揃えば測れるか」を必須にする**

| 結果 | 意味 | 必須の記入 |
|---|---|---|
| **通過** | 通過条件を満たした | 何をどう確かめたか |
| **不合格** | 満たさなかった | 何が起きたか |
| **未実施** | **今回はやらないと判断した**（「前回から変更が無いので省略」など） | 省略した判断の理由 |
| **測れない** | **前提が揃っていない**（認定待ち・実機が無い） | **何が揃えば測れるか** |

背景 2 への答えである。「未実施」と「測れない」を分ける実利は、**後者だけが再実行の対象になる**ことにある（`-Resume` は「まだ記録が無い項目」と「最新が**測れない**か**不合格**の項目」を出す）。「何が揃えば測れるか」を必須にすることで、**その再実行がいつ可能になるのかが記録から読める**。

**記録は 4 値すべてで必須**とする。チェックリスト §8 が「**OK だけを書かない**」と書いているものを、ハーネスが空欄で通せてはならない。

### 4. 実行環境は**ハーネスが自動で刻む**

キーボード配列（`GetKeyboardLayoutNameW` の識別子と、レジストリから引いた表示名）・WinRemap の版（`--version`）・OS のビルドを、実行の見出しに書く。

背景 1 への答えである。**人に「配列を書いてください」と依頼するのは v0.7 で試して、書かれなかった。** 機械が確実に知っていることは機械が書く。人が書くのは機械が知らないこと（打った刻印、見えた挙動）だけにする。

**機械名は入れない。** このリポジトリは公開されており、記録として要るのは「どの配列か」であって「誰のどの PC か」ではない。複数の機械を区別する必要が出たら、自由記述に書けばよい。

### 5. ハーネスは `tests/acceptance/` に置く

[`symbol-keys.toml`](../../../tests/acceptance/symbol-keys.toml)（受け入れ用の設定）と [`probe-ime-cursor.ps1`](../../../tests/acceptance/probe-ime-cursor.ps1)（カーソルの実測）が既にある。**「人が関わる確認のための道具」の置き場所**として一貫する。

`tests/ui/` は**ゲスト VM の中で動く自動テスト**の置き場所であり、性格が違う（[05_ui-test-automation.md](../../05_ui-test-automation.md)）。混ぜない。

### 6. **キーは絶対に注入しない**

ハーネスに `SendInput`・`keybd_event` を置かない。**実キーボードで打って確かめること自体が受け入れの目的**であり、注入で代用できるものは既に `tests/ui` の自動テストが見ている。[ADR 0053](../../v0.4/decisions/0053-test-inject-mode.md) の `--accept-injected` も使わない — **受け入れは素の配布ビルドに対して行う**。

環境の準備（設定の退避と配置、WinRemap の起動）は自動で行い、**破壊的な準備（MSIX の登録・削除）は自動化せず、手順を表示して人の確認を待つ**。

## 却下した代替案

- **中間ファイル（JSON/JSONL）に記録し、別の手順で Markdown へ描画する**: 再実行や集計には強い。だが**成果物が 2 つになり、片方だけが更新された状態が作れてしまう**。この受け入れの読者は人間 1 人（オーナー）で、集計の需要は無い。Markdown の表を追記するだけなら描画層は要らない
- **項目定義をハーネス側のデータファイルに持つ**（`items.psd1` など）: 解析が要らず堅い。しかし**手順が 2 か所に存在する**ことになり、背景 3 をそのまま再生産する。Markdown の解析が壊れる危険は、`-List` で解析結果だけを表示できるようにして受け止める
- **項目の行を id で置き換える（最新の結果だけを残す）**: 表が短く保てる。だが「測れない」がいつどう解消したのかが消える。この文書の価値は結果ではなく**経緯**にある
- **TUI / GUI にする**: 見栄えはよいが、受け入れは年に数回で、対象は 1 人である。`Read-Host` で足りる。**ハーネス自体が受け入れの対象になる**（壊れたら受け入れが止まる）ので、小さいことに価値がある
- **合否の判定まで自動化する**（画面を読む・ログを解析する）: それができる項目は既に `tests/ui` にある。ここに残っているのは**人が見なければ分からない項目**だけである

## 実装で分かったこと（2026-08-02、v0.7 のチェックリストで実測）

- **25 項目すべて解析できた**（S-1〜S-6・H-1〜H-10・P-1〜P-9）。**id が太字であることが効いた** — `| **S-1** |` という形は 3 つの表すべてが既に使っており、かつ**書き戻した記録の行（`| S-1 |`、太字でない）とぶつからない**。解析の対象と生成物を、書式だけで分けられる
- **セルの中の `\|` に注意が要る。** P-5 の行に `Get-AppxPackage … \| Remove-AppxPackage` がある。区切りは「エスケープされていない `|`」である
- **表によって 4 列目の意味が違う。** §4 は「通過条件」、§3 は「v0.7 での見どころ」。列は位置で取り、**見出しはその表の見出し行から読む**ことにした。ハーネスが「通過条件」と言い切ると、文書が言っていないことを言うことになる
- **マーカーの確認は、人に質問する前に行う。** 受け入れを一通り答えたあとで「書き戻す先が無い」と分かるのが、いちばん起きてはいけない失敗である
- **後片付けは `finally` で、かつ「準備が成功したときだけ」。** 退避先が既にあるときは準備を止めるが、そこで後片付けまで走ると**古い退避ファイルを現在の設定に上書きしてしまう**

## 影響・補足

- **チェックリストにマーカーが要る。** `<!-- harness:begin -->` / `<!-- harness:end -->` が無いファイルには書き戻さず、貼るべき断片を表示して終わる。既存の v0.7 のチェックリストは書き換えない（過去の記録である）
- **v0.8 のチェックリストがハーネスの最初の顧客**になる（[開発計画 §6](../01_development-plan.md)）
- **ハーネスは対話するので、AI エージェントからは実行できない**（標準入力が無い）。エージェントが確かめられるように `-List`（解析結果の表示）と `-Answers`（回答を書いたファイルを流し込む自己テスト）を持たせる。**`-Answers` は受け入れ本番では使わない** — 人が打っていないものを「通過」と書けてしまう道具なので、使うと記録にその旨が残るようにする
- **v0.7 の 3 つの穴のうち、ハーネスが自力で塞ぐのは 1 と 2 である。** 3（写し漏れ）は「写す作業そのものを無くす」ことで塞ぐ。1 の残り（打った刻印そのもの）は人しか知らないので、**記録を必須にすることで空欄を作れなくする**までが手当てである
