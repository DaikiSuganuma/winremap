## 0. このバージョンの性格

v0.7 が**利用者から見た欠落**（記号キー）を埋めた版だったのに対し、v0.8 は**作る側と確かめる側の作業を軽くする版**である。4 件のうち 2 件（Zola 化・受け入れの対話化）は利用者から直接は見えない。

見える 2 件（IME のカーソル・`--debug` のコンソール）にも共通点がある。**どちらも「状態が見えない」ことへの手当て**である — IME がオンかどうか、起動時と終了時に何が起きたか。

## 3. Phase B — IME の状態をカーソルの色で示す

**決定は [ADR 0067](decisions/0067-ime-cursor-color.md) にある。** `SetSystemCursor` で `OCR_NORMAL` と `OCR_IBEAM` を差し替え、復元は `SPI_SETCURSORS`。

### この Phase の重さは「色を変えること」ではない

**セッション全体の状態を触るので、WinRemap が死んだあとにも残る。** ADR 0067 の決定 3〜5（panic / 未処理例外 / `WM_ENDSESSION` での復元、起動時の無条件復元、「色が残っていてトレイに居ない＝異常終了」と読める形の設計と文書化）が実装量の大半である。

### タスク

1. `src/cursor.rs` を新設し、`unsafe` をそこに閉じ込める。**AGENTS.md 不変条件 3 の許可リストを改訂**する（前例: [ADR 0031](../v0.2/decisions/0031-notify-module-unsafe-allowlist.md)）
2. 差し替えと復元。**`CopyIcon` した複製を渡す**（`SetSystemCursor` はハンドルを破棄する）
3. 既存の IME 通知経路（[ADR 0033](../v0.2/decisions/0033-ime-status-across-input-threads.md)）から呼ぶ。**フックには手を入れない**
4. 終了経路 5 種の復元（ADR 0067 決定 3 の表）
5. 起動時の無条件復元（機能が有効なときだけ `SPI_SETCURSORS` を打つ）。**痕跡ファイルは置かない**
6. 設定項目（**既定はオフ**）と、設定ウィンドウでの色の選択。**IME オフのときは素のカーソルのまま**にする（残るとしたら必ず色付き、という読み方を成立させるため）
7. 文書化 — 「色が変わったままでトレイに居なければ異常終了」（README・ヘルプサイト）

### 完了条件

- IME のオン・オフでカーソルの色が変わる（**入力欄の上でも**変わること — I ビームを差し替えている理由）
- `Stop-Process -Force` で殺すと**色付きのまま残り**、トレイに居ないことと合わせて異常終了と読める。**次に起動すると戻る**
- 独自のカーソルテーマを使っている環境で、復元後に**そのテーマに戻る**

### 実施記録（2026-08-02）— **実装完了**

`feature/ime-cursor`。`src/cursor.rs` を新設（`unsafe` はここに隔離。AGENTS.md 不変条件 3 を改訂）。設定は `[ime_indicator]` に `change_cursor_color` / `cursor_color` を追加し、**パネル（`enabled`）とは独立**にした。

[`tests/acceptance/probe-ime-cursor.ps1`](../../tests/acceptance/probe-ime-cursor.ps1) が **8/8 通過（7 回連続）**（システムのカーソルの画素を直接読む検査）。起動時の残骸消去・IME オンで着色・**I ビームが形を保つ**・**形がアルファと AND マスクの両方に入っている**・**白い縁がある**・オフで復元・**強制終了で色が残る**・次の起動で戻る。

**オーナーが実際に使って 3 件出た**（2026-08-02）。①標準の I ビームは**画面を反転して描かれている**カーソルで、その画素を透明に落としていた（Zed で黒い四角）。②形を**アルファだけ**で表していたので、**アルファを読まない描画経路**（Zed がこれ）では全面不透明の四角になった。③**暗いアプリでカーソルを見失う** — 着色は白い本体を指定色に落とすが `#0078d4` は白の 37% の明るさで、画面でいちばん明るかったものが中くらいになる。**白い縁を合成して足す**方式で解決（オーナー決定）。3 件とも修正済み・検査に項目を追加。**既定の色も `#0078d4`（アイコンの青）に変更**（オーナー決定）。

実装で分かったことは [ADR 0067](decisions/0067-ime-cursor-color.md) の「実装で分かったこと」に集約した。要点は 6 つ:

- **`SPI_SETCURSORS` だけでは戻らないことがある**（既定スキームではレジストリの値が空）。`user32.dll` の標準カーソルを入れ直してから `SPI_SETCURSORS` を打つ 2 段構えにした
- **明るさが正反対の 2 色で作る。** 色だけでは背景次第で消える。白い縁は「塗り替える」のではなく**形から合成する** — この機械の標準の矢印には黒い輪郭が 1 画素も無く（白 77 画素と半透明の落ち影 67 画素だけ）、塗り替える対象が存在しない
- **形はアルファと AND マスクの両方に書く。** Windows の描画経路は 1 つではなく、アルファを読まない経路では AND マスクがそのまま効く。全ゼロのマスク ＝ 塗りつぶしの四角
- **32bpp でアルファが一様に 0 だと、Windows はアルファ無しと解釈する。** 反転で描かれる画素は塗る画素として扱い、色ビットマップは `CreateDIBSection` で作る
- **検査が前面ウィンドウを支配できないと、黙って別のものを測る。** IME の状態はウィンドウごとで、`SetForegroundWindow` は前面でないプロセスからは拒否される。`AttachThreadInput` で取り、**取れなければ落とす**。注入キーへの依存はやめた（同じ機械の同じ午後の中で挙動が変わった）
- **カーソルのハンドルはプロセスごとにキャッシュされる。** 同じプロセスで 2 回読むと復元を見落とす — この誤読で 1 時間溶かした

`cargo test` 137 件通過、`clippy`（通常・test-inject とも）警告なし、`fmt` クリーン。

## 4. Phase C — `--debug` を `AllocConsole` にする

### なぜやるか

オーナーの目的は「**起動時の挙動や終了時の挙動をログ表示で確認する**」ことである。現状はこれができない。

- 起動元のターミナルに書いているので、**シェルのプロンプトと出力が重なる**（[v0.7 §6.3](../v0.7/03_acceptance-checklist.md)。ADR 0029 の既知の帰結で、WinRemap 側だけでは直せない）
- ログウィンドウは**起動後にしか開けない**ので、起動時のログは追えない

### 決定（[ADR 0068](decisions/0068-debug-console.md)）

[ADR 0029](../v0.2/decisions/0029-attach-console-and-tray-log-window.md) は `AllocConsole` を「ログウィンドウがあるので不要」として却下していた。**覆す根拠は、ログウィンドウがプロセスの寿命の内側でしか存在できないこと**である — 起動時のログは開く前に流れ、終了時のログはウィンドウごと消える。

### タスク

1. `--debug` かつ**リダイレクトされていない**ときだけ `AllocConsole`。起動の最初の 1 行から自前の窓へ出す
2. **終了時は、窓が閉じられるか Enter が押されるまで待つ**（オーナー決定）。**これが無いと窓はプロセスと同時に消え、終了時のログは読めない**
3. **`WM_ENDSESSION`（サインアウト・シャットダウン）では待たない。** OS の終了処理を待たせない
4. **リダイレクト時は従来どおり**リダイレクト先へ書き、待ちもしない。**UI テストがここを踏んでいる**（壊すと自動テストが全滅する）
5. 新しいコンソールの**出力コードページを明示する**。既定は OEM で、日本語のログがそのままでは化ける
6. `--help` / `--version` / 起動時エラーは**従来どおり起動元のターミナルへ**（ADR 0029 の意図は保つ）

### 完了条件

- 起動時のログが**1 行目から**見える
- 終了時のログが**読める**（閉じるまで残る）
- **[H-10](../v0.7/03_acceptance-checklist.md) を書き換える** — 「端末を閉じると終了する」→「**`--debug` の窓を閉じると終了する**」。無印の挙動は変わらない
- ヘルプサイト FAQ の回避策（`Start-Process ... -NoNewWindow -Wait`）を**不要になったので消す**

### 実施記録（2026-08-02）— **実装完了**

`feature/debug-console`。`Cargo.toml` を 0.8.0 に上げ、`notify.rs` に `open_debug_console` と `wait_for_debug_console` を足した（`unsafe` は `notify.rs` の中で収まっており、不変条件 3 の改訂は不要だった）。

| 確かめたこと | 結果 |
|---|---|
| `cargo test` / `clippy --all-targets -D warnings` / `fmt --check` | **135 件通過・警告なし・差分なし** |
| 起動時のログが 1 行目から出る | **出た。** タイトル `WinRemap --debug` の専用コンソールに、`WinRemap v0.8.0 を起動しました` から |
| 終了時のログが読める | **読めた。** トレイ →「終了」のあと `[操作] 終了` → セッション終了行 → 待機行が残り、**プロセスが生きたまま待っている** |
| 起動時エラーでも待つ | **待った**（多重起動のエラーで確認） |
| 文字化け | **無し。** 出力コードページは 932 のままだが、Rust の標準出力がコンソール宛には `WriteConsoleW` を使うため。画面バッファを読んで `U+306F`（は）が入っていることを確認 |
| リダイレクト時の従来動作 | **VM の `00-log-view`（26/26）と `06-foreground-line`（12/12）が PASS。** `the-console-says-the-same` と `no-debug-means-no-console-output` が、まさにこの経路を見ている |

**待っている間はプロセスが生きたまま**なので、`--debug` の窓を閉じるまで `winremap.exe` は置き換えられない（開発中に `cargo build` が「アクセスが拒否されました」で落ちる原因が 1 つ増える）。

## 5. Phase D — 受け入れテストの対話化（**ADR 0069 が要る**）

### 何を解くのか

v0.7 の受け入れで実際に起きたことが、そのまま要件である。

- **配列の記録が空のまま残った。** S-1〜S-5 は通ったが、「どの機械のどのキーで確かめたか」が書かれていない。記号キーは**機械によって答えが変わる機能**なので、この記録が無いと次の版で使えない
- **測れない項目が混ざる。** P-8・P-9 の Store 経路は認定通過後にしか測れず、「通過」と書くと嘘になる
- **手順とチェックリストと記録欄が別々の場所にある。** 人が写す作業が発生し、写し漏れる

### 形（案）

`tests/ui` の資産を流用し、**1 項目ずつ進む対話ハーネス**にする。

1. **環境を準備する**（設定の退避と配置、対象アプリの起動、ログウィンドウを開く）— ここは自動
2. **何を打つかを提示する**（「メモ帳で `abc` と打ち、`Ctrl` を押しながら `;` のキー」）
3. **人が実キーボードで打つ** — **ここは絶対に注入しない。** 実キーボードで確かめること自体が目的である
4. **結果を選ぶ**（通過 / 不合格 / 未実施）＋ **自由記述**（「US 101 の `;`（`VK_OEM_1`）」のような、記録に残す価値のある一文）
5. **チェックリストの §7 に追記する** — 人が写さない

### 決定（[ADR 0069](decisions/0069-interactive-acceptance-harness.md)）

- **記録先はチェックリストの Markdown へ直接**。中間ファイルは挟まない（成果物が 2 つになるとずれる）
- **項目もチェックリストの Markdown から読む。** ハーネスに写さない — 写した瞬間「手順が 2 か所にある」が復活する
- **結果は 4 値**（通過 / 不合格 / 未実施 / 測れない）。**「測れない」には「何が揃えば測れるか」を必須**にし、`-Resume` の対象にする
- **実行環境（キーボード配列・版・OS）はハーネスが自動で刻む。** v0.7 で「配列を書いてください」と依頼して書かれなかったので、機械が知っていることは機械が書く
- 置き場所は **`tests/acceptance/`**（[`symbol-keys.toml`](../../tests/acceptance/symbol-keys.toml)・[`probe-ime-cursor.ps1`](../../tests/acceptance/probe-ime-cursor.ps1) と同居）

### 実施記録（2026-08-02）— **実装完了**

`feature/acceptance-harness`。[`tests/acceptance/run-acceptance.ps1`](../../tests/acceptance/run-acceptance.ps1)。

.\tests\acceptance\run-acceptance.ps1 <checklist> -Resume         # 未記録＋測れない／不合格
.\tests\acceptance\run-acceptance.ps1 <checklist> -List           # 解析結果だけ表示

| 列の見出し | **表ごとに違う 4 列目**（§4 は「通過条件」、§3 は「v0.7 での見どころ」）を、その表の見出しのまま表示する |

- **v0.8 のチェックリストには `<!-- harness:begin -->` / `<!-- harness:end -->` を入れること**（Phase E）

### 作り直し（2026-08-03）— **対話の主体が違っていた**（[ADR 0070](decisions/0070-agent-led-acceptance.md)）

`fix/acceptance-agent-led`。上の実装は対話を PowerShell の `Read-Host` に置き、**AI エージェントを対話から締め出していた**。オーナーの想定は**この会話欄での対話**（エージェントが司会し、人は打って報告する）だったので、主体を入れ替えた。

- **`run-acceptance.ps1` から `Read-Host` を全部外し、非対話のコマンド群にした** — `-Show`（読み上げる中身）／`-Prepare`（設定の配置と WinRemap の起動）／`-Record`（追記）／`-Teardown`（戻す）／`-Environment`
- **進行の手順は [`/acceptance` スキル](../../.claude/skills/acceptance/SKILL.md)へ。** 次に受け入れを回すエージェントが、ADR から手順を組み立て直さずに済む
- **記録の見出しが誰の答えかを名乗る** — 既定は「対話: 人が実キーボードで確認し、AI エージェントが記録」、`-SelfTest` のときだけ「人は打っていない」
- **相対パスで書き戻しだけが落ちる不具合を直した** — `[IO.File]` はプロセスのカレントディレクトリ（PowerShell を開いた場所）を見るので、`Test-Path` は通るのに書き戻しがホームディレクトリを探していた

## 7. フェーズ順序と依存関係

```
Phase A（Zola 化）──────────────┐
                                ├──▶ Phase E（文書・受け入れ・リリース）
Phase C（AllocConsole）──┐      │
                         ├──▶ Phase B（IME カーソル）──┘
Phase D（対話ハーネス）──┘
```

- **C を先に**やる。小さく閉じており、**以降の開発とデバッグが楽になる**（起動時と終了時が見えるようになる）
- **A は Rust に触らない**ので、C・B と並行できる
- **B は C の後**が望ましい。異常終了まわりの確認は、起動時・終了時のログが見えるほうが速い
- **D は B より前**に形だけ用意できると、B の受け入れ（プロセスを殺してカーソルが残ることの確認）をそのハーネスで行える

> **実際の順序は C → A → B → D になった**（2026-08-02）。B が先に済んだのは、オーナーが実際に使って不具合が 2 件出たためである（[§3 の実施記録](#3-phase-b--ime-の状態をカーソルの色で示す)）。**B の受け入れは Phase E で、D のハーネスから行う。**
