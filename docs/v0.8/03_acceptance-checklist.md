## 0. この文書の目的

v0.8 は**作る側と確かめる側の作業を軽くする版**である（[開発計画 §0](01_development-plan.md)）。4 件のうち 2 件は利用者から直接は見えない。したがって確認すべきことは 3 種類ある。

1. **見える 2 件が実際に効くこと** — `--debug` のコンソール（**C-1〜C-5**）と IME のカーソル（**M-1〜M-6**）
2. **見えない 2 件が壊していないこと** — ヘルプサイトは Zola の生成物に変わった（H-9 で見る）、受け入れの手順はこのハーネスに変わった（この文書を使うこと自体が確認になる）
3. **これまでどおり動くこと** — **H-1〜H-10** と **P-1〜P-9** を継承する

### この版で特に注意すること

- **`--debug` の挙動が変わった。** ターミナルに書くのをやめ、専用のコンソールを開いて**閉じられるまで残る**（[ADR 0068](decisions/0068-debug-console.md)）。**H-10 はそのために書き換えてある** — 旧版の記述で試すと不合格に見える
- **カーソルの色はセッション全体の状態を変える。** WinRemap を殺すと**色が残る**。これは不具合ではなく設計である（[ADR 0067](decisions/0067-ime-cursor-color.md) 決定 4）。M-4 でそれ自体を確かめる
- **v0.7 から持ち越した空欄がある。** S-6（配列の切り替え）と、Store 側の P-8・P-9。[§6](#6-持ち越しと測れない項目) を先に読むこと
- **リリースビルドで通す。** `build.ps1` は既定で `-Configuration release`
- **自動テストはパッケージ版を見ていない。** 動かすのは素の `winremap.exe` である。これが P-1〜P-9 の存在理由

## 1. 毎リリースの手順

```powershell
cargo fmt --check
cargo clippy --all-targets -- -D warnings
cargo test                              # 設定の検証・キー記法・記号キー・i18n・パス写像
.\site-src\build.ps1 -Check             # site/ が site-src/ から作った通りか（ADR 0066）
cd tests\ui
.\run-vm-ui-test.ps1                    # ゲスト VM での UI 自動テスト一式（全 10 件）
cd ..\..
cargo build --release --features test-inject
.\tests\acceptance\probe-ime-cursor.ps1 # カーソルの画素を直接読む検査（8 項目、ADR 0067）
cargo build --release                   # 受け入れは素の配布ビルドで行う
```

**自動側は Claude Code が回す。所要時間と、人の作業を邪魔するかは次のとおり**（2026-08-03 実測）。

| 手順 | 所要 | 人の作業を邪魔するか |
|---|---|---|
| `cargo fmt --check` | 1 秒 | しない |
| `cargo clippy --all-targets` | 7 秒（**初回は数分**） | しない（CPU は使う） |
| `cargo test` | 6 秒 | しない |
| `site-src\build.ps1 -Check` | 2 秒 | しない |
| `run-vm-ui-test.ps1`（全 10 件） | **26 分** | **少し邪魔する** — VMware のウィンドウが開き、ゲストの起動時に前面を取ることがある。1 件だけなら約 2 分（`-Check 05-remap-notepad`） |
| `cargo build --release [--features test-inject]` | 21 秒ずつ | しない |
| `probe-ime-cursor.ps1`（8 項目） | 21 秒 | **強く邪魔する。下記** |

**`probe-ime-cursor.ps1` の間は機械に触らないこと。** この検査は**セッション全体のマウスカーソルを差し替え**、メモ帳と `winver` を開いて**前面を何度も奪い**、IME を切り替える。しかも一方通行ではない — **人が前面を動かすと、検査のほうが誤る**。カーソルの色は前面ウィンドウの IME に従うのが仕様なので、前面が流れた先に合わせた**正しい色**を「WinRemap の不具合」と読んでしまう（2026-08-03 の受け入れで 20 回中 3 回、毎回ちがう項目が落ちた。[ADR 0067](decisions/0067-ime-cursor-color.md)「受け入れの実施で分かったこと」）。**現在は前面が保てなければ検査自身が落ちる**ようにしてあるが、その回はやり直しになる。

> したがって**自動側は席を外す時間（昼休みなど）に回すのがよい**。全部で **30 分弱**、うち 26 分が VM である。

1. 上が緑であること。**落ちたら手動へ進まない**（v0.5 以来の規律 — 自動側の判定が壊れているほうが重い）
2. 手動の項目は **Claude Code との対話で進める**（[ADR 0069](decisions/0069-interactive-acceptance-harness.md)・[ADR 0070](decisions/0070-agent-led-acceptance.md)）。Claude Code で:

```
/acceptance docs\v0.8\03_acceptance-checklist.md
```

   **司会は Claude Code が務める。** 環境の準備（設定の退避と配置、WinRemap の起動）を行い、項目を 1 件ずつ読み上げる。**人がすることは、実キーボードで打って、見えたことを自分の言葉で言うこと**だけ。4 値への分類と記録の文は Claude Code が案を出し、**確認を取ってから** [§8](#8-対話ハーネスの記録) の記録欄へ追記する。**人が写す作業は無い。**

   続きからは「続きから」（`-Resume` 相当）、一部だけなら「C-1 と M-4 だけ」と言えばよい。止めたいときはそう言えば、その場で片付け（設定を戻す）まで行う
3. **キーは実キーボードで打つこと。** ハーネスは 1 つもキーを注入しない — 注入で足りるものは `tests/ui` が既に見ている
4. §7 に、その回の全体的な判断（省略した項目とその理由など）を散文で書く
5. **Store 側（P-8・P-9）は認定通過後**に `-Resume` でもう一度回す

### 2.2 `--debug` の専用コンソール（[ADR 0068](decisions/0068-debug-console.md)）

| # | 何を見るか | 手順 | 通過条件 |
|---|---|---|---|
| **C-1** | **起動時のログが 1 行目から読める** | ターミナルで `.\winremap.exe --debug` | ①**別のコンソールウィンドウ**が開く（タイトル `WinRemap --debug`） ②`WinRemap v0.8.0 を起動しました` から**すべて**出ている ③起動元のターミナルのプロンプトと**重ならない**（v0.7 §6.3 の症状が消えている） |
| **C-2** | **終了時のログが読める** | C-1 の状態でトレイ →「終了」 | ①`[操作] 終了` とセッション終了行が出る ②**ウィンドウが消えない**（待機している） ③Enter か閉じるボタンで終わる |
| **C-3** | **窓を閉じると WinRemap も終わる** | C-1 の状態で、動作中に `--debug` の窓を閉じる | ①WinRemap が終了する（トレイから消える） ②**カーソルの色を使っていた場合、色も戻る**（[ADR 0062](../v0.6/decisions/0062-detach-console-when-resident.md) の経路） |
| **C-4** | **リダイレクトすると従来どおり** | `Start-Process .\winremap.exe -ArgumentList '--debug' -RedirectStandardOutput log.txt`（**シェルの `>` では確かめられない。下記**） | ①**窓は開かない** ②`log.txt` に同じ内容が入る ③**待たない**（プロンプトが戻る）④**常駐が続く**。この経路は UI テストが踏んでいる |
| **C-5** | **`--help` と `--version` は起動元へ** | `.\winremap.exe --help` と `--version` | 起動元のターミナルに出る（専用の窓を開かない）。[ADR 0029](../v0.2/decisions/0029-attach-console-and-tray-log-window.md) の意図を保っていること |

**C-4 でシェルの `>` が使えない理由**（2026-08-04 に判明。[ADR 0071 の訂正](decisions/0071-debug-console-must-not-kill-the-app.md#2026-08-04-の訂正決定-3-の表が誤っていた)）。WinRemap は `windows` サブシステムのバイナリで、**この 2 つは事情が違う**。

| 経路 | 標準出力が WinRemap に届くか | 結果 |
|---|---|---|
| PowerShell の `>` | 届く（パイプ） | **ファイルは空**。PowerShell は GUI サブシステムのプロセスを待たないので、常駐に入る前にパイプを閉じる |
| `cmd /c "… > log.txt"` | **届かない** | **窓が開き**、ファイルは空。cmd は `>` を自分の標準ハンドルの差し替えで実装しており `STARTF_USESTDHANDLES` を使わない。Windows は GUI サブシステムの子プロセスにその経路で標準ハンドルを渡さないので、WinRemap からは**未リダイレクトに見える** |
| `Start-Process -RedirectStandardOutput` | 届く | **通る。これで確かめること** |
| Git Bash の `>` | 届く | 通る（MSYS は `STARTF_USESTDHANDLES` で渡す） |

見分け方は `--help` で足りる — ヘルプは必ず何か出すので、**`--help` をその経路に流して 0 バイトなら、その経路では届いていない**。

### 2.3 IME をマウスカーソルの色で示す（[ADR 0067](decisions/0067-ime-cursor-color.md)）

**§2.1 の設定で行う。** `tests\acceptance\probe-ime-cursor.ps1` が画素の水準では確かめているので、ここで見るのは**人の目でしか分からないこと**である。

| # | 何を見るか | 手順 | 通過条件 |
|---|---|---|---|
| **M-1** | **IME のオン・オフで色が変わる** | メモ帳で IME をオンにし、マウスを動かす。オフに戻す | ①オンで**矢印に色が付く** ②オフで**素に戻る** ③切り替えてから色が変わるまでが**待たされる感じでない** |
| **M-2** | **入力欄の上でも変わる**（I ビーム） | 同じ状態で、テキストの上へマウスを乗せる | ①I ビームにも色が付く ②**黒い四角にならない**（形が残っている） ③**暗い背景のアプリ**（Zed など）でも**見失わない**（白い縁が効いている） |
| **M-3** | **管理者権限のウィンドウの上では変わらない**（**2026-08-03 に書き換え**） | 管理者権限のターミナルを前面にして IME をオン | **色は変わらず、パネルも出ない。** リマップが効かないのと同じ理由（UIPI）である — IME の状態は相手ウィンドウへのメッセージ送信で読むので、昇格した窓の向こうは見えない。カーソルの**描画**はセッション全体に効くが**検知**が届かない。回避には昇格が要り、不変条件 5 で禁じている（[ADR 0071](decisions/0071-debug-console-must-not-kill-the-app.md) と同じ回で判明） |
| **M-4** | **強制終了すると色が残り、次の起動で戻る** | IME をオンにして色が付いた状態で `Stop-Process -Name winremap -Force`。そのあと WinRemap を起動し直す | ①**色が残る** ②トレイに居ないことと合わせて「異常終了した」と読める ③**起動し直すと戻る**（何も操作せずに） |
| **M-5** | **独自のカーソルテーマが保たれる** | カーソルのテーマやサイズを変えている場合、色を付けてから戻す | ①色付きでも**自分のテーマの形**である ②戻したあと**元のテーマに戻る**（標準カーソルに化けない）。**テーマを変えていなければ「未実施」** |
| **M-6** | **パネルを出さずにカーソルだけ使える** | 設定を `enabled = false` ＋ `change_cursor_color = true` にして再読み込み | ①「あ」パネルは出ない ②カーソルの色は変わる（2 つが独立していること） |

### 2026-08-03 の回で分かったこと

**リリース前に手当てが要るものが 2 つある。** どちらも `--debug` 経路で、[ADR 0068](decisions/0068-debug-console.md) がこの版で触った領域である。

1. **PowerShell の `>` でリダイレクトすると panic して常駐ごと死ぬ**（C-4、不合格）。`failed printing to stdout: パイプを閉じています (os error 232)`。PowerShell の `>` はネイティブ exe の出力をいったんパイプで受けるので、常駐に入って端末を手放した時点でそのパイプが閉じ、次の書き込みで落ちる。**`cmd /c … > file` なら通る**（常駐が続き、ログも全部入る）。stdout が消えたくらいで常駐が落ちるのは [ADR 0062](../v0.6/decisions/0062-detach-console-when-resident.md) の「端末を手放しても効き続ける」に反する
2. **`--debug` の窓を 1 回クリックするとリマップごと止まる**（項目に無い。この回の発見）。`open_debug_console()`（`src/notify.rs`）は `AllocConsole` の直後にタイトルを付けるだけで**コンソールのモードに触っていない**ため、既定で有効な **QuickEdit** の選択モードに入り、そこへの書き込みがブロックされる。書いていたスレッドが止まると低レベルフックが `LowLevelHooksTimeout`（既定 300 ms）を超え、**Windows がフックの呼び出しを捨てる** — ログが止まるだけでなくリマップが効かなくなる。**不変条件 1（フックを止めない）に直撃する。** 実際この回は、これを踏んだまま M-1 を 2 度やり直している。`SetConsoleMode` で `ENABLE_QUICK_EDIT_MODE` を落とすのが手当て

**文書側の誤りが 1 つ。** M-3 の通過条件「リマップは効かないが、カーソルは効く」は**想定が誤っている**（不合格）。カーソルの*描画*はセッション全体に効くが、IME 状態の*検知*は `SendMessageTimeoutW(WM_IME_CONTROL)` のクロスプロセス送信なので **UIPI に遮断される**。管理者権限のウィンドウが前面のあいだは色もパネルも出ない。回避には昇格が要り、それは**不変条件 5 で禁じている**。本項目と README の Limitations を書き換えること。

**受け入れ用の設定の不備を 1 つ直した。** [`ime-cursor.toml`](../../tests/acceptance/ime-cursor.toml) に `trigger_keys` が無く、**`半角/全角` キーを持たないキーボード**（`Ctrl+Space` で切り替える）では IME を切り替えても追随しなかった（[ADR 0021](../v0.2/decisions/0021-ime-indicator-trigger-keys.md) のとおりの仕様）。`trigger_keys = ["C-Space"]` と `show_app_name = true` を足して M-1 を確認し直した。**この不備は「WinRemap の不具合」に見えた** — 受け入れ用の設定は、その機械で実際に使える形になっていないと項目の判定を誤らせる。

**上の 2 件は同日中に直した**（[ADR 0071](decisions/0071-debug-console-must-not-kill-the-app.md)）。自前のコンソールで QuickEdit を切り、コンソールへの書き込み失敗で panic しないようにした。**窓の中をクリックしても止まらないことはオーナーが実際にクリックして確認済み**。PowerShell の `>` は panic しなくなったが**ファイルは空のまま**で、これは PowerShell が GUI サブシステムのプロセスを待たない性質なので直せない — C-4 の手順を `cmd /c` へ書き換えた。**§8 の C-4 は不合格のまま残してある**（書き換えた手順での再実行がまだなので、次の回に `-Resume` で戻ってくる）。M-3 の想定誤りも同日、README（en/ja）とこの表を書き換えて解消した。

**ハーネス自体について**（§0 の 2「この文書を使うこと自体が確認になる」）。[ADR 0070](decisions/0070-agent-led-acceptance.md) の対話形式で回した初回である。人が写す作業は実際に無く、11 件で記録の空欄も出なかった。**効いたのは、症状の切り分けをその場でできること**だった — C-4 は `cmd` 経由との比較を、QuickEdit はログの時刻の欠落を、M-1 は設定の読み合わせを、いずれも会話の途中で行って原因まで届いている。`Read-Host` 版なら「不合格」とだけ書いて終わっていた。

### 2026-08-04 の回で分かったこと

**前日「直した」と書いた 2 件のうち、片方は手順のほうが誤っていた。** C-4 の差し替え先に書いた `cmd /c "… > log.txt"` は通らない。cmd は `>` を自分の標準ハンドルの差し替えで実装しており `STARTF_USESTDHANDLES` を渡さないので、**Windows が GUI サブシステムの子プロセスに標準ハンドルを渡さない** — WinRemap からは未リダイレクトに見え、設計どおり窓を開き、ファイルは空のままになる。WinRemap 側に不具合は無い。正しい経路は `Start-Process -RedirectStandardOutput`（と Git Bash の `>`）で、そちらでは 4 条件とも満たした。**08-03 の調査でこの行を書いたとき、`cmd /c` を実際に通した記録が無い。確かめずに書いた 1 行が、翌日の受け入れで人の時間を使わせた**（[ADR 0071 の訂正](decisions/0071-debug-console-must-not-kill-the-app.md#2026-08-04-の訂正決定-3-の表が誤っていた)）。判定は `--help` を流すだけで足りる — **0 バイトなら届いていない**。

**QuickEdit と panic の手当ては効いていた。** 誤った `cmd /c` 経路を踏んだこと自体が、期せずしてその確認になっている — 前日はここで `os error 232` の panic とともにトレイから消えていたのに、この回は常駐が続いた。

**H-2 の実施中に、カーソルの色そのものの不具合が 2 件出た。** どちらも「打鍵が引っかからないか」を見ている最中に**目で見つけた**もので、項目としては H-2 は通過している。

1. **IME がオンのままカーソルの色だけ消える**（M-1、不合格）。変換途中でマウスカーソルを窓の外へ出し、確定してから戻すと、IME はオンなのに色が付いていない。IME を打ち直すと戻る。**筋の通らない箇所は見つかった** — `detect::query_foreground()` の `open` は 3 値で `None` は「オフ」ではなく「分からなかった」と `detect.rs` に明記してあるのに、呼び出し側が `== Some(true)` でその区別を捨て、不明のときに色を外していた（[ADR 0072](decisions/0072-cursor-keeps-tint-when-state-unknown.md) で修正）。**ただしそれが原因だと確かめたわけではない。** 修正後の再現では、4 分間のログに「不明」が 1 行も出なかった。**M-1 は次の回で再確認するまで不合格のままにしてある**
2. **IME をオンにすると I ビームが消える**（M-2、不合格）。Zed でもメモ帳でも、I ビームの状態から IME をオンにすると I ビームが見えなくなり、オフにすると見える。矢印のほうは色が付く。**08-03 に M-2 を通過としたのは誤判断だった** — そのとき同じ症状を「入力すると I ビームが消える」と受け取り、Windows が打鍵中にポインターを隠す仕様だと解釈した。今回**打鍵しなくても起きる**ことが分かって覆った。原因は未特定。画面に触らない読み取り検査で `restore()` が入れ直す stock の I ビームは系のものと同一（`mask=32x64/1bpp`・color 無し）と確かめ、**「復元が I ビームを壊す」説は否定した**。残る筋は `SPI_SETCURSORS` と色付きカーソルの作り置きの競合だが、裏は取れていない

**「再現しない」を結論にしないこと。** この回はどちらも再現しなかったが、**オーナーが 2 度見ている**ものを再現待ちで消さず、不合格のまま残した。カーソルの色は**間欠的にしか壊れない**種類の機能である（前面・IME・他プロセスの応答性に依存する）ので、記録のほうを証拠として扱う。

**分かった副産物。** ログを見ると **Zed は IME の状態が常に「オフ」と読まれている**（09:13:58・09:15:13）。M-2 の原因かどうかは別として、独自に入力を処理するアプリでは検知が届かないことがある、という材料である。次の版で見ること。

## 9. 記録の書き方

v0.5 の記録欄（[§6](../v0.5/03_acceptance-checklist.md)）が見本である。**「OK」だけを書かない。** 何をどう確かめたか、省略したなら省略した判断を残す。落ちた項目は、落ちた事実と原因の切り分け結果まで書く。**ハーネスは 4 種類すべてで記録を必須にしている**ので、空欄では先へ進めない。

この版で特に残す価値があるのは次の 3 つである。

- **M-2 を、実際にどのアプリの、どんな背景で見たか。** 「見えた」ではなく「Zed のダークテーマの本文の上で、白い縁が見えた」と書く。この項目は**背景の明るさによって答えが変わる**ので、明るいアプリだけで見た記録は次の版で使えない
- **C-1〜C-3 を、どのターミナルで行ったか。** `--debug` の重なりは PSReadLine の再描画が原因だった（[v0.7 §6.3](../v0.7/03_acceptance-checklist.md)）ので、**Windows Terminal / PowerShell / cmd のどれで見たか**に意味がある
- **省略した項目と、その判断。** 「前回から変更なし」も判断である。埋まっていない空欄がどこにあるかが分かるほうが、埋まったふりより価値がある
