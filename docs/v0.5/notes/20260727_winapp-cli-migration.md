## 0. 結論（先に書く）

**進める価値は高い。ただし §3 の測定ゲートを通してから移植を始める。**

理由は 1 つで、我々の側にすでに実測があるからである。同じ 2 つのボタンを押すのに、

| 経路 | 実測 |
|---|---|
| terminator `click_element`（実体は**座標クリック**） | Edit **2 / 6**、Clear **2 / 4** |
| 素の .NET UIA クライアント（`InvokePattern`） | Edit **4 / 4**、Clear **4 / 4** |

winapp CLI の `invoke` は後者と同じ UIA パターン駆動である（[03](../../../../../GitLab/windows-utility/docs/projects/20260726_winappCLI比較検証/03_検証レポート_トレイメニュー操作.md) でメニュー項目の起動に使われているのがまさにこれ）。したがって**「押下が半分しか当たらない」問題は移行で消える見込みが高い**。

ただし注意すべき点がある。**その利得だけなら winapp CLI は要らない**。`tests/ui/guest/dump-uia.ps1` が素の .NET UIA でそれを達成済みだからである。よって本検証の焦点は「winapp CLI でしか得られないものが、依存を1つ増やすに値するか」であり、それは §3 の P4〜P7 で測る。

## 1. いま不安定さはどこにあるのか

v0.5 Phase A でここまでに切り分けた結果、原因は 3 層に分かれている。**移行で効くのは 2 と 3 だけ**で、1 は済んでいる。

| 層 | 中身 | 状態 |
|---|---|---|
| **1. アプリ層** | 設定・ログウィンドウが UIA に出ない | **解決済み**（ADR 0055 / eframe フォーク）。設定 43→59→72 個、ログ 7 個の子孫が見える |
| **2. 操作層** | terminator のクリックが座標クリックで、反映も遅れる | **未解決**。上表のとおり半分。回避として押下をシナリオから外し `dump-uia.ps1` へ移した |
| **3. エージェント層** | LLM がツリーを読み違える／途中で止まる／プロンプト欠損に気づかない | **未解決**。ただし 2026-07-28 の 2 通しでは 6 件とも両回一致し、1 シナリオ 1〜3.5 分まで縮んだ（12〜14 分かかっていたのは専用 VM へ移す前）。**「ぶれなかった 2 回」であって「ぶれない」ではない**ので、層としては未解決のまま置く |

3 について記録しておく価値があるのは、**エージェントが「アプリの不具合」と報告した 3 件がすべて実測で否定された**ことである。

- 「WinRemap がインストールされていない」→ 直接叩いて存在と起動を確認
- 「プロンプトが文字化けして届いていない」→ 送受信 2276 / 2276 文字で一致。真因は PowerShell 5.1 の引数クォート欠落（2557→1687 文字）
- 「Clear を押してもログが消えない」→ 素の UIA で 7 個 → 3 個。エージェントがクリック前のツリーを読んでいた

**判定が誤るだけでなく、誤りの向きが「アプリのせい」に偏る。** これが最も高くついている。移行の本命は速度でも機能でもなく、**LLM を判定ループから外すこと**である。

## 2. winapp CLI で何が変わるか（と、変わらないか）

### 2.1 得られるもの

| # | 得られるもの | いま何が困っているか |
|---|---|---|
| A | **`invoke`（UIA パターン駆動）** | 座標クリックの取りこぼし（2/6・2/4） |
| B | **`wait-for`（タイムアウトで exit 1）** | egui はオンデマンド再描画なので、クリック直後の読み取りが古い状態を返す。いまは `Start-Sleep 3` で誤魔化しており、**固定待ちである限り原理的に不安定**。01/04 の再発はここ |
| C | **メニュー項目をコマンド ID で列挙・起動**（`1003`=設定 / `1004`=ログを表示） | `#32768` は素の UIA でも terminator でも空の Pane にしか見えず、頭文字キー押下でしのいでいる。ID は安定（[03 §4](../../../../../GitLab/windows-utility/docs/projects/20260726_winappCLI比較検証/03_検証レポート_トレイメニュー操作.md)） |
| D | **`--json` / `ui record` / スクショ** | 判定をスクリプトで書ける。失敗時の診断が残る |
| E | ワンショット CLI | 常駐 MCP がゴールデンスナップショットに焼き付く問題、stdout を握って EOF 待ちになる問題の発生要因が消える |

B と C が **`dump-uia.ps1` を育てる路線では手に入らないもの**である。ここが依存を増やす対価に見合うかの判断点。

### 2.2 変わらないもの・悪くなるもの

| # | 事項 | 影響 |
|---|---|---|
| F | **`LLKHF_INJECTED` 問題は解決しない** | `--via send-input` は terminator と同じ SendInput、既定の `--via post-message` は低レベルフックを一切通らず**むしろ不可**。シナリオ 05 は `--accept-injected`（ADR 0053）前提のまま |
| G | **可視トレイ（`Shell_TrayWnd`）のアイコンは `click` できない** | 「前面でないウィンドウは押さない」という winapp の安全弁に阻まれる。**いまの `promote-tray-icon.ps1`（アイコンをタスクバーへ昇格させる）方式と正面から衝突する**。overflow 経路へ戻すことになる |
| H | **メニュー表示中は `send-keys` が使えない** | 頭文字キーのフォールバックが winapp では取れない。C（invoke）が動くことが前提条件になる |
| I | **egui/AccessKit の要素に `AutomationId` が無い** | セレクタは name 部分一致に頼る。スラッグ（`btn-...-7753`）はランタイム ID 由来で**ハードコード不可**。UI 文言を変えるとテストが壊れる前提になる。**未測定・最大の不確実性** |
| J | **public preview** | v0.5.0 で `ui` が大幅拡張された実績があり、コマンド仕様が変わりうる |

G は特に注意が要る。トレイ操作の経路が「昇格させて可視トレイを直接叩く」から「chevron を invoke → overflow ウィンドウ内で探す」へ変わるため、**`promote-tray-icon.ps1` は不要になるか、逆に邪魔になる**。

## 3. Phase 1 — 測定（決定ゲート）

移植の前にここで止まる。**ゲスト内スクリプト 1 本**（`tests/ui/guest/probe-winapp.ps1`）で完結させる。1 本にするのは winapp の制約（メニューはプロセスを跨ぐと解除される／`click` は前面のときだけ）に合わせるためで、これは移植後のシナリオの形そのものでもある。

| # | 測ること | 合格の目安 | 比較対象（実測済み） |
|---|---|---|---|
| **P1** | `winapp ui inspect` で設定ウィンドウの中身が見えるか | 子孫 40 個以上、`Edit` / `General` / `Keymaps` / `notepad` が引ける | 素 UIA で 43（キーマップ選択後 59／編集モード 72） |
| **P2** | ログウィンドウの行が読めるか | 行がテキスト要素として引ける | 素 UIA で 7 |
| **P3** | 要素の指し方と**安定性** | winremap を 3 回起動し直して同じセレクタで引ける | — |
| **P4** | `invoke` で Edit / Clear を押す × **各 10 回** | **10/10** | terminator 2/6・2/4 ／ 素 UIA 4/4 |
| **P5** | `wait-for` が Edit→`Save`/`Revert` の遷移を待てるか。exit code の意味 | 固定 sleep 無しで 10/10 | いまは `Start-Sleep 3` で不安定 |
| **P6** | トレイ経路。**(a) 昇格済み可視アイコン**と **(b) overflow** の両方 | どちらかが 10/10 で設定・ログを開ける | 現行は頭文字キー＋Enter |
| **P7** | 1 シナリオ相当の所要時間 | — | 現行 **1:06〜3:34／シナリオ**（2026-07-28 の 2 通し実測。§8）。専用 VM へ移す前は 3.5〜14 分だった |

### 書き方の制約（基盤側で実測済み）

probe を書く前提。出典は windows-utility の `test-vm/利用プロジェクト向けガイド.md` §4（すべて実機で確認済み）。

| 制約 | 正しいやり方 |
|---|---|
| `wait-for` は**セレクター必須**（位置引数）。省略は `A selector is required` で失敗 | 先に `winapp ui search <文字列> --app <アプリ>` か `inspect` で探す |
| `--timeout` は**ミリ秒**（既定 5000）。`--timeout 15` は 15 ミリ秒 | 秒で書かない |
| **`wait-for` はアプリの起動を待たない。** プロセスが無いと即失敗（粘らない） | 起動待ちは `Get-Process` |
| **`--gone` でアプリの終了は判定できない。** プロセスが消えると `--app` の解決自体が失敗する | 終了待ちも `Get-Process` |
| `list-windows` は該当ゼロでも**終了コード 0**（`Found 0 windows`） | 有無の判定に使わない。件数か `--json` を見る |
| スラッグ（`win-459b` 等）は実行ごとに変わる | 要素名か `AutomationId`（egui 側には無いので name） |

**負例を必ず入れる。** 「成功するはずのものが成功した」だけでは、アサーションが効いていないのか通ったのか区別できない。存在しない要素・異なる入力値で**確実に 0 以外になる**ことまで確認する。P4/P5 の測定にはこれを含める。

### 測定結果（2026-07-28 実施、[`tests/ui/guest/probe-winapp.ps1`](../../../tests/ui/guest/probe-winapp.ps1)）

ゲスト `winremap-test`／winapp CLI 0.5.0／WinRemap v0.5.0（`--lang en`、`minimal.toml`）。**14 チェック中 13 pass**。

| # | 測ったこと | 結果 |
|---|---|---|
| **P1** | 設定ウィンドウの中身 | **pass**。50 要素、`Edit`・`General`・`Keymaps`・`notepad` を名前で解決（素 UIA の 43 と数え方が違うだけ。キーマップ選択後は 66） |
| **P2** | ログウィンドウの行 | **pass**。テキスト要素 4（起動バナー・案内文・`[action]`・`[debug]`） |
| **P3** | 起動し直しての安定性 | **pass**。**3/3**。名前（`Edit`・`Keymaps`）は再起動をまたいで解決する |
| **P4** | `invoke` ×10 | **pass**。`Edit` **10/10**、`Revert` **10/10**（terminator は 2/6・2/4） |
| **P5** | `wait-for` | **pass**。**10/10**、固定 `Start-Sleep` 無しで遷移を捕まえた。負例も exit 1 |
| **P6** | トレイ経路 | (a) 昇格した可視アイコンは **不可**（`Shell_TrayWnd` は前面にならず `click` が拒否される）／(b) オーバーフロー経由は **10/10 pass** |
| **P7** | 所要 | probe 全体（トレイ 10 往復＋`invoke` 20 回＋再起動 3 回＋両ウィンドウの採取）で **3 分 40 秒** |

**新たに踏んだ落とし穴が 3 つある。どれも「アプリの不具合に見える」形で出た。**

1. **`wait-for` は、名前が複数の要素に一致すると「見つからない」と報告する。** `Save` はボタンと文中（「the file is untouched until you press Save」）の 2 か所に一致し、exit 1 で `'Save' not found` になる。同じ状態で `get-property` は「Selector matched 2 elements」と正しく言い、`search` は 2 件返す。**測定の 2 回分をこれで落とした**（「invoke は成功しているのに編集モードにならない」ように見えた）。対処は一意な名前を使うか、`search --json` でスラッグに解決してから渡すこと（スラッグ経由なら 21 ms で成功）
2. **chevron の `invoke` はトグルである。** 前の実行が開いたままだと閉じてしまい、10 回中 5 回失敗した（[03 の制約 1](../../../../../GitLab/windows-utility/docs/projects/20260726_winappCLI比較検証/03_検証レポート_トレイメニュー操作.md) が予告していたとおり）。「開いていたら閉じてから開く」を挟むと 10/10 になる
3. **PowerShell 5.1 から呼ぶときの作法が 2 つ。** 引数は**配列で渡す**（`ValueFromRemainingArguments` のパラメーターに配列を渡すと 1 本の文字列に潰れ、winapp は usage を出す）。読むのは**必ず `--json`**（テキスト出力は CP932 として読まれて文字化けする。JSON の `\uXXXX` は無事）。加えて `ConvertFrom-Json` の結果は**いったん変数に受けてから返す**（パイプラインのまま返すと配列が 1 要素のままになる）

### ゲートの読み方

| 結果 | 判断 |
|---|---|
| P1・P2 が取れない | **移行しない**。素 UIA では取れているので winapp 固有の問題。深追いせず terminator 継続 |
| P4 が terminator と同程度（半分） | **移行の主目的が消える**。`dump-uia.ps1` 拡張路線へ切り替え |

| P3 が不安定（起動ごとにセレクタが変わる） | 移行するが、**name 部分一致のみに限定**し、「GUI 文言を変えるとテストが壊れる」を docs に明記して受け入れる |
| P6 が (a)(b) とも不成立 | **トレイ操作だけ残す混成**にする。設定・ログの中身は winapp、トレイは素 UIA（`dump-uia.ps1` の `Open-TrayMenuItem`） |

## 4. Phase 2 — 1 本だけ移植して「不安定さが消えたか」に答える

`01-settings-window` を **winapp スクリプト 1 本**に書き換え、**連続 5 回**流す。

- 判定基準: **5/5 一致**。1 回でも割れたら次へ進まず、§1 の 3 層のどこで割れたかを特定する
- 併せて 1 回あたりの所要時間を記録する（現行 12〜14 分に対して何分か）
- 比較対象として、terminator 版 01 の履歴を併記する（押下を含めていた頃は 3 回連続 FAIL、押下を外した後は**未検証**のまま中断）

**この 5 回が本検証の答えである。** ここまでは「できるか」、ここからが「安定するか」。

移植するとき、Phase 1 の測定から**そのまま持ち込む決まりが 4 つ**ある。

1. **トレイアイコンの昇格をやめる。** winapp は可視トレイ（`Shell_TrayWnd`）を押せない一方、オーバーフロー経由は 10/10 で通る。`promote-tray-icon.ps1` は terminator 版のための道具であり、winapp 版のシナリオでは**不要どころか邪魔**になる（昇格するとオーバーフローから消える）。ランナーの `NeedsTray` は経路ごとに分ける
2. **chevron を開く前に「開いていたら閉じる」。** `invoke` はトグルなので、前の実行の状態を持ち越すと 1 回おきに失敗する
3. **セレクターは一意な名前かスラッグで。** 名前が 2 つの要素に一致すると `wait-for` は「見つからない」と言う。スラッグは実行ごとに変わるので、`search --json` で取り直してから使う
4. **読むのは `--json` だけ。** テキスト出力は PowerShell 5.1 で文字化けする

## 6. Phase 0 — 足場（**winapp を採らなくても先にやる**）

windows-utility 側が [04](../../../../../GitLab/windows-utility/docs/projects/20260726_winappCLI比較検証/04_VM運用方針とセットアップ更新.md) で「1 プロジェクト 1 VM ／ 接続情報は利用プロジェクトに置き `-ConfigPath` で渡す」を決めた。**これは我々が抱えていたバグの根治でもある**ので、検証の前に取り込む。

いま `run-vm-ui-test.ps1` は、共有の `.secrets\test-vm.json` を実行中だけ**書き換えて `finally` で戻す**という細工をしている。理由は入口スクリプトが対象 VM を引数で受け取らなかったからで、実際に事故も起きた（実行中に既定を切り替えられ、最後のシナリオが別 VM へ飛んだ）。そして**強制終了すると `finally` が走らず、他プロジェクトの設定を書き換えたまま残る**（前回まさにこれを手で戻した）。

`-ConfigPath` が入ったので、この細工は丸ごと消せる。

| # | 作業 | 効果 | 状態 |
|---|---|---|---|
| 1 | `winremap/.secrets/test-vm.json` を作り `winremap-test` を指す。`.gitignore` に `/.secrets/` を追加 | 接続情報を自リポジトリで持つ | **完了** 2026-07-27 |
| 2 | `run-vm-ui-test.ps1` を `-ConfigPath` 経由に変更し、`Set-DefaultVmConfig` / `Restore-DefaultVmConfig` を削除 | 共有ファイルを一切触らなくなる。強制終了しても他プロジェクトに影響しない | **完了** 2026-07-27 |
| 3 | `winremap-test` の `ready` スナップショットと `winapp --version` を確認 | 検証の土台確認 | **完了** winapp 0.5.0 |
| 4 | `docs/05_ui-test-automation.md` の VM 名を `win11-test` から `winremap-test` へ | 命名規則（[04 §3](../../../../../GitLab/windows-utility/docs/projects/20260726_winappCLI比較検証/04_VM運用方針とセットアップ更新.md)）に合わせる | **完了** 2026-07-27 |

- `Reset-Guest` は自前の revert＋起動＋固定待ちをやめ、`run-in-vm-vmware.ps1 -Restore` に委譲した。**準備完了の判定は「Tools が応答した」ではなく「`-interactive` 実行が通った」**で、基盤側は実測 2〜3 分かかると記録している。旧実装の「Tools 応答＋`Start-Sleep 15`」はこの条件を満たしておらず、§1 で「操作層」に分類した不安定さの一因だった可能性がある
- 残骸掃除の `Clear-StaleRun` は削除。ゴールデンを電源オフ＋`-AppProcessNames` で取り直すことが根治であり、二重に持つと片方だけ直す事故になる
