## 0. このバージョンの性格

v0.5.0 は**新機能を足すより、v0.4 で先送りしたものを閉じるバージョン**である。抱えているのは 3 つで、いずれも「次も送れる」ものではない。

| # | 持ち越し | 送った経緯 |
|---|---|---|
| 1 | **ログへの文字コード・制御コード表示** | v0.4 のスコープに入れたまま未着手（オーナー決定 2026-07-26 で本バージョンへ） |
| 2 | **UI テストの決定論化（AccessKit）** | v0.4 の自動化はスクリーンショットを AI に読ませる方式で、判定がぶれる（オーナー決定 2026-07-26 で本バージョンへ） |
| 3 | **v0.1〜v0.3 の受け入れ回帰** | v0.2.0 と v0.4.0 の **2 リリース続けて未実施**。v0.4 の記録欄が「v0.5 の計画で明示的に扱うこと」としている |

3 は 2 に依存する（手で全項目を通すコストが理由で 2 回送られてきたので、自動化で減らさない限り 3 回目も同じことになる）。したがって**順序は 2 → 3**で、1 は独立に進められる。

## 2. Phase A — UI テストの決定論化（AccessKit）

### 2.1 背景

v0.4 の UI テストは、設定ウィンドウとログウィンドウの中身を**スクリーンショットに撮って AI に読ませて**いる（[05_ui-test-automation.md](../05_ui-test-automation.md) §4）。UIA ツリーにはタイトルバーしか出ないためで、この方式には次の弱点がある。

- 判定が LLM の読み取りに依存し、同じ画面で結果がぶれうる
- 「要素名が読めたか」までしか見られず、`role:Button|name:Reload` を押すといった**操作**ができない
- プロンプトを直すたびに複数回実行して同じ判定になることを確かめる必要がある（同 §4）

原因は**描画方式ではない**（当初「OpenGL だから」と書いていたのは誤り。オーナー指摘 2026-07-26）。egui は [AccessKit](https://accesskit.dev/) を話せる。出ていないのは次の 2 点による。

1. `Cargo.toml` が eframe を `default-features = false` で取っており、**既定機能である `accesskit` が外れている**（`accesskit_winit` → `accesskit_windows` の UIA プロバイダーが binary に入らない）
2. 有効にしても足りない。**eframe 0.35 は AccessKit アダプターを ROOT ビューポートにしか作らない**（`eframe-0.35.0/src/native/glow_integration.rs:275-286`、`ViewportId::ROOT` 決め打ち）。WinRemap の root は不可視 1×1 のホストで、設定・ログは遅延子ビューポートである（[ADR 0037](../v0.2/decisions/0037-gui-invisible-host-viewport.md)）

### 2.2 タスク

1. **調査（時間を区切る）** — feature を有効にしたビルドで、子ウィンドウに本当にツリーが出ないことを実機で確認する。§2.1-2 の読みが外れていれば以降は不要になるため、**最初に潰す**
2. **ADR 0055** — どの道を採るか。少なくとも次を比較する:
   - eframe に子ビューポート対応の AccessKit 初期化を入れて **upstream へ PR**（本筋。マージまで待てないなら patch/fork を併用）
   - `[patch.crates-io]` でフォークを一時的に指す（ADR に「upstream がマージされたら外す」条件を書く）
   - **root を実ウィンドウにする**（ADR 0035/0037 を覆すことになる。ログ窓を閉じたら設定窓も死ぬ・起動時にちらつく という当時の問題が戻るため、最後の手段）
   - 依存追加（`accesskit_winit`／`accesskit_windows`）のライセンス確認（MIT/Apache-2.0）と、配布物のサイズ・起動時間への影響
3. **実装** — 採った道に沿って有効化する。**アクセシビリティは利用者にとっても利益**（スクリーンリーダーで設定ウィンドウが読める）なので、テスト専用の feature には**しない**
4. **シナリオの書き換え** — `tests/ui/scenarios/01`〜`04` を、スクリーンショット読み取りからセレクタ（`role:X|name:Y`）ベースへ移す。**05（リマップ E2E）はキー送出が本質なので現状のまま**
5. 不変条件の確認 — AccessKit のツリー構築は GUI スレッドで行われ、フックにもメッセージループにも触れない（不変条件 2）。ツリーに**キー入力の内容を載せない**（不変条件 6）

### 2.3 完了条件

- 設定ウィンドウとログウィンドウの主要な要素が UIA から見え、Terminator のセレクタで押せる
- シナリオ 01〜04 がスクリーンショット読み取りを使わずに PASS する
- 同じシナリオを**2 回以上実行して判定が一致**する（v0.4 §4 の規律）
- リマップが停止・遅延しない（不変条件 1・2）

### 2.4 やらないこと

- **完全なアクセシビリティ対応の保証**。ここで作るのは「テストが読めて押せる」水準であり、スクリーンリーダーでの利用体験の作り込みは範囲外（改善はするが完了条件にはしない）

### 2.5 実施記録 — **完了（2026-07-28）**

| §2.3 の完了条件 | 結果 |
|---|---|
| 設定・ログウィンドウの主要要素が UIA から見え、セレクタで押せる | **達成**。設定ウィンドウ 43 要素（キーマップ選択で 59、編集モードで 72）、ログウィンドウ 7 要素（`Clear` 後 3）。`Edit`・`Clear` は `InvokePattern` で押せる（[ADR 0055](decisions/0055-accesskit-for-child-viewports.md)） |
| シナリオ 01〜04 がスクリーンショット読み取りを使わずに PASS | **達成**。4 本とも「スクリーンショットを撮るな・画像から読むな」を明記したプロンプトで PASS |
| 同じシナリオを 2 回以上実行して判定が一致 | **達成**。`00-uia-actuation` を含む 6 件を 2 通しし、**全件で両回一致**（[05_ui-test-automation.md §4](../05_ui-test-automation.md) に所要時間つきで記録） |
| リマップが停止・遅延しない（不変条件 1・2） | **達成**。05（`C-h` → `x`、置換パネルが開かない）が両回 PASS。起動時間は accesskit の有無で**有意差なし**（暖機後 25〜34 ms 対 24〜31 ms、ADR 0055 に実測） |

計画から変わった点が 1 つある。**押下の検証はエージェントから外し、AI を挟まない `tests/ui/guest/dump-uia.ps1`（ランナーの `00-uia-actuation`）へ移した。** terminator の `click_element` は実体が座標クリックで、同じボタンが `Edit` 2/6・`Clear` 2/4 しか当たらないのに対し、素の UIA クライアントは 4/4 だった。**半分しか当たらない検査は退行と不調を区別できない**ため、エージェントは読み、ハーネスが押す形にした。§2.2-4 の「セレクタベースへ移す」は読み取り側で満たしている。

テスト環境も載せ替えた。共通基盤の既定 VM を実行中だけ書き換える運用をやめ、専用 VM `winremap-test` と本リポジトリの `.secrets/test-vm.json` を `-ConfigPath` で明示する方式にした（[05_ui-test-automation.md §2](../05_ui-test-automation.md)）。

Terminator MCP を winapp CLI へ置き換えるかは[検証計画](notes/20260727_winapp-cli-migration.md)の Phase 1 ゲート（**オーナー承認待ち**）で決める。**Phase A の完了はその判断を待たない**（上の 2 通しがその比較基準線になる）。

## 3. Phase B — v0.1〜v0.3 回帰の自動化と実施

### 3.1 背景

[v0.4 受け入れチェックリスト](../v0.4/03_acceptance-checklist.md) の記録欄のとおり、v0.1〜v0.3 の回帰確認は **v0.2.0 と v0.4.0 の 2 回続けて未実施**である。理由はどちらも「手で全項目を通すコストに見合わないと判断した」であり、リリースのたびに同じ判断が繰り返される構造になっている。

このバージョンで**構造を変える**。自動化で通せる範囲を増やし、「手で通すのはこれだけ」と言い切れる状態にする。

### 3.2 タスク

1. Phase A の後に、v0.1〜v0.3 チェックリストの各項目を **①自動化する ②手動に残す ③陳腐化したので落とす** の 3 つに仕分ける。②③には理由を書く
2. ①をシナリオ化する。とくに次は自動化の価値が高い:
   - v0.2 A-10〜A-20（ログウィンドウの開閉・追従・コピー・多重オープン）
   - v0.2 B0-1〜B0-16（ビューポート構成の回帰。`EventLoop can't be recreated` の再発検知）
   - v0.2 B1-1〜B1-40（設定ウィンドウの表示。Phase A のセレクタが効けば大半が機械判定できる）
   - v0.3 M-1〜M-7（設定の検証エラー。GUI を使わず `parse_str` の単体テストへ落とせるものが混じっている可能性がある）
3. **手動に残る項目を 1 枚にまとめる**（`docs/v0.5/03_acceptance-checklist.md` に「毎リリース手で通す最小集合」として）。体感確認（連続タイプの停止・遅延）、マルチモニター、管理者権限ウィンドウ、IME 実機確認など、原理的に自動化できないものが中心になるはず
4. **実施して記録する。** v0.5.0 のリリース準備で、v0.1〜v0.3 の全項目を（自動＋手動で）1 度通し切る

### 3.3 完了条件

- v0.1〜v0.3 の各項目が「自動／手動／廃止」に仕分けされ、理由とともに記録されている
- 手動に残る項目が**1 枚に収まり**、毎リリース現実的に通せる分量になっている
- **v0.1〜v0.3 の全項目を 1 度通し切った記録がある**（これが本フェーズの本題）

### 3.4 実施記録（2026-07-28）

| 完了条件 | 状態 |
|---|---|
| 各項目が 自動／手動／廃止 に仕分けされている | **達成**。[v0.5 受け入れチェックリスト §3](03_acceptance-checklist.md) に v0.1〜v0.3 の全項目を分類し、手動・廃止には理由を書いた |
| 手動に残る項目が 1 枚に収まっている | **達成**。**H-1〜H-9 の 9 項目**（所要 30〜40 分）。約 200 項目のうち体感・見た目・実機依存・外部アプリだけが残った |
| 全項目を 1 度通し切った記録がある | **自動分は達成、手動分はオーナー実施待ち**。`cargo test` 94 件と UI 自動テスト 8 件（`00-uia-actuation`・`00-cli-smoke`・`00-regression`・シナリオ 01〜05）が**すべて緑**。H-1〜H-9 は人にしかできない項目なので、v0.5.0 のリリース準備で通して同チェックリスト §6 に記入する |

自動側に**ハーネス検査を 2 本追加**した（エージェントを挟まない）。`00-cli-smoke` は起動・CLI・無音起動時のエラーダイアログ（8 チェック）、`00-regression` はウィンドウのライフサイクル・操作ログ・複数キーマップ表示・`--lang ja`（14 チェック）。トレイメニューの項目選択は**winapp CLI のコマンド ID**（1001〜1005）で行う — 頭文字キー方式は表示言語に依存し、`--lang ja` で成立しないことが実測で分かったためである。

**自動化が退行以外のものを見つけた。** v0.2 B0-3・B0-15 の「テキストエディタで開く」ボタンは v0.4 の設定ウィンドウ内編集に置き換わって**すでに存在しない**。仕分けでは廃止に落とした。手で通していた頃は「見当たらないので飛ばす」で消えていた種類の差分である。

## 4. Phase C — ログ表示への入力文字コード・制御文字コード表示

v0.4 Phase B の持ち越し。**背景・不変条件 6 との整合・タスク・完了条件は [v0.4 開発計画 §3](../v0.4/01_development-plan.md) をそのまま引き継ぐ**（書き換えていない）。要点だけ再掲する。

- 本プロジェクトの発端は **Ctrl+H（`0x08` BS）と Backspace（端末上で `0x7f` DEL）の食い違い**であり、ログがキー名までしか出さないためその違いを画面上で確かめられない
- **セキュリティ上最も注意を要するフェーズ**である。着手前に **ADR で不変条件 6（キーロガー化の禁止）の境界を固定する**: 制御コードのみか印字可能文字も出すか、既定 OFF とディスク非保存の維持、算出をフックコールバックではなく `drain_debug_log` で行うこと
- ADR 番号は Phase A の 0055 の次（**0056** 以降）

あわせて本フェーズで片付ける小さな未決が 1 件ある。

- **ログウィンドウに「どの設定ファイルを読み込んだか」が出ない**（[05_ui-test-automation.md](../05_ui-test-automation.md) §4 の未決）。起動時の `N keymap(s) loaded from <path>` は `src/main.rs` からコンソールにしか流れず、一方でトレイからの再読み込みは `reload_ok` をログウィンドウに出す。この非対称を解消するか否かをオーナー判断で決め、決めたとおりにする

### 4.1 先行して実施 — ログの読みやすさ（2026-07-28）

**計画外**。オーナーから「今のログが読めない」との指摘があり、Phase C（何を表示するか）に入る前に**表示の構造**を作り直した。詳細と理由は [ADR 0057](decisions/0057-log-view-modes.md)。

- ヘッダーに **「全イベント」チェックボックス**を追加。既定はキー 1 つにつき 1 行の**判定**、チェックすると**物理イベント・送出イベントを含む全部**
- 各行を **時刻・種別タグ・本文**の 3 列に。`[debug]` を `[入力]`・`[判定]`・`[注入]`・`[操作]` に置き換えた
- ログウィンドウの初期サイズを 760×480 → **900×720**
- ハーネス検査 `00-log-view` を追加（[05_ui-test-automation.md](../05_ui-test-automation.md) §ハーネス検査）

**ADR 0056 の守備範囲は変えていない。** 0057 は「どう並べるか」だけを決めており、「何を出してよいか」（不変条件 6 の境界）は Phase C で改めて決める。

### 4.2 続き — 読めないところを潰す（2026-07-29）

同じく**計画外**。0057 の後にオーナーから 5 点の指摘があり、対応した。詳細と理由は [ADR 0058](decisions/0058-log-readability.md)。

- **キー名**: `0xBF`・`0x61` のような裸の VK をやめ、`Num1 (0x61)`・`/ (0xBF)` と出す。設定に書ける名前（`vk_display_name`）とログ用の名前（新設 `src/keyname.rs`）を分けた。配列依存の文字は `MapVirtualKeyW` で実際のキーボードに問い合わせる — **不変条件 3 の unsafe 許可リストに 1 モジュール追加**（AGENTS.md 更新済み）
- **コンソール出力**: `--debug` を付けたときだけ出す。内容はログウィンドウと同じ 1 行（時刻・タグ付き）。`notify::console_line` を呼ぶのは log モジュールだけになった。**`--debug` なしでは端末に何も出ない**
- **前面アプリの行**: `[debug]` の無時刻 3 行から、簡易モードに出る 1 行（`application` の値＋適用キーマップ）とフルパスの詳細行へ
- **ログウィンドウ自身の操作**を `[操作]` 行として記録（追従・全イベント・消去・コピー。コピーは行数も）
- チェックボックス間に 12px の間隔

`00-log-view` は 15 件 → **23 件**になった。あわせて、**ログウィンドウを開いている間、自分で切り替えた先のアプリが前面アプリ行に出ないことを 2 回の実行で観測した**（[docs/05](../05_ui-test-automation.md) の落とし穴節・ADR 0058 末尾）。ログ機能そのものは動いており、`05-remap-notepad`（アプリ別リマップ）も通っているため v0.5 は止めないが、**未解決の観測として残す**。

## 5. Phase D — README（en/ja）・ヘルプサイトへの反映

Phase C の結論（ログの文字コード表示）を利用者向けの言葉で書く。**Phase A・B は開発者向けなので対象外**。

- どこに出るか、発端の Ctrl+H／Backspace 問題の見分け方、**ディスクに保存されないこと**
- 英語が正、`README.ja.md` を追随させる（AGENTS.md ワークフロー 7）

## 7. フェーズ順序と依存関係

```
Phase A（UI テスト決定論化） ──▶ Phase B（v0.1〜v0.3 回帰） ──┐
                                                             ├──▶ Phase E（リリース）
Phase C（ログの文字コード表示） ──▶ Phase D（README/サイト） ──┘
```

- **Phase A → B は必須の順序**。B の目的は「手で通す量を減らす」ことなので、A の成果が無いと 3 回目の先送りになる
- **Phase C は A・B と独立**。ADR さえ通ればいつ着手してもよい
- **Phase A が想定以上に重い場合**（upstream 待ちなど）は、A を切り離して C・D だけで v0.5.0 を出し、A・B を v0.6 に送る判断もありうる。その場合も **B だけは手作業で実施する**こと（3 リリース連続の未実施は許容しない）
