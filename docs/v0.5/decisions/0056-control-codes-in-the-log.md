# ADR 0056: ログに制御コードを表示する（印字可能文字は出さない）

- 作成日: 2026-07-29
- 作成: Claude Code（AI モデル: claude-opus-5[1m]）／レビュー・承認: オーナー（粒度の決定 2026-07-29）
- ステータス: 採用
- 関連: [v0.4 開発計画 §3](../../v0.4/01_development-plan.md)（本フェーズの元定義）、[ADR 0016](../../v0.1/decisions/0016-debug-key-logging.md)（デバッグログの出力経路）、[ADR 0029](../../v0.2/decisions/0029-attach-console-and-tray-log-window.md)（既定 OFF・ディスク非保存）、[ADR 0057](0057-log-view-modes.md)・[ADR 0058](0058-log-readability.md)（表示の構造とキー名）

## 背景

本プロジェクトの発端は **Ctrl+H と Backspace の食い違い**である（ブリーフ §1.1）。ログはキー名までしか出さないため、`C-h` と `Back` が並んでいても**それぞれが何を送るのか**は画面から読めなかった。

v0.4 Phase B として計画され、v0.5 Phase C に持ち越された。**着手前に不変条件 6（キーロガー化の禁止）の境界を ADR で固定する**ことが、v0.4 の時点から条件になっていた。

## 決定

### 1. 粒度 — 制御コードのみ（オーナー決定 2026-07-29）

出すのは **C0 制御コードだけ**である。印字可能文字は出さない。

| 入力 | ログ | 理由 |
| --- | --- | --- |
| `C-h` | `C-h (BS 0x08)` | 制御コードは**そのキーの性質**。文書の中身とは無関係 |
| `Back` | `Back (BS 0x08)` | 同上 |
| `a` | `a` | 印字可能文字。`a → 0x61` を毎行出すのは**打った文字列の記録**に近づく |
| `S-a` | `S-a` | 同上 |
| `A-h` | `A-h` | Alt・Win はコマンドであって文字ではない |

**この線引きが不変条件 6 の境界である。** キー名は従来どおり出す。制御コードはキー名と同粒度の情報 — `C-h` が BS であることは、そのキーの押下から一意に決まり、利用者が何を書いたかを含まない。一方、印字可能文字を逐一出せば、ログを読める者は**打鍵内容を復元できる**。そこが境界で、こちら側には来ない。

既定 OFF（ログウィンドウを開いている間だけ有効）とディスク非保存は変わらない。**粒度が上がっただけで、保存経路は 1 つも増えていない。**

### 2. 算出方法 — `ToUnicode` ではなく純粋なテーブル

| | 採用 | 却下 |
| --- | --- | --- |
| 方法 | VK と修飾から引くテーブル（`src/keymap/control.rs`） | `ToUnicode` / `ToUnicodeEx` |
| 場所 | `winremap` ライブラリ（OS 非依存） | バイナリ側 |
| 検証 | **ヘッドレス CI で単体テスト**（6 ケース群） | Windows デスクトップでしか動かない |

`ToUnicode` を却下した理由は 3 つある。

1. **副作用**: 呼び出しスレッドのデッドキー状態を書き換える。次の打鍵を壊しうる API を、ログ 1 行のために毎イベント呼ぶ価値はない
2. **テスト可能性**: 純粋関数なら `cargo test` で境界（`C-h`・`Back`・`Enter`・印字可能キー・`A-h`）を固定できる。ブリーフ §9 が「OS 非依存の中核はヘッドレスでテストする」と定めている
3. **必要がない**: 対象の集合では答えが**配列非依存**である。Ctrl+文字はどの配列でも文字の下位 5 ビットになる

**配列依存の制御コード（Ctrl+`[` = ESC など）は範囲外**とした。これらの OEM キーはそもそも設定記法で名前を持たない（`keymap/parse.rs` の TODO）。記号キー対応を v0.6 で扱うとき、同じ ADR で一緒に決めればよい。

対象は次のとおり。

- `Ctrl` + `a`〜`z` → `0x01`〜`0x1A`（Shift は結果を変えないので参照しない）
- `Back` → `0x08` BS / `C-Back` → `0x7F` DEL
- `Tab` → `0x09` HT
- `Enter` → `0x0D` CR / `C-Enter` → `0x0A` LF
- `Esc` → `0x1B` ESC

算出は `drain_debug_log`（メッセージループ）から呼ばれる整形経路で行う。**フックコールバックには手を入れていない**（不変条件 2）。

### 3. 表示形式 — `名前 (略号 0xXX)`

```
07:27:15.377 [入力]     h ↓
             [判定]     C-h (BS 0x08) → Back (BS 0x08) に置換
             [注入]       Back (BS 0x08) ↓（置換）
```

略号が先に来るのは、読むのはそちらだからである（`0x08` だけでは大半の人に何も伝えない）。数字は不具合報告に貼るためにある。**制御コードを持たないキーには何も付かない**ので、普通のタイピングでログが数字だらけになることはない。

`Num1 (0x61)`（ADR 0058 の VK 表記）と形が似ている点は自覚している。区別は略号の有無で付く — 制御コードには必ず `BS`・`CR` のような名前が入り、VK の 16 進にはそれが無い。

### 4. 端末の慣習（`0x7F`）は出さない — 発端の問題をどう読むか

v0.4 の完了条件は「**Ctrl+H の `0x08` と Backspace の `0x7f` の違いがログ上で判別できる**」と書かれていた。**これはそのままでは実装できない。**

Windows のレベルでは **Backspace キーも `0x08`（BS）**である。`0x7F`（DEL）を送るのは**端末エミュレーターの慣習**であって、Backspace キーの性質ではない。WinRemap は前面アプリが端末かどうかを知らないし、その端末がどの慣習を採るかも知らない。**知らないことを断定して出すのは、ログとして最も避けるべきこと**である（ADR 0058 で「配列依存の文字を静的表にしない」と決めたのと同じ理由）。

代わりに、発端の問題はこう読める形にした。

```
[判定]  C-h (BS 0x08) → Back (BS 0x08) に置換
```

**両側が同じ BS 0x08 である** — つまり WinRemap は「Backspace キーが送るものと同じもの」を届けている。ここから先（端末が Backspace キーを DEL に読み替える慣習）は**アプリ側の話**なので、README とヘルプサイト（Phase D）で説明する。ログの仕事は「WinRemap が何をしたか」を正確に言うことで、そこで止める。

**この 1 点は v0.4 §3.4 の完了条件の文面から意図的に外れている。** オーナーへ報告済み。

## 却下した代替案

- **印字可能文字も出す**: オーナー決定で不採用。診断力は上がるが、打鍵内容の記録に近づく。既定 OFF でも性格が変わる
- **`ToUnicode` で実際の文字を引く**: 上記のとおり副作用とテスト不能性
- **専用の `[コード]` 行を足す**: 簡易モードから隠れてしまう。発端の問題は**探さなくても目に入る**必要がある
- **`U+0008` 表記**: VK の 16 進と混ざらない利点はあるが、発端の問題は `0x08` / `0x7f` という語で語られてきた（ブリーフ §1.1）。読み手の語彙に合わせた

## 不変条件への影響

- **不変条件 2**: 変更なし。算出はメッセージループ側の整形経路のみ。フックは従来どおり VK と修飾をリングに積むだけ
- **不変条件 6**: **本 ADR が境界そのもの**。制御コードはキー名と同粒度、印字可能文字は出さない、既定 OFF とディスク非保存は維持。テスト `printable_keys_carry_nothing` がこの線を固定している
- **不変条件 3**: 変更なし。`control.rs` はライブラリ側の純粋なコードで `unsafe` を含まない

## 確認方法

- 単体テスト 6 件群（`src/keymap/control.rs`）: 発端の対、Ctrl+文字の全域、名前付きキー、Ctrl で変わる 2 つ、印字可能キーが何も返さないこと、Alt/Win が何も返さないこと
- `keyname` 側 3 件: `C-h (BS 0x08)` と `Back (BS 0x08)` の描画、普通のキーに何も付かないこと
- ハーネス検査 `00-log-view` 3 件: 判定行に両側の `BS 0x08` が出ること、`a` に `0x61` が付かないこと、ログウィンドウが読み込んだ設定ファイルを名乗ること
