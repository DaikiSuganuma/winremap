# ADR 0055: 子ビューポートに AccessKit を付ける方式

- ステータス: **承認**（オーナー承認 2026-07-26）。決定 4 の実測も同日完了し、**パッチが効くことを確認済み**（[調査記録](../notes/20260726_accesskit-child-viewport.md)）
- 日付: 2026-07-26
- 作成: Claude Code（AI モデル: claude-opus-5）
- 参照: [AccessKit](https://accesskit.dev/)、[eframe 0.35.0 `glow_integration.rs`](https://docs.rs/eframe/0.35.0/src/eframe/native/glow_integration.rs.html)、[ADR 0037（不可視ホスト＋子ビューポート）](../../v0.2/decisions/0037-gui-invisible-host-viewport.md)、[ADR 0035（単一 EventLoop）](../../v0.2/decisions/0035-single-event-loop.md)、[調査記録](../notes/20260726_accesskit-child-viewport.md)、[v0.5 開発計画 §2](../01_development-plan.md)

## 文脈

v0.4 の UI テストは設定ウィンドウとログウィンドウを**スクリーンショットに撮って AI に読ませて**判定している。判定がぶれ、要素を**押す**ことができず、プロンプトを変えるたびに複数回実行して一致を確かめる必要がある。UIA から読めれば `role:Button|name:Reload` で操作でき、判定が決定論的になる。

[調査記録](../notes/20260726_accesskit-child-viewport.md)のとおり、原因は次の 2 段になっている。

1. `Cargo.toml` が eframe を `default-features = false` で取っており、既定機能の `accesskit` が外れていた（**本 ADR の作業ブランチで有効化済み**。これだけでは足りない）
2. **eframe 0.35 は AccessKit アダプターを `ViewportId::ROOT` にしか作らない。** WinRemap の root は不可視 1×1 のホストで、設定・ログは遅延子ビューポートである（ADR 0037）

実測は明快で、同じ feature・同じウィジェットで、ルートに描けば UIA に 9 要素（ボタン名まで）出るのに対し、遅延子ビューポートでは **0 要素**である。

なお egui の最新リリースは 0.35.0 で、本プロジェクトはすでにそれを使っている。**待っていれば直るものではない。**

## 決定（案）

1. **eframe の子ビューポート生成経路に AccessKit の初期化を足し、`emilk/egui` へ upstream PR を出す。** 位置は `glow_integration.rs` の `viewport.egui_winit.get_or_insert_with(...)`。イベントループのプロキシをその場まで引き回す必要がある
2. **マージを待つ間は `[patch.crates-io]` でフォークを指す。** ADR に外す条件を書く: **upstream にマージされ、それを含む eframe が公開されたら patch を外す**。フォークは `DaikiSuganuma/egui` に置き、対象ブランチとコミットを本 ADR に追記する
3. **`accesskit` feature は本番ビルドでも有効にする。** テスト専用の feature にはしない
4. 実装の前に、`[patch.crates-io]` を使ったローカル改変版で**子ビューポートの子孫が UIA に出ることを実測**する。ここで出なければ本 ADR は差し戻し、代替案を検討する
   - **実施済み（2026-07-26）**: 子孫 10 個が見え、`InvokePattern` 経由でボタンを押すと実際にクリックが届いた。**読めるだけでなく押せる**
   - 実測して初めて分かった制約が 1 つある。**アダプターはウィンドウを最初に表示する前に作らなければならない**（`accesskit_winit` が panic する）。ルートは白いちらつき対策で元から不可視で作られるため踏まないが、子ビューポートは可視で作られるので踏む。**一旦隠して作り、アダプターを付けてから表示する**必要がある — 上流 PR にもこの扱いが要る

## 理由

- **決定 3（本番でも有効）**: アクセシビリティは利用者の利益であり、テストのためだけに付けるものではない。スクリーンリーダー利用者が設定ウィンドウを読めるようになる。テスト専用 feature にすると「出荷物では読めない」状態を意図的に作ることになり、[ADR 0053](../../v0.4/decisions/0053-test-inject-mode.md) で feature を切ったときの理由（**入力を変換する挙動**を出荷物に入れない）とは性質が違う。ここで増えるのは読み取り専用の情報提供であり、キー処理には触れない
- **決定 1（upstream が本筋）**: この欠落は WinRemap 固有ではなく、遅延ビューポートを使う全アプリに当てはまる。フォークを持ち続けるより上流に返すほうが、保守の総量が小さい
- **決定 2（patch は暫定）**: upstream のマージ時期は制御できない。v0.5 を人質に取らないために暫定手段を持つが、**外す条件を書いておかないと恒久化する**
- **決定 4（先に実測）**: コードの読みだけで「直るはず」と判断して ADR を承認すると、実装フェーズで覆るおそれがある。調査で feature だけでは足りないと分かったのと同じ理由で、次の段も実測で確かめる

## 却下した代替案

- **root を実ウィンドウにする（ADR 0037 を覆す）**: 一番簡単に見えるが、ADR 0035/0037 が解いた問題が戻る — winit の `EventLoop` はプロセスに 1 つしか作れず、ログウィンドウを閉じたら設定ウィンドウも道連れになり、起動時にウィンドウがちらつく。**テストのためにアーキテクチャを壊す**取引であり、割に合わない
- **設定・ログウィンドウを即時ビューポート（immediate viewport）に変える**: 即時ビューポートも同じ経路を通らないため解決にならず、加えて描画がホストのフレームに同期する
- **UIA を諦め、スクリーンショット判定のまま精度を上げる**（プロンプトの作り込み、OCR の併用等）: 判定の揺れは減らせても**操作**はできないままで、Phase B（v0.1〜v0.3 の回帰自動化）で必要な「押して確かめる」項目に届かない
- **Win32 側で自前の UIA プロバイダーを実装する**: `unsafe` と COM の実装が増える。AGENTS.md 不変条件 3（`unsafe` は Win32 ラッパーに閉じる）に反しはしないが、AccessKit が既に解いている問題を再実装することになる
- **eframe をフォークして恒久的に持つ**: 上流に返さないと、egui の版を上げるたびに追従コストがかかる。決定 2 の暫定運用と外す条件で足りる

## 不変条件との整合

- **不変条件 2（フックの遅延を増やさない）**: AccessKit のツリー構築は GUI スレッドのフレーム内で行われる。フックのコールバックにもメッセージループにも触れない
- **不変条件 6（キーロガー化の禁止）**: アクセシビリティツリーに**キー入力の内容を載せない**。載るのは画面に出ているラベル・ボタン名であり、ログウィンドウの内容は既に画面に出ているものと同じ粒度に留める
- 依存追加（`accesskit_winit` / `accesskit_windows`）はいずれも MIT / Apache-2.0
- **バイナリサイズ**: feature 有効化で `9,503,232` → `9,973,760` バイト（**+470 KB・+5.0%**、release ビルド実測 2026-07-26）。常駐アプリとして許容範囲。起動時間への影響は実装時に測る（AccessKit の Windows 実装は UIA クライアントが来るまでツリーを作らない遅延初期化なので、通常起動では効かないはずである）
