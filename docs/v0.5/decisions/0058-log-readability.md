# ADR 0058: ログを「読める」ものにする — キー名・タグ・コンソール出力の一本化

- 作成日: 2026-07-29
- 作成: Claude Code（AI モデル: claude-opus-5[1m]）／レビュー・承認: オーナー
- ステータス: 採用
- 関連: [ADR 0057](0057-log-view-modes.md)（2 つの表示モード）、[ADR 0016](../../v0.1/decisions/0016-debug-key-logging.md)（デバッグログの出力経路）、[ADR 0029](../../v0.2/decisions/0029-attach-console-and-tray-log-window.md)（親コンソールへの接続）、[ADR 0031](../../v0.2/decisions/0031-notify-module-unsafe-allowlist.md)（unsafe 許可リストの前例）

## 背景

ADR 0057 で列と 2 つのモードを入れた後、オーナーから 5 点の指摘があった（2026-07-29）。いずれも「ログが読めない」という 1 つの問題の別々の面である。

1. ヘッダーの 2 つのチェックボックスが隙間なく並び、1 つの部品に見える
2. コンソール出力とウィンドウ表示の内容が違う。しかも `--debug` を付けていなくても端末には出る
3. 画面（前面アプリ）を切り替えたときの行だけ `[debug]` のまま・時刻なしで、直前のキー入力の続きに見える
4. `0xBF` や `0x61` と出て、何を押したのか分からない
5. ログウィンドウ自身のクリック（追従・全イベント・消去・コピー）が記録されない

## 決定

### 1. キー名 — 「設定に書ける名前」と「押したキーの名前」を分ける

`vk_display_name` は**設定ファイルの語彙**を答える関数である。設定記法がまだ名前を持たない OEM 記号・テンキー・IME キーには答えがなく、16 進にフォールバックしていた。ログが必要としているのは別の問いで、「いま押されたのはどのキーか」である。

新設した `src/keyname.rs` が後者を 3 段で答える。

| 段 | 判定 | 例 |
| --- | --- | --- |
| 1 | 設定名がある | `a` / `Down` / `LCtrl` |
| 2 | 配列に依存しない固定名 | `Num1 (0x61)` / `NumLock (0x90)` / `Convert (0x1C)` |
| 3 | このキーボードが出す文字（`MapVirtualKeyW`） | `@ (0xC0)` / `/ (0xBF)` |
| 4 | いずれでもない | `0x07` |

2・3 で **16 進を括弧で残す**のは 2 つの理由による。不具合報告に必要であること、そして「まだ設定に書けないキーだ」という正直な合図になること。裸の `/` は `"/" = ...` と書けるように見えるが、パーサーは受け付けない（OEM キーは `keymap/parse.rs` の TODO のまま保留）。

3 段目に静的テーブルを使わなかった理由: `0xC0` は JP 配列では `@`、US 配列では `` ` `` である。テーブルにすると読者の半数に対して嘘をつく。実際の配列を知っているのは Windows だけなので、Windows に訊く。

### 2. コンソール出力は `--debug` のときだけ、内容はウィンドウと同じ

従来は「端末に繋がっていれば出す」だった。つまりシェルから起動しただけで実況が流れ、しかも各呼び出し側が自前でプレフィックスを組み立てていたため、ウィンドウとは別の文字列が出ていた。

- **いつ出すか**: `--debug` を付けたときだけ。端末があるかどうかは「出せるか」の判定にすぎない
- **何を出すか**: ウィンドウの各行を、クリップボードと同じ `as_text` で 1 行にしたもの（`HH:MM:SS.mmm [判定] C-n → Down に置換`）

実装上は `gui::log::record` 1 か所がスタンプ・コンソール・バッファの全部を行う。`notify::console_line` の呼び出し元は log モジュールだけになった。エラー（`notify::error`）と `--help` / `--version`（`notify::info`）はログではないので、この規則の外にあり、従来どおり出る。

**副作用（承知の上）**: `--debug` なしで端末から起動しても起動バナーすら出ない。常駐トレイアプリとしてはこれが正しい姿で、Explorer から起動したときと同じになる。

### 3. すべての行にタグと時刻を与える

`[debug]` は全行に付いていて何も区別していなかった。タグ列は**どの流れの行か**を表す 6 種類にした。

| タグ (ja / en) | 種別 | 何の行か |
| --- | --- | --- |
| `[入力]` / `[input]` | Detail | 物理キーの押下・解放 |
| `[判定]` / `[decided]` | Decision | そのキーをどうしたか |
| `[注入]` / `[injected]` | Detail | WinRemap が送出したイベント |
| `[操作]` / `[action]` | Action | 利用者の操作（トレイ・ボタン・設定読み込み） |
| `[前面]` / `[window]` | Action + Detail | 前面アプリの変化 |
| `[IME]` | Detail | IME インジケーターの問い合わせ |

前面アプリの報告（指摘 3）は 3 行の無時刻ブロックをやめ、**簡易モードに出る 1 行**と、詳細モードだけに出るパスの行に分けた。

```
18:01:51.471 [前面]   application 指定値: "notepad.exe" — 適用されるキーマップ: emacs-keys
             [前面]     C:\Windows\System32\notepad.exe
```

見える 1 行に `application` の値と適用キーマップを置いたのは、この報告が答えるべき問いが「なぜここでルールが効かないのか」だからである。フルパスは長く、めったに答えにならないので下げた。

### 4. ログウィンドウ自身の操作も記録する

追従・全イベントのチェックボックス、消去、コピーの 4 つが `[操作]` 行を残す。「ログが流れなくなった」「行が消えた」の答えがログの中にある状態にする。コピーは行数も出す（短い貼り付けを数で検算できる）。

消去とコピーの実装では**バッファのロックを解放してから**行を書く。`action` が同じ Mutex を取るため、握ったまま呼ぶとウィンドウが固まる。

### 5. チェックボックスの間隔

`theme::LOG_CONTROL_GAP = 12.0`。egui のチェックボックスはラベルの直後に次の部品が来るため、隙間がないと 1 つの部品に見える。

## 却下した代替案

- **`vk_display_name` そのものを拡張する**: 設定に書けない名前を設定用の関数が返すことになり、設定画面が `Num1` と表示して、そう書いたファイルはパーサーに弾かれる。名前空間を分けたのはこのため
- **OEM キーを静的テーブルで持つ**: 上記のとおり配列によって嘘になる
- **`GetKeyNameTextW` でキーの刻印を得る**: 最も正確（`半角/全角` がそのまま出る）だが、スキャンコードが要る。フックのリングに 1 フィールド増やす価値が、`MapVirtualKeyW` との差に見合わないと判断した。将来 OEM キーを設定記法に入れるときに再検討する
- **コンソール出力をチェックボックスの状態に従わせる**: 端末セッションにはチェックボックスがない。`--debug` の端末は全イベントを出す（後からチェックを入れられないため）
- **前面アプリ報告を `Kind::Detail` にする**: 「どのアプリにいるか」はリマップ結果を決める情報で、簡易モードから消してよいものではない

## 不変条件への影響

- **不変条件 2（フックコールバック内の処理制限）**: 変更なし。`keyname` も `record` もメッセージループ・GUI スレッド・インジケータースレッドからのみ呼ばれる。フックは従来どおり生の VK をリングに積むだけ
- **不変条件 3（unsafe の隔離）**: `src/keyname.rs` を許可リストに追加した（AGENTS.md を更新）。`MapVirtualKeyW` 1 か所のみ、`// SAFETY:` 付き。ポインタもハンドルも渡さない呼び出しで、ADR 0031（`notify.rs`）・ADR 0041（`clock.rs`）と同じ形 — 「Win32 に訊かないと答えられない 1 つの問いを、1 つのモジュールに閉じ込める」
- **不変条件 6（キーロガー化の禁止）**: 変更なし。出るのはキー名レベルのままで、`Num1` や `/` はキー名であって入力内容の記録ではない。既定 OFF・ディスクに書かないことも変わらない

## 確認方法

`tests/ui/guest/log-view.ps1`（`00-log-view`）に 8 件追加した。テンキーの命名、OEM キーの形、前面アプリ行とそのパス行、チェックボックス操作の記録、コピー行数、コンソールの列、そして `--debug` なしでコンソールが完全に沈黙すること。

実測したコンソール出力（`--debug`、ウィンドウなし）:

```
2026-07-29 07:09:27  WinRemap v0.5.0 started
TEST BUILD: input injected by other software is remapped too (--accept-injected)
WinRemap 0.5.0: 1 keymap(s) loaded from C:\Test\logview.toml
07:09:27.027 [window] application = "explorer.exe" — matching keymaps: global
07:09:27.027 [window]   C:\Windows\explorer.exe
```

### 途中で分かったこと（未解決・アプリ側は未確定）

前面アプリ行の検査を書いたときに、**ログウィンドウを開いている間、切り替えた先のアプリ（Notepad）が前面アプリ行に一度も出ない**ことを 2 回の実行で観測した。出たのは `winremap.exe` と `explorer.exe` だけである。`GetForegroundWindow()` で Notepad が前面だと確認でき、そのキーはフックに届いている（判定行が出ている）ので、**「フックは見ているが、前面の変化が報告されていない」**という状態になる。

3 回目の実行で切り分けた。**同じスクリプトの同じ関数で、WinRemap のウィンドウを 1 枚も開かずに `--debug` だけで動かすと、Notepad への切り替えは報告される。**

```
07:19:47.368 [window] application = "notepad.exe" — matching keymaps: global
07:19:47.368 [window]   C:\Program Files\WindowsApps\Microsoft.WindowsNotepad_...\Notepad.exe
```

つまり**ログウィンドウが開いているときだけ**起きる。2026-07-28 に記録した「WinRemap のウィンドウが前面にあるとき注入したキーがフックに届かない」と同じ系統の可能性が高い。

この機能の変更が原因ではない（ログ経路を変えただけで、報告の呼び出し条件は従来どおり `EVENT_SYSTEM_FOREGROUND` である）。また `05-remap-notepad`（Notepad でだけ `C-h` → `x`）は通っており、**exe キャッシュ自体は追従している**。したがって v0.5 は止めないが、**未解決の観測**として [05_ui-test-automation.md](../../05_ui-test-automation.md) の落とし穴節に測定ごと残し、切り分け記録が `00-log-view` の実行記録（`W|` 行）に毎回出るようにした。次にこの周辺を触る人はそこから読む。
