## 0. この文書の目的

v0.1〜v0.3 の受け入れ確認は **v0.2.0 と v0.4.0 の 2 リリース続けて未実施**である。理由はどちらも同じで、「手で全項目を通すコストに見合わない」。項目は 3 バージョン分でおよそ 200 あり、リリースのたびに同じ判断が繰り返される構造になっていた。

そこで v0.5 では**構造を変える**。各項目を「自動で通す／手で通す／もう通さない」に仕分け、**手で通すものを §4 の 1 枚に収める**。以後のリリースでは §4 だけを人が見ればよい。

## 1. 毎リリースの手順

```powershell
cargo test                        # 設定の検証・キー記法・i18n（§3 で「単体」と書いた項目）
cd tests\ui
.\run-vm-ui-test.ps1              # ゲスト VM での UI 自動テスト一式（§5）
```

1. 上の 2 つが緑であること
2. **§4 の手動最小集合**を通す
3. §6 の記録欄に日付と結果を書く

自動側が落ちたら手動へ進まない。落ちた項目が「手で見れば通る」ものだとしても、**自動側の判定が壊れていることのほうが重い**（v0.4 §G と同じ規律）。

## 2. 仕分けの原則

| 区分 | 中身 |
|---|---|
| **自動** | 機械が読める観測で判定できる — UIA の要素名・値、プロセスの有無、終了コード、ファイルやクリップボードの中身 |
| **手動** | 体感（遅延・取りこぼし・CPU）、見た目（レイアウト・配色・アイコンの判読）、実機依存（IME・マルチモニター・DPI・管理者権限・実キーボード）、外部アプリ（PHPStorm・ブラウザ・Word） |
| **廃止** | 一度きりの設計判断のための確認、または別の仕組みで恒久的に担保されたもの |

**迷ったら手動に置く。** 自動化したつもりで観測が抜けているほうが、手で 1 行読むより高くつく。テストが「アプリの不具合そっくりの失敗」を出す経験は Phase A で十分に積んだ（[05_ui-test-automation.md §6](../05_ui-test-automation.md)）。

**自動の判定に LLM を入れない。** 要素の探索をエージェントに任せると「ウィンドウが何も出していない」と「エージェントが開いていない」が区別できない。自動側の判定はすべて素の UIA クライアント（`tests/ui/guest/*.ps1`）で行い、エージェントは**読むだけ**にする。
