# ADR 0074: egui のフォークを 0.36.1 に載せ替え、wgpu を検証できないまま upstream PR を出す

- 作成日: 2026-08-09
- 作成: Claude Code（AI モデル: claude-opus-5[1m]）／レビュー・承認: オーナー
- ステータス: **承認（2026-08-09）**。[v0.9 開発計画 §3](../01_development-plan.md) Phase B の方式
- 関連: [ADR 0055](../../v0.5/decisions/0055-accesskit-for-child-viewports.md)（**本 ADR はその続きである**。子ビューポートに AccessKit を付ける方式、`[patch.crates-io]` の暫定運用と外す条件）、[ADR 0037](../../v0.2/decisions/0037-gui-invisible-host-viewport.md)（不可視ホスト＋子ビューポート）、[ADR 0035](../../v0.2/decisions/0035-gui-single-event-loop-multi-viewport.md)（単一 `EventLoop`）、[05_ui-test-automation.md](../../05_ui-test-automation.md)
- 公式: [egui のリリース](https://github.com/emilk/egui/releases)（0.36.0 = 2026-08-05、0.36.1 = 2026-08-07）／[`eframe 0.36.1` の `glow_integration.rs`](https://github.com/emilk/egui/blob/0.36.1/crates/eframe/src/native/glow_integration.rs)

## 背景

[ADR 0055](../../v0.5/decisions/0055-accesskit-for-child-viewports.md) は 3 つを決めた。**(1) eframe の子ビューポート生成経路に AccessKit の初期化を足して upstream PR を出す（本筋）、(2) マージを待つ間は `[patch.crates-io]` でフォークを指す（暫定）、(3) 外す条件を ADR に書く**。

**(1) は 2026-08-09 現在も未提出である。** v0.5・v0.6・v0.7・v0.8 と 4 版にわたって出していない。理由は ADR 0055 決定 1 に書いてある — **wgpu バックエンドにも同じ変更が要る**（`wgpu_integration.rs`）が、WinRemap は glow しか使わないため**検証手段が無く**、「片方だけの PR は不完全になる」と判断していた。

その間に **(2) の暫定が効き始めた**。

- **上流は 0.36.0（2026-08-05）・0.36.1（2026-08-07）を出している。** フォークは **0.35.0 から分岐**したままで、`[patch.crates-io]` が **egui スタック全体を 0.35.0 に固定している**
- `Cargo.toml` のコメントは「この pin を放置すると egui スタック全体が 0.35.0 に固定される」と警告していた。**その状態になった**
- ADR 0055 決定 2 の理由づけも「**外す条件を書いておかないと恒久化する**」だった。条件は書いてあるが、**条件を満たす行動（PR）を取っていない**ので同じことである

**上流はまだ直っていない。** `eframe 0.36.1` の `glow_integration.rs` を確認したところ、`init_accesskit` は**いまも `ViewportId::ROOT` にしか呼ばれていない**（2026-08-09 確認）。**待っていて直るものではない**という ADR 0055 の判断は、1 年分のリリースを経ても変わっていない。

## 決定

1. **フォークを 0.36.1 に載せ替える。** `DaikiSuganuma/egui` の `accesskit-child-viewports` を、タグ `0.36.1` から切り直す（master からは切らない。未公開の変更を巻き込まないため — ADR 0055 と同じ方針）
2. **`wgpu_integration.rs` にも同じ初期化を書く。** 呼び出し規約とプロキシの引き回しが glow と違うので、機械的な移植にはならない
3. **wgpu 側を検証できないまま PR を出す。** PR の本文に**「glow は実機で確認済み、wgpu は書いたが動作確認できていない」と明記する**
4. **PR を出すことを完了条件にする。** マージは上流の都合であり、こちらで制御できない
5. **マージされ、それを含む eframe が公開されたら `[patch.crates-io]` を外す**（ADR 0055 決定 2 の「外す条件」をそのまま引き継ぐ）。**v0.9 の期間内に入らなければ、pin は 0.36.1 のフォークを指したまま v0.9 を出す**

## 理由

- **決定 3 が本 ADR の要点である。** 「検証できないから出さない」を 4 版続けた結果が現状である。**不完全な PR は、出さない PR より価値がある** — 上流のメンテナは wgpu を確かめられる立場にあり、こちらは確かめられない。**確かめられない側が確かめられるまで待つ**という構図には出口が無い
- **正直に書くことが条件である。** 「動作確認できていない」と書かずに出せば、レビューする側の時間を無駄にする。書いたうえで出せば、**協力の依頼**になる
- **決定 1（0.36.1 へ）を同時にやるのは、どのみち必要だからである。** 上流に PR を出すなら最新のタグに対して出すのが筋で、WinRemap 側も pin を外せる日に備えて 0.36 系で動くことを確かめておく必要がある
- **決定 4（PR を出すこと自体を完了条件にする）**: マージを完了条件にすると、上流の都合で v0.9 が止まる。ADR 0055 が「v0.5 を人質に取らないために暫定手段を持つ」と書いたのと同じ考え方である

## 却下した代替案

- **wgpu を検証できるまで出さない（現状維持）**: 4 版続けてこれを選び、pin が恒久化しつつある。**検証手段を得る見込みが無い**（WinRemap は wgpu を使わないので、使ってもいないバックエンドのために環境を用意することになる）
- **glow だけの PR を出し、wgpu には触れない**: 上流から見れば「片方のバックエンドだけ直った」状態で、レビューで止まる公算が高い。**同じ欠落が wgpu 側に残ることを、こちらは知っている** — 知っていて触れないのは不誠実でもある
- **フォークを恒久的に持つ**: ADR 0055 で却下済み。egui の版を上げるたびに追従コストがかかり、**今回それが実際に発生している**
- **AccessKit を諦める**（`[patch.crates-io]` を外し、UI テストをスクリーンショット判定に戻す）: ADR 0055 が却下した案であり、**判定の揺れと「押せない」問題が戻る**。v0.5 で解いたものを手放すことになる
- **0.36 への載せ替えだけ行い、PR は v0.10 に送る**: 載せ替えの作業の中で PR に必要なものはほぼ揃う。**同じコードを 2 度読むことになる**ので、まとめて行うほうが安い

## 影響・補足

- **GUI 全体に触る変更である。** 0.35 → 0.36 の API 変更に追随する必要がある。**単独のブランチで進め、Phase A・C・D と混ぜない**（開発計画 §7）
- **確認は VM の UI テスト全 10 件で行う。** AccessKit が子ビューポートで効いていなければ `00-uia-actuation` が落ちるので、**この 1 件が方式の生死を判定する**
- **バイナリサイズと起動時間を測り直す。** ADR 0055 が実測を残している（feature 有効化で +442〜470 KB、起動時間は有意差なし）。0.36 で変わっていないことを確かめ、同じ形で記録する
- **PR がマージされた場合、`[patch.crates-io]` を外すのは「それを含む eframe が公開されてから」である。** master にマージされただけでは外せない（crates.io の版が要る）
- **フォークのブランチとコミットを、載せ替え後に本 ADR へ追記する**（ADR 0055 が 0.35.0 について行ったのと同じ形）
