## 0. このバージョンの性格

**v0.8 で見つかった宿題を片付ける版である。** 利用者から見える新機能は入れない（オーナー判断 2026-08-09）。

v0.8 は「作る側と確かめる側の作業を軽くする版」だった。その過程で**作った当人が気づいていなかった欠陥が 3 種類**出てきた — 動いていないと思っていなかったコード（`restore()` の 1 段目）、検査していないと思っていなかった出力（着色カーソル）、直したと思っていた文書（README は直してサイトは直っていない、が 3 回）。

**共通しているのは「失敗が黙って捨てられていたこと」である。** `continue` と `let _ =` で捨てた戻り値、誰も測らなかった生成物、片方だけ直した文書。v0.9 はそこを塞ぐ。

## 2. Phase A — カーソルの色まわり（**M-2 の根治には ADR 0073 が要る**）

**2 件入っている。** 2.1〜2.2 は M-2 の根治（ADR 0073 の範囲）、**2.3 は設定ウィンドウの欠落**で、ADR は要らない。**同じ機能に触るので 1 本のブランチでまとめて進める。**

### 何が起きているか

**着色した I ビームとして、可視画素が 1 つも無いカーソルが入る。** 色が消えるのではなく何も描かれない。矢印は無事で、IME を切り替えても戻らず、WinRemap を起動し直すと戻る。実作業の中で 4 回起き、狙って再現できたことは一度もない。詳細は[調査ノート](../v0.8/notes/20260809_m2-empty-ibeam.md)。

**原因は未特定である。** ただし**確定した欠陥が 2 件**あり、どちらも単独で直す価値がある。

### 2.1 `restore()` の 1 段目が、この Windows では一度も動いていない

```
LoadImageW(user32, IDC_ARROW, IMAGE_CURSOR, 0, 0, LR_SHARED) -> 0  (GetLastError=1814)
LoadImageW(user32, IDC_IBEAM, ...)                           -> 0  (GetLastError=1814)
```

`1814` は `ERROR_RESOURCE_NAME_NOT_FOUND`。[`src/cursor.rs`](../../src/cursor.rs) は「`IDC_*` のアトムは user32 内のリソース ID でもある」という前提で書かれているが、**Windows 11 26200 では成り立たない**。失敗は `continue` で捨てられ、**復元は `SPI_SETCURSORS` の 1 段だけで回っている**。[ADR 0067](../v0.8/decisions/0067-ime-cursor-color.md) が「既定スキームではレジストリの値が空で、`SPI_SETCURSORS` だけでは戻らないことがある」として用意した備えが、丸ごと外れていた。

**この機械のレジストリはまさにその状態である**（`IBeam` が空、`Arrow` だけ `aero_arrow.cur`）。**矢印が壊れず I ビームだけ壊れる**という非対称は、これで説明が付く。

### 2.2 作った結果も、元にする対象も、誰も検査していない

`tinted()` は結果を検査せず、`apply()` は元カーソルを検査しない。そして `from_color()` は「アルファが無ければ AND マスクを見る」ので、**空のカーソルを元にすると、また空を作る**。一度入ると自己再生産する。

### 2.3 設定ウィンドウに `change_cursor_color` と `cursor_color` が出ない（**オーナー報告 2026-08-10**）

**v0.8 の目玉の設定が、設定ウィンドウの `[ime_indicator]` にひとつも出ていない。** 表示（`ime_ui()`）が並べる行は `enabled` / `duration_ms` / `size` / `opacity` / `show_app_name` / `trigger_keys` の 6 つで、**`change_cursor_color` と `cursor_color` が抜けている**。

**当初「表示だけの落ち」と書いたが、それは誤りだった**（2026-08-10 に実装しながら判明）。[`ImeIndicatorDraft`](../../src/config/draft.rs) が**そもそも 2 つのフィールドを持っていない**ので、**読み取りも編集も保存も通っていない**。設定ウィンドウで編集できる設定の一覧から、丸ごと外れていた。

> **設定が消える事故にはなっていなかった。** `apply()` は**下書きの値が変わったキーだけ**を `toml_edit` で書き換えるので、下書きが知らないキーには触れない。**知らないことが、たまたま守っていた。** それに依存し続けないよう、v0.9 では下書きに載せたうえで「触らない編集で残る」ことをテストで固定する。

**利用者から見ると「設定ウィンドウで見えない設定」である。** README とヘルプサイトと `02_config-spec.md` には書いてあるので、**文書にはあるのに画面には無い**という、Phase D の D-2 と同じ形の食い違いになっている。

> **`enabled` で隠してはならない。** `ime_ui()` は 2 行目以降を `if settings.enabled` で囲っている（パネルの見た目の設定だから、という理由）。**カーソルの色は `enabled` と独立**であり（[ADR 0067](../v0.8/decisions/0067-ime-cursor-color.md)、受け入れ M-6 がまさにそれを見ている）、**`enabled = false` でも表示されなければならない**。ここを機械的に真似すると、v0.8 で決めた独立性が画面の上で壊れる。

### タスク

1. **起動時に、汚れる前の素のカーソルを複製して持つ。** 復元はそこから行う。「user32 から読み直す」方式は前提から成立していない
   - **持てなかった場合の退避**（起動時にすでに汚れていた等）も決める。`SPI_SETCURSORS` は依然として有効な手段である
2. **可視画素が 1 つも無い着色カーソルは入れない。** 作れなかったこととしてログに残す。**これだけで利用者から見える症状は消える**
3. **空のカーソルを元に作らない。** 自己再生産を断つ
4. **失敗を黙って捨てない。** いまの `continue` と `let _ =` をログに出す（v0.8 で足した `apply()` の戻り値と同じ形）
5. **`probe-ime-cursor.ps1` に「着色 → 復元 → 着色」を繰り返す項目**を足し、繰り返しの中で空にならないことを見る
6. **設定ウィンドウに `change_cursor_color` と `cursor_color` を通す**（2.3）。**表示だけでなく、下書き・編集・保存の 4 つとも**である。**`enabled` で隠さない。** `cursor_color` は `#rrggbb` の形で見せる（[`parse_hex_color`](../../src/ime_indicator_settings.rs) が受け付ける唯一の綴りである）。i18n のラベルは日英とも足す（**実施済み 2026-08-10**。テスト 3 件を含む）

**タスク 1〜5 は実施済み（2026-08-11）。** [`src/cursor.rs`](../../src/cursor.rs) の作り直しで、要点は 4 つある。

1. **`capture_pristine()` を新設**し、[`main.rs`](../../src/main.rs) の `cursor::restore()` の直前で呼ぶ。**単一起動の判定より後**でなければならない — 2 つ目の WinRemap がここを通ると、1 つ目の正当な着色を消してしまう。中では ADR 0073 決定 1 のとおり、**先に `SPI_SETCURSORS` を 1 度打って**前の実行が残した着色を落とし、**そのうえで採った複製が空でないことを確かめる**
2. **`user32.dll` から読み直す経路は消した。** 直したのではなく無くした。ADR 0073 が却下したとおり、リソース ID は文書化されておらず、同じ罠を踏む構造を残さないためである
3. **空の判定を 2 か所に入れた。** 元が空なら着色しない（決定 4）、**作った結果が空なら入れずに捨てる**（決定 3）。後者は前者があっても必要である — `outlined()` は半分より薄い画素を落とすので、**縁だけでできたカーソルは、空でない元から空を作れる**。この経路が届くことは単体テストで固定した
4. **`Kind::Failed` を足した。** 「1 つも着色できなかった」が、これまで「差し替え 0 件の成功」と読める形で記録されていた

**「安全網が張れている」ことを言う 1 行を起動時に出す**ようにした（`カーソル: 復元用に素の複製を 2 個持ちました`）。**これは失敗の記録ではなく成功の記録である** — 今回の教訓は「`1814` が 2 版のあいだ返り続けたのに、誰も問い合わせる先が無かった」ことなので、**張れているかどうかを見に行ける**ことそのものが直しの一部である。

### 完了条件

- **繰り返しの検査が通る**（1〜2 で塞いだつもりのものが、実際に塞がっている）— **通過（2026-08-11）。** `probe-ime-cursor.ps1` に `repeated-toggles-never-empty-the-tint` を足し、**10/10**
- **設定ウィンドウに 2 つの設定が出る。`enabled = false` でも出る**（受け入れ H-3 か M-6 で見る）— **通過（2026-08-11、オーナー目視）。** 表示・編集の両方に 2 行が出ること、**`enabled` のチェックを外しても消えないこと**を確認した
- **空のカーソルを人工的に入れた状態から起動しても、素に戻る**（2.1 の直しがこの経路を通る）— **別の形で確かめた（下記）**

> **「通った」だけでは、新しい経路の証拠にならない。** この機械では `SPI_SETCURSORS` **も**効くので、検査が 10/10 でも「複製から戻せた」のか「今までどおり 2 段目だけで戻った」のかは区別が付かない。**復元から `SPI_SETCURSORS` を一時的に外した版を作って測り直した**（2026-08-11）。`restores-when-the-ime-goes-off`・`repeated-toggles-never-empty-the-tint`・`the-next-start-restores-it` を含めて **10/10 が通った** ＝ **複製だけで戻せている**。細工は測ったその場で外し、`grep` で残っていないことを確かめてある。
>
> **人工的に空を入れる形にしなかった理由**もここにある。この機械ではその状態を `SPI_SETCURSORS` が単独で戻せてしまうので、**その検査は 2.1 の直しを通らない**。上の分離のほうが、直した経路そのものを測っている。
- **オーナーが数日使って再発しない。** ただし**再発しないことを直った証拠にしない** — 4 回とも実作業の中でしか出ていないので、**検査で捕まえられる形にすること**が完了条件である（[受け入れ §7 の 2026-08-08](../v0.8/03_acceptance-checklist.md)）

> **ホットスポットが手掛かりとして残っている。** 壊れたカーソルは `(9,10)`、正常に作られたものは `(8,9)` だった。**壊れたほうは別の元から作られている。** 次に捕まえたときは、そのときのホットスポットと直前の `カーソル:` のログ行（`作り直し` が付いているか）を見ること。

## 3. Phase B — egui / eframe を 0.36.1 へ（**ADR 0074 が要る**）

### なぜやるか

`Cargo.toml` の `[patch.crates-io]` が **egui スタック全体を 0.35.0 に固定している**。上流は **0.36.0（2026-08-05）・0.36.1（2026-08-07）**が出ており、[ADR 0055](../v0.5/decisions/0055-accesskit-for-child-viewports.md) 決定 2 が警告した「pin の恒久化」が実際に起きはじめている。**pin を外す唯一の道は upstream にマージされることである。**

**上流はまだ直っていない。** `eframe 0.36.1` の `glow_integration.rs` を確認したところ、`init_accesskit` は**いまも `ViewportId::ROOT` にしか呼ばれていない**（2026-08-09 確認）。フォークは依然として必要である。

### 何が止めていたか

[ADR 0055](../v0.5/decisions/0055-accesskit-for-child-viewports.md) 決定 1 のとおり、**wgpu バックエンドにも同じ変更が要る**（`wgpu_integration.rs`）。WinRemap は glow しか使わないので検証手段が無く、「片方だけの PR は不完全になる」として出していなかった。**2 版のあいだ出していない。**

### タスク

1. **フォークを 0.36.1 に載せ替える**（`DaikiSuganuma/egui` の `accesskit-child-viewports`。いまは 0.35.0 から分岐）
2. **`wgpu_integration.rs` にも同じ初期化を書く。** 検証手段が無いことは PR に正直に書く — **上流のメンテナのほうが wgpu を確かめられる**
3. **実測でアダプターの制約を満たす**（[ADR 0055](../v0.5/decisions/0055-accesskit-for-child-viewports.md) 決定 4）— アダプターはウィンドウを最初に表示する前に作る必要がある。子ビューポートは可視で作られるので、**一旦隠して作り、付けてから表示する**
4. **`emilk/egui` へ PR を出す**
5. WinRemap 側で **UI テストが全件通ること**を確かめる（設定・ログウィンドウが UIA から読めて押せること）
6. **マージされて公開版に入ったら `[patch.crates-io]` を外す**（[ADR 0055](../v0.5/decisions/0055-accesskit-for-child-viewports.md) 決定 2 の「外す条件」）。**v0.9 の期間内に入らなければ、pin は 0.36.1 のフォークを指したまま出す**

**1・2・3・5 は実施済み（2026-08-11）。**

- **載せ替えは競合ゼロだった。** 枝は `accesskit-child-viewports-0.36`（`DaikiSuganuma/egui`）。0.35.0 版の枝は残してある
- **wgpu は別コミットにした。** 上流が glow だけ取れるようにするためである。**動作確認できていないのは wgpu 側だけ**なので、そこが切り離せる形になっていることに意味がある
- **wgpu で 1 か所だけ glow と形が違う。** wgpu は `egui_winit::create_window` を通り、そこが対象モニターの解決も持っているので、「隠して作る」指定を `WindowAttributes` ではなく **`ViewportBuilder` 側**に置いた
- **WinRemap 側のコード変更は不要だった。** `Cargo.toml` の版と枝名だけ。テスト 142 件・`fmt`・`clippy` はそのまま緑

### 完了条件

- `cargo tree` で egui スタックが **0.36.1** であること — **通過。** `egui` / `eframe` / `egui-winit` ほか、木の中に `0.35` は 1 つも残っていない
- **VM の UI テスト全 10 件が通る**（AccessKit が子ビューポートで効いていることの実測でもある）— **通過（2026-08-11）。121/121。** 設定ウィンドウの要素数は **54 で、載せ替え前と同一**だった
- **PR が出ている**（マージは上流の都合なので完了条件にしない）— **未**

> **載せ替えの前にも 1 回、同じ 121/121 を取ってある。** 今日は Phase A で GUI（設定ウィンドウの 2 行）に触っているので、**その状態で緑を確かめてから**載せ替えた。落ちたときに「載せ替えのせい」と言い切れるようにするためである。

> **「wgpu が書けないから出さない」を続けると pin が恒久化する。** 不完全でも出して上流と話すほうが、フォークを持ち続けるより保守の総量が小さい — というのが ADR 0055 の理由づけそのものである。

## 4. Phase C — MSIX のアイコンが「青い四角」になる件

### 何が起きているか

Store 版を「設定 → アプリ → スタートアップ」で見ると、**アイコンが青一色に塗りつぶされている**（2026-08-09、オーナー確認）。GitHub 版は正しく出る。

**当初の見立ては「`altform-unplated` のアセットが無いこと」だった。それは半分しか当たっていなかった**（2026-08-11 に実測で判明）。**原因は 3 つ重なっていた。**

| # | 何が足りなかったか | 直し |
|---|---|---|
| **1** | **`resources.pri` がそもそも無かった。** `scale-` も `targetsize-` も `_altform-` も、**フォルダーを見て見つかるものではなく、パッケージのリソース索引を通して引かれる**。索引の無いパッケージは**マニフェストが名指しした 1 個のファイルしか使わない** | `build.ps1` に **`makepri`** の段を足した |
| **2** | **`targetsize-44_altform-unplated` が無かった。** 公式手順が名指ししているのはこのサイズである。08-10 に置いた 5 枚は 16/24/32/48/256 で、**44 だけ抜けていた** | `examples/msix_assets.rs` の `TARGET_SIZES` に 44 を足した |
| **3** | **「設定 → アプリ → スタートアップ」は `unplated` を引かない。** ここは**プレート（下地）の上にロゴを載せる**面で、下地の色は `BackgroundColor`。それが `transparent`（＝**アクセントカラーを使う**という意味であって「透明」ではない）だったので、**青い下地に青いロゴ**が乗っていた | マニフェストの `BackgroundColor` を **`#FFFFFF`** にした |

**1 が本命だった。** 08-10 に置いた 5 枚は、索引が無いあいだ **一度も参照されていなかった**。同じ理由で `scale-*` の 10 枚も効いていなかった。**Store に出した 0.8.0 も `resources.pri` を持っていない**ので、この欠陥は 0.6.0 から出荷され続けている。

画像そのものは正常である（不透明部分 41〜46%）。GitHub 版が正しく出ていたのは、**インストーラー版のアイコンが exe に埋め込まれた `.ico` で、索引を通らないから**である。

## 5. Phase D — 受け入れとリリース運用の穴

**WinRemap の中身ではなく、作り方と確かめ方の側の話である。** 3 件入っていて、いずれも v0.8 で**実際に判定を誤らせたか、欠陥を隠していた**。

| # | 何が起きたか | 塞ぐもの |
|---|---|---|
| **D-1** | H-1 で「単語削除になりました」という報告を受けた。**額面どおり書けば「発端の問題が再発した」という記録になる**ところだった。実際は設定が PHPStorm に届いておらず、素の `Ctrl+H` を見ていた | 受け入れの**誤判定** |
| **D-2** | 実挙動が変わったのに**サイトだけ古いまま**が 3 回。README は毎回直っていた | 文書の**食い違い** |
| **D-3** | `restore()` の 1 段目が `1814` で失敗し続けていたが、`continue` で捨てられていて**機能の導入時から誰も気づけなかった** | 欠陥の**隠蔽** |

### 5.1 H-* に準備が無い（`-Prepare H`）

M-* には `-Prepare M` があるのに H-* には何も無く、**実運用の設定（`notepad.exe` だけの最小設定）のまま H-1 を実施して、発端の問題そのものを「不合格」と読みかけた**（[受け入れ §7 の 2026-08-08](../v0.8/03_acceptance-checklist.md)）。

- **`-Prepare H` を足す**か、少なくとも**チェックリストの H-1 の行に「どの設定で測るか」を書く**
- **見てもらう前に、その機能が有効な設定で動いていることを確かめる。** 同じ日に 2 度踏んでいる（H-1 と、M-2 の A〜D の切り分け）

**実施済み（2026-08-10）。** [`tests/acceptance/manual-minimum.toml`](../../tests/acceptance/manual-minimum.toml) を新設し、`-Prepare H` を足した。対象は `["*"]` — H-1 は「そのとき手元にあるターミナル」で測る項目なので、アプリ名を数え上げる形にすると**数え漏らしたアプリが「不合格」に化ける**。`C-h` に加えて **`C-a` = `Home`** を入れてある。`C-h` だけでは交絡するからである（シェルの Emacs キーバインドでも 1 文字消える。2026-08-10 の P-7 で踏んだ）。

**「見てもらう前に動いていることを確かめる」はハーネス側に入れた。** `Start-HarnessProcess` が**実際に動いているプロセスの実行ファイルのパスを名指す**ようにし、動いていなければ `[人] 起動したはずの … が動いていない — 受け入れを始めないこと` を出す。

> **ここで穴を 1 つ踏んだ。** 最初の実装は「プロセスが見えたら成功」としていたが、**別の WinRemap が常駐していると 2 つ目は自力で終了する**（`Local\winremap-single-instance`）。その途中経過を捕まえて「起動した」と報告していた。実測すると**約 0.5 秒で消える**。1 秒待ってから見直す形に直した。**確認を足すときは、その確認自体が何を見ているかを測ること。**

### 5.2 文書の直しが片方に落ちる

**実挙動が変わったとき、直す場所は README とヘルプサイトの 2 つある。** v0.8 では**同じ落ち方を 3 回**した — FAQ のリダイレクトの記述、`ime.html` の管理者権限の記述、`config.html` に新しい設定が無い件。いずれも README は直っていて `site-src/` への反映が漏れていた。

**選択肢は 2 つある**（§8 の 6 で決める）。

| | 案 | 中身 | 捕まえられるもの |
|---|---|---|---|
| **軽** | **チェックリストに 1 行足す** | H-9 の観点に「**この版で増えた設定が `config.html` にあるか**」を明記する | 設定の載せ忘れ（3 件のうち 1 件） |
| **重** | **CI で突き合わせる** | 設定名の一覧を [`02_config-spec.md`](../v0.1/02_config-spec.md)・README・`config.html` の 3 か所から抜き出し、**食い違ったら赤にする**（`site-src\build.ps1 -Check` と同じ発想） | 同上。**文章の中身の食い違いは捕まらない** |

**軽い案から始めることを勧める。** 3 件のうち 2 件（リダイレクトの説明・管理者権限の記述）は**文章の意味の食い違い**で、機械が突き合わせられるものではない。機械で捕まるのは「設定名があるか」だけであり、それは 1 行の項目でも捕まる。

**軽い案で実施済み（2026-08-11、オーナー決定）。** [受け入れ §5](../v0.8/03_acceptance-checklist.md#5-h-9文書で見る観点) に 3 つ足した。

1. **`config.html`（日英）の行**。この表には `ime.html` と `faq.html` はあったのに **`config.html` が無かった** — ③を見落とした直接の原因である
2. **「README が直っているからサイトも直っている、と読まない」**という前置き。3 件に共通する落ち方がこれである
3. **増えた設定を数え上げるコマンド** — `git diff <前の版のタグ>..HEAD -- src\config\raw.rs`。設定名を受け付けるのはこの構造体だけ（`deny_unknown_fields`）なので、差分がそのまま一覧になる。v0.7.0 との差分で試すと `change_cursor_color` と `cursor_color` がちょうど出る ＝ **v0.8 で漏れた 2 件をこの手順は捕まえる**

**重い案（CI での突き合わせ）は入れない。** 捕まえる範囲は軽い案と同じ「設定名があるか」だけで、勝っているのは気づく時期だけである。もし将来やるなら、**突き合わせ先は 3 つの文書どうしではなく `src/config/raw.rs` と各文書にする** — 文書どうしを比べても、全部が同じだけ古ければ緑になる。

### 5.3 失敗を黙って捨てない

Phase A のタスク 4 と同じ性質のものが、ほかにもある。**`let _ =` と `continue` で捨てている Win32 の戻り値を洗い、少なくともログに出す。**

**実施済み（2026-08-11）。** `src/` 全体で `let _ = unsafe { … }` は **22 か所**あった。洗った結果は次のとおりで、**直したのは `cursor.rs` の 2 か所だけである**。

| 何 | 数 | 判断 |
|---|---|---|
| `cursor.rs` の `SetSystemCursor` と `SPI_SETCURSORS` | 2 | **直した。** 失敗すれば着色が残るか戻らないかで、**利用者に見える**。しかも「戻せなかった」は誰にも届いていなかった |
| 後片付け（`DeleteObject`・`DeleteDC`・`CloseHandle`・`DestroyWindow`・`KillTimer`・終了時の `UnhookWindowsHookEx` / `UnhookWinEvent`） | 12 | **そのまま。** 失敗しても取れる手が無く、プロセスの終わりで OS が回収する |
| `PostThreadMessageW`（メッセージループの起こし） | 5 | **そのまま。** 「取りこぼした合図＝ログ 1 行かパネルの点滅 1 回の遅れ」であることが、いずれもコメントに書いてある。**うち 2 か所はフックのコールバック上**で、そこでログを書くこと自体が禁じ手である |
| コンソールまわり（`FreeConsole`・`SetConsoleMode`・`SetStdHandle`・`SetConsoleTitleW`） | 4 | **そのまま。** 報告先がそのコンソール自身なので、書ける保証がない |
| `SPI_GETWORKAREA`（記録バナーの位置） | 1 | **そのまま。** 1920×1080 の控えが用意してあり、コメントにも書いてある |

**この洗い出し自体が答えの一つである。** 22 か所のうち 20 か所は**理由がその場に書いてあった**。書いていなかった 2 か所が、そのまま**2 版のあいだ気づかれなかった欠陥**だった。**`let _ =` の隣に理由が無いことが、見るべき場所の目印になる。**

## 7. フェーズ順序と依存関係

```
（先に v0.8 の受け入れを閉じる: H-6・P-1〜P-9）
        │
        ├──▶ Phase A（M-2 の根治）──┐
        ├──▶ Phase C（MSIX アイコン）├──▶ Phase E（文書・受け入れ・リリース）
        ├──▶ Phase D（運用の穴）────┘
        └──▶ Phase B（egui 0.36.1）──┘
```

- **A を最優先にする。** 利用者から見える唯一の不具合であり、v0.8 で「既知の問題」として文書に書いた借りでもある
- **B は独立していて重い。** GUI 全体に触るので、A・C・D と混ぜずに単独のブランチで進める
- **C・D は小さい。** A の待ち時間（再発待ち・検査の作り込み）に挟める
- **Phase A の「オーナーが数日使って再発しない」は時間がかかる。** リリースを人質に取らないよう、**検査で捕まえられる形にすることを完了条件**にしてある
