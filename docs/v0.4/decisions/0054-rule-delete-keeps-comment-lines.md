# ADR 0054: 規則を削除しても、その上のコメント行は残す

- ステータス: 承認（オーナー承認 2026-07-26、Phase A 受け入れテスト C-4 の指摘への対応）
- 日付: 2026-07-26
- 作成: Claude Code（AI モデル: claude-opus-5）
- 参照: [ADR 0036: 保存時のコメント保持](../../v0.2/decisions/0036-config-save-preserves-comments.md)、[ADR 0049: 編集ドラフトモデル](0049-config-edit-draft-model.md)、[02_config-editing-design.md §4.2](../02_config-editing-design.md)、[toml_edit の decor](https://docs.rs/toml_edit/latest/toml_edit/struct.Decor.html)

## 文脈

設定 GUI で規則を削除して保存したとき、どのコメントが一緒に消えるかを決めた規則が v0.2 §4.2 にある。

> 該当キーを消し、**直前に密着した（空行を挟まない）コメント行**も一緒に消す。空行で離れたコメントは残す

「密着＝その規則の説明」という読みに基づいている。受け入れテスト C-4（オーナー実施 2026-07-26）でこれが実際の書き方と合わないことが分かった。

```toml
[keymap.remap]
# --- Editing ---
"C-h" = "Back"
"C-d" = "Delete"
```

`"C-h"` を削除すると `# --- Editing ---` も消える。このコメントは 1 つの規則ではなく**その下の一群**を指しており、最初の 1 件を消しただけで見出しが失われる。規則の直上に空行を置かずに見出しを書くのは自然な書き方であり、「密着しているか」では「その規則のものか」を判別できない。

判別できない以上、どちらかに倒すことになる。消し過ぎると利用者の書いた文章が黙って失われ、`↶ 元に戻す` は編集セッション全体を捨てる操作なので、1 行だけ取り戻す手段がない。

## 決定

1. **規則の削除で消えるのは、その規則の行と、行末（同じ行）に書かれたコメントだけとする。** その上に**独立した行**として書かれたコメントは、空行の有無にかかわらず残す。
2. 残したコメント行は、次に残る規則の直前へ移す（間の空行も含めて移す）。これは従来「空行で離れたコメント」に対して行っていた動作と同じで、対象が広がっただけである。
3. 最後の規則を消した場合、その上のコメントは行き先が無いので一緒に消える。導く対象が残っていないため。
4. あわせて、**GUI が書き足す規則のキーは引用符付きで書く**（`"C-n" = "Down"`）。`toml_edit` の既定エンコーダーは `C-n` を裸のキーとして書き、TOML としては同じだが、引用符付きで並ぶ既存の規則の中で 1 行だけ見た目が変わる（受け入れテスト C-3）。

## 理由

- **利用者が書いた文章を黙って消さないことを優先する。** 消し過ぎは復旧できない（元のファイルを開き直す以外にない）が、残し過ぎは目に見えていて 1 回の編集で消せる。非対称なので、残す側に倒すのが正しい。
- **規則にしたときに一言で説明できる。** 「消えるのはその行だけ」は、利用者が保存後の差分を見て納得できる（v0.2 §4.2 の判断基準そのもの）。「密着なら消える」は、空行の有無という見えにくい条件を覚えていないと予測できない。
- **見出しの喪失は連鎖する。** 見出しが 1 件目の削除で消えると、残りの規則が何の一群だったのか分からなくなる。逆に説明コメントが 1 つ残っても、読めば古いと分かる。

## 却下した代替案

- **v0.2 §4.2 のまま（密着コメントは消す）**: 今回の指摘そのもの。見出しを守れない。
- **見出しらしさを推測する**（`---` を含む、次に空行が無い、下に複数の規則が続く 等）: 判定が当たったり外れたりする規則は、外れたときに何が起きたのか説明できない。`# 削除用` と `# --- Editing ---` を機械的に見分ける根拠は文面には無い。
- **削除時に確認を挟み、コメントをどうするか尋ねる**: 1 行消すたびに問われる。画面設計 §11 未決 1 で「削除に確認は挟まない」と決めた方針とも衝突する。
- **コメントも編集対象にして、GUI 上で消せるようにする**: ADR 0049 決定で「コメントは GUI で編集しない・`toml_edit` が保持する」としている。編集できるようにすると往復保持の担保が崩れ、B2 の範囲を大きく超える。
- **削除した規則のコメントを「（削除済み）」等に書き換える**: 利用者が書いていない文字列をファイルに書き込むことになる。往復保持の原則に反する。

## 影響

- `src/config/draft.rs` の `detached_comments` が、空行で区切られたブロックではなく**独立行のコメント全体**を返す。単体テスト 2 件（`deleted_rule_keeps_the_comment_lines_above_it`、`deleting_the_first_rule_of_a_group_keeps_its_header`）で固定した。
- 受け入れチェックリスト C-4 の期待結果を書き換えた（`docs/v0.4/03_acceptance-checklist.md`）。
- 設定ファイルの書き戻し規則は `02_config-editing-design.md` §4.2 が正。本 ADR で表の「項目の削除」行を置き換えた。
- **同じ「消さない側に倒す」判断を、ファイル冒頭のコメントにも適用した。** `[[keymap]]` で始まるファイルでは冒頭のコメント塊が `toml_edit` 上は 1 番目のキーマップの装飾になっており、並べ替えで一緒に移動し、そのキーマップの削除で消えていた（受け入れ C-5・C-7 の実施で使った `examples/emacs.toml` の差分から判明）。切り離して先頭に残す（`rebuild_keymaps`、テスト `the_file_header_stays_above_the_first_keymap`）。これは本 ADR の決定事項ではなく、同じ原則による不具合修正である。
