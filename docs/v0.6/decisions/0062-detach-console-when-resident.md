# ADR 0062: 常駐に入る直前にコンソールを切り離す（`--debug` を除く）

- ステータス: 承認（オーナー決定 2026-07-29）
- 日付: 2026-07-29
- 作成: Claude Code（AI モデル: claude-opus-5[1m]）

## 文脈

Windows ターミナルから `winremap.exe` を起動すると WinRemap は常駐するが、**そのターミナルを閉じると WinRemap も終了する**（オーナー報告 2026-07-29）。プロンプトはすぐ戻り、続けてコマンドを打てるため、利用者からは「すでに独立したプロセスになっている」ように見える。実際にプロセスは独立しており、シェルは終了を待っていない。

終了の原因は親子関係ではなく**コンソールへの接続**である。[ADR 0029](../../v0.2/decisions/0029-attach-console-and-tray-log-window.md) で、ターミナル起動時のみ出力を届けるために `AttachConsole(ATTACH_PARENT_PROCESS)` を呼ぶことにした。この接続はプロセス終了まで解除されない。

Windows はコンソールウィンドウが閉じられたとき、**そのコンソールに接続している全プロセス**に `CTRL_CLOSE_EVENT` を送る。公式ドキュメント（HandlerRoutine）によれば、システムはハンドラの応答を限られた時間しか待たず、その後プロセスを終了させる。つまり**ハンドラを書いても生き延びる方法はない**。WinRemap は `SetConsoleCtrlHandler` を設置していないため既定ハンドラ（`ExitProcess`）で落ちる。

オーナーの要求は「`--debug` でない場合は、どのアプリから呼び出されても親を持たないプロセスにしたい」である。

## 決定

1. **`--debug` が指定されていないときは、常駐に入る直前に `FreeConsole()` でコンソールを切り離す**。呼び出し位置は `main.rs` の `hook::run_message_loop` の直前、`notify::detach_console()` として `notify.rs` に置く（`unsafe` の隔離先は ADR 0031 で許可済みの `notify.rs` のまま。不変条件 3 の改訂は不要）
2. **切り離しは意図的に遅らせる** — 設定ファイルのエラー、多重起動、フック設置の失敗といった**起動時の失敗は、それが報告されたターミナルに出したまま**にする。切り離し後に発生するもの（トレイからのリロード失敗など）は、エクスプローラー起動時と同じダイアログ経路（`notify::error`）に落ちる
3. **`--debug` は接続したままにする** — このモードのログはそのターミナルへ流し続けるものであり、切り離すと出力先が消える。したがって `--debug` セッションは従来どおりターミナルと運命を共にする（デバッグ用途では自然な挙動である）
4. **リダイレクトされている場合の扱い** — `FreeConsole` はファイル・パイプのハンドルには影響しない。ただしコンソールから借りたハンドル（`CONOUT$`）は切り離し後に無効になり、Rust の `println!` / `eprintln!` は書き込み失敗で **panic** する。そこで、**stdout と stderr の両方をランチャーが設定していた場合に限り**出力を継続し、それ以外は無効ハンドルに書かないよう出力を止める（`HAS_CONSOLE` を false にする）。判定材料はコンソール接続前に記録する（接続後はハンドルが誰の設定か区別できないため）

参照（公式）:

- FreeConsole: https://learn.microsoft.com/en-us/windows/console/freeconsole
- HandlerRoutine（`CTRL_CLOSE_EVENT` の扱い）: https://learn.microsoft.com/en-us/windows/console/handlerroutine
- AttachConsole: https://learn.microsoft.com/en-us/windows/console/attachconsole

## 理由

- **常駐ツールの寿命が、たまたま起動に使ったウィンドウに依存すべきではない**。エクスプローラーから起動した場合と、ターミナルから起動した場合とで、常駐後の挙動が変わる理由はない
- ADR 0029 が接続を必要としたのは**出力を届けるため**であり、`--debug` なしでは常駐後に出力すべきものがそもそも無い（キーごとのログは `CLI_DEBUG` で抑止され、コンソールへは 1 行も出ない）。接続を保持する利益がゼロで、寿命を縛る不利益だけが残っていた
- 「迷ったときの優先順位」の第 1 位は**安定性（フックを止めない）**である。ターミナルを閉じただけでリマップが止まるのは、この優先順位に照らして直すべき挙動である
- 起動時の失敗をターミナルに残す（決定 2）ことで、`winremap.exe --config typo.toml` のような使い方の体験は変わらない

## 却下した代替案

- **`SetConsoleCtrlHandler` で `CTRL_CLOSE_EVENT` を無視する**: 不可能。ハンドラが `TRUE` を返してもシステムはプロセスを終了させる（HandlerRoutine の仕様）。「効いているように見えて実は数秒後に落ちる」実装になり、最悪である
- **`AttachConsole` そのものをやめる**: `--debug` のターミナル出力（ADR 0029 が守った開発者ワークフロー）を失う。過剰である
- **起動直後（引数解析後）に切り離す**: 実装は最も単純だが、設定エラーがターミナルではなくダイアログで出るようになる。ターミナルから起動した利用者にとって明確な劣化であり、採用しない
- **自分自身を `CREATE_NEW_CONSOLE` / `DETACHED_PROCESS` で再起動する**: プロセスの起動が 2 回になり、単一インスタンスミューテックス（`hook::acquire_single_instance`）と競合する。フックの再設置も必要で、得られるものに対して複雑すぎる

## 影響・補足

- **残る制限**: 本 ADR が解決するのは**コンソール接続による終了**である。ランチャーが子プロセスを Job オブジェクト（`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`）に入れる場合、そのランチャーの終了と同時に殺される挙動は残る。一部の IDE の統合ターミナルがこれに該当し得る。回避には `CREATE_BREAKAWAY_FROM_JOB` での自己再起動が必要で、上記の理由から採用していない。この制限は README の Limitations に記載する
- **起動から切り離しまでの数百 ms** は依然としてコンソールに接続している。この間にターミナルを閉じれば従来どおり終了する。実用上の影響はないと判断する
- テストは付けない（`notify.rs` は Win32 層であり、AGENTS.md ワークフロー 6 のテスト必須対象は `keymap.rs` / `config.rs`）。UI テストの `cli-smoke.ps1` は `--help` / `--version` のみを見ており、いずれも常駐に入る前に終了するため影響を受けない
