# ADR 0063: 記号（OEM）キーは刻印の文字で書き、配列は Windows に聞く

- 作成日: 2026-07-31
- 作成: Claude Code（AI モデル: claude-opus-5[1m]）／レビュー・承認: オーナー（2026-07-31）
- ステータス: 採用
- 関連: [ADR 0058](../../v0.5/decisions/0058-log-readability.md)（ログのキー名解決。本 ADR は §5 でその前提の一部を更新する）、[ADR 0056](../../v0.5/decisions/0056-control-codes-in-the-log.md)（制御コード。配列依存の 6 個を本 ADR に持ち越していた）、[02_config-spec.md §2](../../v0.1/02_config-spec.md)（記号キーを「対応時に ADR を書いて判断する」として保留した箇所）
- 実測: [キーボード配列の実測](../notes/20260731_layout-probe.md)
- 公式: [`VkKeyScanW`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-vkkeyscanw)・[`MapVirtualKeyW`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-mapvirtualkeyw)・[Virtual-Key Codes](https://learn.microsoft.com/en-us/windows/win32/inputdev/virtual-key-codes)

## 背景

`;` や `/` や `@` を設定ファイルに書けない。v0.1 の設定仕様が「VK（Virtual-Key）コードがキーボードレイアウト依存のため、対応時に ADR を書いて判断する」として保留し、**v0.5・v0.6 と 2 回送られた**。README の Limitations に残り続けている、利用者から見た最大の欠落である。

送られ続けた理由は 1 つで、**記号キーの VK とその意味の対応がキーボードによって違う**ためである。`0xC0` は日本語 106 キーボードでは `@`、US 101 キーボードでは `` ` `` である。静的な表を 1 つ持てば、**半分の利用者にとって嘘になる**。

v0.5 は同じ問題を**ログの表示側だけ**先に解いた。`MapVirtualKeyW(MAPVK_VK_TO_CHAR)` で「その機械の配列が刻んでいる文字」を Windows に聞く方式である（ADR 0058）。本 ADR は同じ問題を**設定ファイルの入力側**で解く。

### 設計前の実測（開発機、2026-07-31）

表を持たない方式の裏取りとして開発機で値を採ったところ、設計を左右する事実が 4 つ出た。詳細は[実測ノート](../notes/20260731_layout-probe.md)。

| # | 分かったこと |
|---|---|
| 1 | **`GetKeyboardLayout` は `0x04110411`（ja-JP）なのに、刻印は US 配列だった。** 日本語入力＋US キーボードは開発者には普通の構成で、オーナーの開発機がそれである。**入力言語 ID から物理配列は判定できない** |
| 2 | **`@` はこの機械では OEM キーですらない。** `S-2`（vk `0x32`・シフト面）である。JP 106 では `0xC0` の非シフト面にある |
| 3 | **`\` を返す VK が 2 つある**（`0xDC` と `0xE2`）。`VkKeyScanW` は片方しか返さない。JP 106 では `0xDC` が `¥`、`0xE2` が `\`（ろ）で別のキーである |
| 4 | **`0xDF`（`VK_OEM_8`）は文字を持たない。** 名前でしか指せない |

## 決定

### 1. 記法 — 刻印の文字を主、`Oem*` を別名とする

```toml
[keymap.remap]
"C-;" = "Enter"        # その機械の刻印どおりに書く
"C-/" = "C-z"
"C-OemMinus" = "F1"    # 配列に依存しない別名
```

刻印の文字を主にしたのは、**キーを見れば何を書けばよいか分かる**ためである。「Keyhac / fakeymacs 利用者がそのままの感覚で移行できる」という設計思想（ブリーフ §1.5）に沿う。

別名を併置したのは実測 3・4 のためである。**文字だけでは指せないキーが実在する**。加えて、配列の違う機械へ設定を持って行きたい利用者に逃げ道が要る。

別名の綴りは **Win32 の名前をそのまま使う** — `Oem1`〜`Oem8`・`Oem102`・`OemPlus`・`OemComma`・`OemMinus`・`OemPeriod`。独自の造語（`Semicolon`・`Slash`）を作らないのは、**造語は配列によって嘘になる**ためである。`VK_OEM_1` と呼ばれるキーは US 配列で `;`、JP 配列で `:` を刻む。`Semicolon` と名付ければ後者で嘘になるが、`Oem1` は何も主張しないので嘘をつきようがない。既存の名前（`Back`・`Enter`）が「そのキーが何であるか」を言えているのと違い、OEM キーにはそれが無い — この差は隠さない。

### 2. シフト面の文字は受け付けず、書き方を教える

```
line 8, column 1: in `notepad`: `@` needs Shift on this keyboard; write `S-2` instead
```

暗黙に Shift を補わないのは、**コマンドの完全一致規則（[config-spec §3.1](../../v0.1/02_config-spec.md)）と衝突する**ためである。`"C-@"` を「Ctrl+Shift+2」と解釈すると `C-@` と `C-S-2` が同じルールになる。利用者が両方を書いたら重複エラーにすべきだが、**その重複は機械によって発生したりしなかったりする**。同じ設定ファイルが片方の機械では通り、もう片方では「重複」で落ちることになる。

エラーにするもう 1 つの理由は、**メッセージが事実を教える**ことである。「その文字はこの配列ではシフト面にある」は利用者が知る必要のあることで、黙って `S-` を足すと、なぜログに `C-S-2` と出るのか分からなくなる。

助言は**押すキーの刻印で言う**（`S-Oem1` ではなく `S-;`）。読み手はキーを探しているのであって、識別子を探しているのではない。

代償として、JP 106 では `"C-@"` と書けるのに US 配列では書けない、という非対称が残る。**これは配列が実際に非対称だからで、隠すほうが害が大きい。**

### 3. 解決は設定のコンパイル時に 1 回

フックのコールバックは従来どおり VK で引くだけで、配列のことを何も知らない（不変条件 2）。

キーボードを差し替えたら**トレイメニューの Reload config が要る**。リロード時に配列を読み直すので、再起動は要らない。起動中のレイアウト変更を追いかける実装（`WM_INPUTLANGCHANGE` の監視）は入れない — 常駐中に物理キーボードを差し替える頻度に対して、監視コードとその失敗モードが高すぎる。

### 4. `keymap` は純粋関数のまま、配列は注入する

ブリーフ §4 は `keymap` を「**純粋関数として実装し単体テスト対象とする**」と定めている。`VkKeyScanW` をパーサーから直接呼ぶと、この規約と不変条件 3（unsafe の隔離）の両方に触れる。

そこで**配列のスナップショットを値として渡す**。

```rust
// 純粋データ。lib 側（keymap::Layout）に置く
pub struct Layout { faces: Vec<(u16, char)>, needs_shift: Vec<(char, u16)> }

pub fn parse_key_combo(input: &str, layout: &Layout) -> Result<KeyCombo, KeyParseError>
pub fn parse_input_pattern(input: &str, layout: &Layout) -> Result<InputPattern, KeyParseError>
pub fn config::parse_str(source: &str, layout: &Layout) -> Result<RemapTable, ConfigError>
```

実際の読み取りは **`src/layout.rs`（新規・バイナリ側）**が行う。`MapVirtualKeyW` と `VkKeyScanW` の 2 呼び出しのみで、**unsafe 許可ファイルの一覧にこの 1 ファイルを追加する**（AGENTS.md 不変条件 3・ブリーフ §5-3。オーナー承認 2026-07-31）。

これは実装の都合ではなく、**テストできる形にするための設計**である。記号キー対応は「機械によって答えが変わる」機能なので、機械に依存しない試験手段が無いと回帰を検出できない。実際、US 配列の開発機しか無いまま JP 配列の挙動を書くことになるため、**偽の配列を注入できることが、JP の正しさを主張できる唯一の方法**である。

`Layout` は 2 方向を持つ。互いの逆写像ではないため両方要る。

| 向き | 用途 |
|---|---|
| `faces`: VK → 刻印の文字 | キーの名前（ログ・設定ウィンドウ）と、文字 → VK の解決 |
| `needs_shift`: 文字 → VK | 「その文字は Shift が要る」という助言と、シフト面の制御コード |

同じ文字を 2 つのキーが刻む場合（実測 3）は **VK の小さいほうに解決する**。並び順を固定してあるので、同じ設定・同じ機械なら常に同じキーになる。もう一方は別名で指せる。

### 5. ログの括弧の意味を更新する（ADR 0058 の一部を上書き）

ADR 0058 は、ログで記号キーを `/ (0xBF)` と括弧付きで出す理由を 2 つ書いた。片方は不具合報告のためだが、もう片方は

> **「まだ設定に書けないキーだ」という正直な合図**

である。**本 ADR でこの前提が無くなる。** 書けるようになったキーに「書けない」という合図を出し続けるのは嘘になる。

新しい規則は、**設定に書けるものは括弧を外す**である。

| ログの出力 | 意味 |
|---|---|
| `/` | 設定にそのまま書ける。行をコピーして貼れる |
| `Oem2` | 配列が読めなかった場合。これも書ける |
| `Num1 (0x61)` | まだ書けない。括弧は従来どおりの合図 |

ADR 0058 のステータスは変えない。3 段階のキー名解決という決定はそのまま生きており、変わったのは括弧の付与条件だけである。

### 6. 配列依存の制御コードを答える（ADR 0056 の持ち越しを回収）

ADR 0056 は `Ctrl+[` = ESC のような配列依存の制御コードを範囲外とし、こう書いた。

> 記号キー対応を v0.6 で扱うとき、同じ ADR で一緒に決めればよい。

その v0.6 は配布経路のバージョンになったので、ここで決める。**`Ctrl` ＋ そのキーが刻む文字**が `@ [ \ ] ^ _` のいずれかなら、C0 の続きを答える（NUL・ESC・FS・GS・RS・US）。

ここでは **Shift を読む**。文字がシフト面にあることが実際にある（US 配列の `^` は `Shift+6`）ためで、`C-S-6` は本当に RS を送る。文字ではなくキーで決まる英字の場合に Shift を読まないこと（ADR 0056）とは、依拠している事実が違う。

### 7. 単キールールの危険には警告を出さない

`";" = "Enter"` と書けば `;` が打てなくなる。これは `"a" = ...` と書いたときと同じで、利用者の選択である。**「設定に書いたとおりに動く」という原則を曲げない。** ヘルプサイトには一言書く。

### 8. 表示は 2 つに分ける

`KeyCombo` の `Display` はキーボードを問い合わせられないので、記号キーを**別名**で出す（`C-Oem1`）。エラーメッセージがこれを使う。パーサーが必ず受け付ける綴りなので、出力が「設定に書けない文字列」になることはない。

配列が分かっている場所では `combo_notation(&combo, &layout)` が**刻印**で出す（`C-;`）。設定ウィンドウのルール表・コメントの突き合わせ・入力欄の読み仮名はすべてこちらを通す。**表と、その行に付くコメントと、ファイルの文字列が、同じ綴りで一致する**必要があるためである。

## 却下した代替案

| 案 | 却下理由 |
|---|---|
| **刻印の文字だけ**（別名なし） | 実測 3・4 のキー（`\` の 2 つ、`VK_OEM_8`）を指す手段が無くなる。設定を別配列の機械へ持って行くこともできない |
| **固定名だけ**（`Semicolon` / `Oem3`） | JP 配列で `@` と刻まれたキーを `Oem3` と書かせることになる。**キーを見ても何を書けばよいか分からない** |
| **VK を 16 進で直接書く**（`"C-0xBF"`） | 実装は最も簡単だが、設定ファイルが読めなくなる。ログが `0xBF` を出していた v0.5 以前の状態を、設定側に持ち込むことになる |
| **レイアウト ID で分岐する**（ja-JP なら JP 106 の表） | **実測 1 が否定した。** 開発機は ja-JP かつ US 配列である。この分岐はオーナー自身の機械で間違う |
| **`GetKeyNameTextW` でキーの刻印を取る** | ADR 0058 が「スキャンコードが要る」ため却下した。入力側で要るのは文字 → VK の方向で、この API では引けない |
| **`ToUnicode` で文字を得る** | 呼び出しスレッドのデッドキー状態を壊す（ADR 0056 が同じ理由で却下）。設定を 1 回読むだけのために利用者の次の打鍵を壊す危険は取れない |
| **スキャンコード基準の記法**（物理位置で指す） | 配列非依存という点では最も筋が通るが、利用者はスキャンコードを知らない。kmonad 系の発想であり、Keyhac / fakeymacs 利用者の移行という設計思想に合わない |
| **プロセス全体で 1 つのグローバル配列を持ち、引数で渡さない** | 既存の `hook::set_debug` 等と同じ形になるが、**US と JP を 1 つのプロセス内で同時にテストできなくなる**。この機能でそれができないのは、検証手段を捨てるに等しい。バイナリ側は実際にグローバル（`layout::current`）を持つが、それは lib の純粋な API の**上に**乗っている |
| **`WM_INPUTLANGCHANGE` を監視して自動で読み直す** | §3 のとおり。頻度に対して割に合わない。リロードで足りる |

## 影響

| 対象 | 変更 |
|---|---|
| `src/keymap/layout.rs`（新規） | `Layout`・OEM キーの一覧と別名。純粋データ |
| `src/layout.rs`（新規・**unsafe 許可ファイルに追加**） | Windows への問い合わせと、プロセス全体のスナップショット |
| `src/keymap/parse.rs` | 記号 1 文字と `Oem*` を受け付ける。`NeedsShift` エラーを追加。`TODO: OEM keys` を削除。**`C--`（マイナスキー）が書けるようになった** — 修飾子の区切りと同じ文字なので、従来は `UnknownModifier("")` になっていた |
| `src/keymap/control.rs` | 配列依存の 6 個（§6） |
| `src/keymap/mod.rs` | `combo_notation`（§8） |
| `src/config/{mod,compile,comments}.rs` | `&Layout` を受け取り、コンパイル時に解決 |
| `src/keyname.rs` | 括弧の付与条件（§5） |
| `src/gui/config_window.rs` | キー記法パネルに記号の行（**その機械の刻印を並べる**）。ルール表とコメントの綴りを §8 に合わせる |
| `src/i18n.rs` | 記号の行のラベルと注記（日英） |
| テスト | 参照配列 2 種（US 101 / JP 106）を `keymap::tests` に置き、`config` のテストからも使う。バイナリ側には**実機の配列に対する性質テスト** 4 件 |

`C--` が書けるようになったのは副産物だが、**従来は書けないことすら分からなかった**（`-` を修飾子の区切りとして読み、空の修飾子名でエラーになっていた）ので、記録に値する。
