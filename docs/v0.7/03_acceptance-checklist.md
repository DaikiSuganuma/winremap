## 0. この文書の目的

v0.7 は**機能の版**である。したがって確認すべきことは 2 種類ある。

1. **記号キーが実際に打てること** — 設定に書けるだけでなく、**その機械のキーボードで打って変換されること**（**S-1〜S-6** を新設する）
2. **これまでどおり動くこと** — v0.6 の **H-1〜H-10** と **P-1〜P-8** をそのまま継承し、更新経路の **P-9** を足す

**§1 の手順と、§2・§3・§4 の 3 つの表だけを人が見ればよい。**

### この版で特に注意すること

- **記号キーは、まだ一度も実キーボードで打たれていない。** Phase A は単体テスト（実機の配列に対する性質テストと、偽の US / JP 配列テーブル）で完了とした。開発機ではオーナーの WinRemap が常駐していて 2 つ目が起動しないためである（[開発計画 §2.7](01_development-plan.md)）。**S-1〜S-5 がその未確認を解消する項目**であり、この版でいちばん重い
- **配列に依存する項目である。** 表の `;` や `@` は**自分のキーボードの刻印で読み替える**。読み替えが要ること自体が仕様である（[ADR 0063](decisions/0063-symbol-keys.md)）
- **リリースビルドで通す。** `build.ps1` は既定で `-Configuration release`
- **自動テストはパッケージ版を見ていない。** 動かすのは素の `winremap.exe` である。これが P-1〜P-9 の存在理由
- **自動側に 1 件、決着待ちの赤がある。** [§6](#6-受け入れ前に決着が要る事項) を先に読むこと

## 2. 記号キー（**v0.7 で新設**）

### 2.1 事前準備

受け入れ用の設定を 1 つ作る。**実運用の設定は退避してから**行う。

```powershell
Move-Item $env:APPDATA\winremap\config.toml $env:APPDATA\winremap\config.toml.bak
```

```toml
# 受け入れ用。; と - は自分のキーボードの刻印で読み替える
[[keymap]]
name = "accept"
application = ["notepad.exe"]

[keymap.remap]
"C-;" = "Back"          # S-1: 刻印どおりに書く
"C-OemMinus" = "Down"   # S-2: 配列非依存の別名（どちらの配列でも「-」のキー）
```

> **`"C--"` と `"C-OemMinus"` を同時に書かないこと。** 同じキーを 2 通りに綴っているだけで、設定として矛盾する。S-2 では別々に 1 回ずつ試す。

### 2.2 項目

| # | 何を見るか | 手順 | 通過条件 | 由来 |
|---|---|---|---|---|
| **S-1** | **記号キーのリマップが効く** | メモ帳で `abc` と打ち、`Ctrl` を押しながら `;` のキーを押す | ①**1 文字消える**（`Back` になっている） ②ログウィンドウにその行が出て、**記号が `;` と出る**（`(0xBA)` のような括弧付きでない） | [ADR 0063](decisions/0063-symbol-keys.md)。**この版の目玉が実キーボードで動くことの確認**。落ちたらリリースしない |
| **S-2** | **別名が効く** | 同じくメモ帳で `Ctrl` ＋ `-` のキー。次に設定を `"C--" = "Down"` に書き換えて**トレイ → 再読み込み**し、もう一度押す | どちらの綴りでもカーソルが 1 行下がる（**同じキーを指している**） | ADR 0063 §2。`C--` は**記号キー以前から書けなかった綴り**で、v0.7 の副産物として直っている（[開発計画 §2.7](01_development-plan.md)） |
| **S-3** | **シフト面のエラーと案内** | 自分の機械で **Shift を押さないと打てない記号**を 1 つ選ぶ（US 101 なら `@`、JP 106 なら `+` や `*`）。`"C-@" = "Back"` のように書いて保存し、トレイ → 再読み込み | ①**エラーになる** ②**行番号と桁**が出る ③`` `@` needs Shift on this keyboard; write `S-2` instead `` のように**代わりの綴りが案内される** ④**案内された綴りに直すと通り、実際に効く** | ADR 0063 §1。④まで見ること — 案内が実際にパースできる綴りであることが、この設計の要点である |
| **S-4** | **「使えるキー名」に自分のキーボードが出る** | トレイ → 設定 → キーマップを選び、ルール表の**キー名アイコン**（記法のアイコン）を押す | ①「記号」の行に**この機械の刻印**が並ぶ（US 101 と JP 106 で違う） ②注記に「Shift が要る文字は `S-2` のように書く」「`Oem1`〜`Oem102` はどのキーボードでも同じキーを指す」がある ③**日本語表示でも英語表示でも読める**（豆腐が無い。`¥` `^` に注意） | ADR 0063。**固定の一覧ではなく実機を読んで出している**ことの確認。「キーボードを読み取れていません」と出たら不合格 |
| **S-5** | **ログの綴りをそのまま設定に貼れる** | ログウィンドウを開き、メモ帳で記号キーをいくつか打つ（`/` `\` `;` など）。**出た綴りをそのままコピーして設定に貼り**、再読み込みして押す | ①**設定に書けるキーは括弧無し**で出る ②**貼った綴りが通り、効く** ③文字を持たないキー（あれば）だけ従来どおり括弧付き | ADR 0063 §5。括弧は「まだ設定に書けない」という合図でもあったので、**書けるようになった以上は外す**という決定の確認 |
| **S-6** | **配列の切り替えを再読み込みで拾う**（**キーボードがある場合のみ**） | 別配列のキーボード（JP 106 ↔ US 101）に差し替え、トレイ → **再読み込み**。S-4 のポップアップと S-1 のキーを見る | ①刻印の一覧が**新しいキーボードのものに変わる** ②`"C-;"` が**新しい配列の `;` のキー**に解決する ③差し替えただけで再読み込みしなければ**変わらない**（仕様どおり） | ADR 0063 §3（解決はコンパイル時に 1 回）。**実機が無ければ「未実施」と記録する** — [実測ノート §4](notes/20260731_layout-probe.md) の JP 106 の表もここで埋まる |

> **S-1〜S-5 は必須、S-6 は条件付き。** S-6 を飛ばした場合、JP 106 での挙動は**偽テーブルの単体テストだけが根拠**である状態が続く（[開発計画 §2.7](01_development-plan.md)）。飛ばしたこと自体を記録に残す。

### 2.3 終わったら

```powershell
Move-Item -Force $env:APPDATA\winremap\config.toml.bak $env:APPDATA\winremap\config.toml
```

## 6. 受け入れ前に決着が要る事項

### 6.1 前面アプリ行（v0.5 からの持ち越し）— **自動側が赤のまま**

[開発計画 §3.5](01_development-plan.md) で足した `06-foreground-line` が、**v0.5 の観測を再現した**（2026-08-01）。

| 状態 | 前面アプリの切り替えが報告されるか |
|---|---|
| WinRemap のウィンドウを 1 枚も開いていない | **される**（37 ms） |
| ログウィンドウを開いている・**切り替え先が WinRemap 自身のウィンドウ** | **される**（143 ms） |
| ログウィンドウを開いている・**切り替え先が他のアプリ**（メモ帳） | **されない**（10 秒待っても出ない） |

UI Automation の読み取りと**画面の写真が一致している**ので、これは「ウィンドウが見せていない」のではなく**報告そのものが起きていない**。

#### これは表示の問題ではない（2026-08-01 に確定）

同じ検査が、**アプリ別キーマップが選ばれ続けるかまで測っている**（`the-keymap-still-applies`）。前面アプリの報告を書く [`refresh_foreground_cache`](../../src/window.rs) が、**フックがキーマップを選ぶときに読むキャッシュも同時に更新している**ためである。結果は **FAIL** だった。

```
08:33:39.646 [decided]   C-h (BS 0x08) → passed through
```

ログウィンドウを開いたままメモ帳を前面にして `C-h` を押すと、**フックはキーを見ているのに、メモ帳に紐付いたルールを選ばない**。前面アプリのキャッシュが `winremap.exe`（適用キーマップ `(none)`）のまま止まっているためで、メモ帳の文字は `abc` のままだった（ルールが効いていれば `abcx`）。

**つまり利用者から見た症状はこうなる。**

> **WinRemap のウィンドウを開いたまま別のアプリへ切り替えると、そのアプリ用のキーマップが効かない。**

GUI は専用スレッドで動き、フックのメッセージループはメインスレッドで回り続ける設計である（[`src/gui/mod.rs`](../../src/gui/mod.rs) の「Its own thread, so the message loop keeps servicing the hook while a window is up」）。**その前提のどこかが崩れている**が、原因はまだ特定していない。

#### 判断

**§1 の完了条件「自動側が全件緑」に対する唯一の例外がこれである。オーナーの判断が要る。**

| 選択肢 | 意味 |
|---|---|
| **v0.7 で直す**（推奨） | 原因を突き止めて ADR を書き、修正する。**利用者に見える不具合**であり、ログ周辺に触れる版でもあるので筋は通る |
| **現状を仕様として受け入れる** | 赤を承知でリリースする。その場合でも**検査は消さない**。README とヘルプサイトに「ウィンドウを開いている間はアプリ別キーマップが効かない」と書く必要がある — 書けない性質のものなら、それは直すべきだという答えでもある |

> **H-2 で同じことを人が見ること。** 自動側は注入したキーで測っている。実キーボードで同じ症状が出るかは、この版の H-2 で必ず確かめる。

## 8. 記録の書き方

v0.5 の記録欄（[§6](../v0.5/03_acceptance-checklist.md)）が見本である。**「OK」だけを書かない。** 何をどう確かめたか、省略したなら省略した判断を残す。落ちた項目は、落ちた事実と原因の切り分け結果まで書く。

この版で特に残す価値があるのは次の 2 つである。

- **S-1〜S-5 で実際に打った記号と、その機械の配列。** 「`;` が効いた」ではなく「US 101 の `;`（`VK_OEM_1`）で効いた」と書く。記号キーは**機械によって答えが変わる機能**なので、どの機械で確かめたかが書かれていない記録は次の版で使えない
- **S-6 を飛ばしたなら、飛ばしたこと。** JP 106 の実機確認は Phase A から持ち越されており、**埋まっていない空欄がどこにあるかが分かる**ことのほうが、埋まったふりより価値がある
