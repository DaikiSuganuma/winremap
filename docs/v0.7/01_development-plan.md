## 0. このバージョンの性格

v0.7 は**利用者から見た最大の欠落を埋めるバージョン**である。

> **`;` や `/` や `@` を、設定ファイルに書けない。**

README の Limitations にこう書いてある。

> **Punctuation/OEM keys** (`;`, `,`, ...) cannot be used in rules yet — their
> virtual-key codes are keyboard-layout dependent.

これは v0.1 の設定仕様（[02_config-spec.md §2](../v0.1/02_config-spec.md)）で「対応時に ADR を書いて判断する」として保留されたもので、**v0.5・v0.6 と 2 回送られている**。v0.6 の計画は「**v0.7 の目玉として単独で扱う。次は送らない**」と書き、オーナーもそれを承認した（2026-07-29、v0.6 §9-2「**v0.8 へは送らない**」）。したがって本バージョンの主題はこれである。

もう 1 本、**UI テストの操作系を winapp CLI へ移す**作業が入る。これは v0.5 から持ち越していたオーナー承認待ちの案件で、2026-07-31 に**移行するという判断を得た**。測定ゲート（[検証計画 §3](../v0.5/notes/20260727_winapp-cli-migration.md)）は 2026-07-28 に通過済みで、残っているのは移植そのものである。

2 本に絞る理由は、どちらも「終わったかどうか」がはっきりする作業だからである。記号キー対応はパーサー・設定ウィンドウ・ログ・ドキュメントに広く波及し、winapp 移行は UI テスト基盤の作り直しになる。**混ぜると、v0.5 が経験した「何が原因で落ちたのか分からない」形に戻る。**

## 2. Phase A — 記号（OEM）キー対応 — **実装完了（2026-07-31）**

### 2.1 なぜ 3 回も送られてきたのか

理由は 1 つで、**VK（Virtual-Key）コードと記号の対応がキーボードによって違う**ためである。`0xC0` は日本語 106 キーボードでは `@`、US 101 キーボードでは `` ` `` である。静的な表を 1 つ持つと、**半分の利用者にとって嘘になる**（[ADR 0058](../v0.5/decisions/0058-log-readability.md) が却下案としてこれを書いている）。

v0.5 はログの表示だけを先に解決した。`MapVirtualKeyW(MAPVK_VK_TO_CHAR)` で**その機械の配列が刻んでいる文字**を Windows に聞く方式である（[`keyname.rs`](../../src/keyname.rs)）。本フェーズは、同じ問題を**設定ファイルの入力側**で解く。

### 2.2 Phase 0 実測（開発機、2026-07-31）

設計を書く前に、開発機の実際の値を採った。**表を持たずに Windows へ聞く方式が正しいことの裏取り**であり、同時に設計上の論点を 2 つ掘り当てた。

| 呼び出し | 用途 |
|---|---|
| `MapVirtualKeyW(vk, MAPVK_VK_TO_CHAR)` | VK → その配列が刻む文字（v0.5 が既に使用） |
| `VkKeyScanW(ch)` | 文字 → VK ＋ シフト状態（**本フェーズで必要になる逆方向**） |

#### 実測 1 — 入力言語 ID から物理配列は分からない

開発機の `GetKeyboardLayout(0)` は **`0x04110411`（ja-JP）**である。にもかかわらず、VK の刻印は **US 配列**だった。

| VK | Win32 の名前 | この機械の刻印 | JP 106 キーボードなら |
|---|---|---|---|
| `0xBA` | `VK_OEM_1` | `;` | `:` |
| `0xBB` | `VK_OEM_PLUS` | `=` | `;` |
| `0xC0` | `VK_OEM_3` | `` ` `` | `@` |
| `0xDE` | `VK_OEM_7` | `'` | `^` |

**日本語入力を使いながら US 配列のキーボードを繋ぐ**のは開発者には普通の構成であり、オーナーの開発機がまさにそれである。つまり「日本語環境だから JP 配列」という分岐は**書いてはならない**。`0xBA` を `;` と決め打つ実装は、この機械では当たり、JP 106 キーボードでは外れる。

> **設計への帰結**: レイアウト ID による分岐を一切書かない。VK と文字の対応は**常に Windows に聞く**。

#### 実測 2 — 欲しい文字がシフト面にあることがある

`VkKeyScanW` は VK とシフト状態を返す。開発機（US 配列）ではこうなった。

| 文字 | VK | シフト状態 |
|---|---|---|
| `;` | `0xBA`（OEM_1） | **0（そのまま押せる）** |
| `/` | `0xBF`（OEM_2） | **0** |
| `-` | `0xBD`（OEM_MINUS） | **0** |
| `:` | `0xBA` | 1（Shift が要る） |
| **`@`** | **`0x32`（数字の 2）** | **1（Shift が要る）** |
| `^` | `0x36`（数字の 6） | 1 |
| `_` | `0xBD` | 1 |

**`@` は、この機械では OEM キーですらない。** `S-2` である。ところが JP 106 キーボードでは `@` は `0xC0` の非シフト面にある。同じ `"C-@"` という記法が、機械によって「Ctrl+Shift+2」と「Ctrl+`0xC0`」の 2 通りに解決されうる。

これは記法の設計そのものに関わる論点なので §2.4-1 で扱う。

#### 実測 3 — 同じ文字を返す VK が 2 つある

開発機では `0xDC`（`VK_OEM_5`）と `0xE2`（`VK_OEM_102`）が**どちらも `\`** を返した。`VkKeyScanW('\')` は片方（`0xDC`）しか返さない。JP 106 キーボードでは `0xDC` が `¥`、`0xE2` が `\`（ろ）で、**別々のキーである**。

> **設計への帰結**: 文字だけでは指せないキーが実在する。**配列非依存の別名**（`Oem5` / `Oem102`）が逃げ道として必要になる。オーナーが選んだ「刻印の文字を主・固定名を別名」という方針（2026-07-31）は、この実測とも一致する。

#### 実測 4 — 文字を持たない OEM キーがある

`0xDF`（`VK_OEM_8`）は開発機で文字を返さなかった（`MapVirtualKeyW` が 0）。名前でしか指せない。

### 2.3 決めたこと（オーナー決定 2026-07-31）

**刻印の文字を主とし、配列非依存の固定名を別名として受け付ける。**

```toml
[[keymaps]]
application = ["notepad.exe"]

[keymaps.remap]
"C-;" = "Enter"        # 刻印どおりに書く（この機械では 0xBA）
"C-/" = "C-z"
"C-OemMinus" = "F1"    # 別名（配列に依存しない）
```

採らなかった案と理由:

| 案 | 却下理由 |
|---|---|
| **刻印の文字だけ** | 実測 3・4 のキー（`\` の 2 つ、`VK_OEM_8`）を指す手段が無くなる。設定を別配列の機械へ持って行くこともできない |
| **固定名だけ**（`Semicolon` / `Oem3`） | JP 配列で `@` と刻まれたキーを `Oem3` と書かせることになる。**キーを見ても何を書けばいいか分からない**。「Keyhac / fakeymacs 利用者がそのままの感覚で移行できる」という設計思想（ブリーフ §1.5）に反する |

### 2.4 ADR 0063 で決める論点

1 つの ADR にまとめる（記法とその解決方式は分けられない）。

#### 1. シフト面の文字を受け付けるか

**提案: 受け付けない。非シフト面の文字だけを設定に書ける文字とし、シフトが要るものは明示的なエラーにする。**

```
line 8, column 1: in `notepad`: `@` needs Shift on this keyboard — write `S-2` instead
```

理由は 2 つある。

- **暗黙の Shift はコマンドの完全一致規則（[02_config-spec.md §3.1](../v0.1/02_config-spec.md)）と衝突する。** `"C-@"` を「Ctrl+Shift+2」と解釈すると、`C-@` と `C-S-2` が同じルールになる。利用者が `C-@` と `C-S-2` を別々に書いたら重複エラーにすべきだが、**その重複は機械によって発生したりしなかったりする**
- **エラーメッセージが教育になる。** 「その文字はこの配列ではシフト面にある」という事実は、利用者が知る必要のあることである。黙って `S-` を足すと、なぜ `C-S-2` のログが出るのか分からなくなる

代償は、JP 106 キーボードで `"C-@"` と書けるのに US 配列では書けない、という非対称が生まれることである。**これは配列が実際に非対称だからで、隠すほうが害が大きい**と考える。

#### 2. 別名の綴り

**提案: Win32 の名前をそのまま使う。** `Oem1`・`Oem2`・`Oem3`・`Oem4`・`Oem5`・`Oem6`・`Oem7`・`Oem8`・`Oem102`・`OemPlus`・`OemComma`・`OemMinus`・`OemPeriod`。

独自の造語（`Semicolon`・`Slash`）を作らないのは、**造語は配列によって嘘になる**ためである。`Semicolon` と名付けたキーが JP 配列では `:` を出す。`Oem1` は何も主張しないので嘘をつきようがない。既存の名前（`Back`・`Enter`）が「そのキーが何であるか」を言えているのと違い、OEM キーにはそれが無い — この差は隠さない。

#### 3. いつ・どこで解決するか

**提案: 設定のコンパイル時に 1 回だけ解決する。** フックのコールバックは VK で引くだけの現状を変えない（不変条件 2）。

キーボードを差し替えたり配列を切り替えたりしたら、**トレイメニューの Reload config が要る**。これはドキュメントに書く。起動中のレイアウト変更を追いかける実装（`WM_INPUTLANGCHANGE` の監視）は入れない — 常駐中に物理キーボードを差し替える頻度に対して、監視コードとその失敗モードが高すぎる。

#### 4. `keymap` を純粋関数のまま保つ方法

ブリーフ §4 は `keymap.rs` を「**純粋関数として実装し単体テスト対象とする**」と定めている。`VkKeyScanW` を直接呼ぶと、この規約と不変条件 3（unsafe の隔離）の両方に触れる。

**提案: 解決関数を注入する。**

- `keymap::parse` は「文字 → VK」を行う関数を引数で受け取る。パーサー自体は Win32 を呼ばない
- 実際の解決は **`src/layout.rs` を新設**して置く。`VkKeyScanW` / `MapVirtualKeyW` の 2 呼び出しのみ。unsafe 許可ファイルの一覧（AGENTS.md 不変条件 3・ブリーフ §5-3）に**この 1 ファイルを追加する**
- テストは US 配列・JP 106 配列の偽テーブルを注入して回す。**JP キーボードが手元に無くても JP の挙動をテストできる**ようになる

これは実装の都合ではなく、**テストできる形にするための設計**である。記号キー対応は「機械によって答えが変わる」機能なので、機械に依存しない試験手段が無いと回帰を検出できない。

#### 5. ログの表示（ADR 0058 の前提が崩れる）

[ADR 0058](../v0.5/decisions/0058-log-readability.md) は、ログで記号キーを `/ (0xBF)` と括弧付きで出す理由を 2 つ書いている。片方は不具合報告のためだが、もう片方は

> **「まだ設定に書けないキーだ」という正直な合図**

である。**本フェーズでこの前提が無くなる。** 書けるようになったキーに「書けない」という合図を出し続けるのは嘘になるので、表示を見直す。提案は、**設定に書ける記号キーは括弧を外して `/` と出し、書けないもの（シフト面の文字・文字を持たないキー）だけ従来どおり括弧付きにする**。ログを読んだ人がそのままコピーして設定に貼れる形が正しい。

#### 6. 制御コードの持ち越し（ADR 0056）

[ADR 0056](../v0.5/decisions/0056-control-codes-in-the-log.md) は、`Ctrl+[` = ESC のような**配列依存の制御コード**を範囲外とし、こう書いた。

> 記号キー対応を v0.6 で扱うとき、同じ ADR で一緒に決めればよい。

その v0.6 は配布経路のバージョンになったので、**ここで決める**。記号キーが VK に解決できるようになれば、`C-[` の制御コードも計算できる。

#### 7. 単キールールにしたときの危険

`";" = "Enter"` は、`;` が打てなくなることを意味する。これは `"a" = ...` と書いたときと同じで、利用者の選択である。**警告は出さない**（設定に書いたとおりに動く、という原則を曲げない）。ただしヘルプサイトには一言書く。

#### 8. 却下する案の記録

| 案 | 却下理由 |
|---|---|
| **VK を 16 進で直接書けるようにする**（`"C-0xBF"`） | 実装は最も簡単だが、設定ファイルが読めなくなる。ログが `0xBF` を出していた v0.5 以前の状態を設定側に持ち込むことになる |
| **`GetKeyNameTextW` でキーの刻印を取る** | ADR 0058 が「スキャンコードが要る」ため却下した。入力側の解決は文字 → VK の方向であり、この API では逆が引けない |
| **スキャンコード基準の記法**（物理位置で指す） | 配列非依存という点では最も筋が通るが、利用者はスキャンコードを知らない。kmonad 系の発想であり、Keyhac / fakeymacs 利用者の移行という設計思想に合わない |

| シフト面のエラーと案内 | ✅ `` `@` needs Shift on this keyboard; write `S-2` instead ``。案内された綴りが**実際にパースできること**までテストしている |
| README の Limitations | Phase C で行う |

#### 案から変えた点

**`Layout` の持ち方を 2 方向から 1.5 方向に減らした。** 当初はキー→文字（刻印）、キー→シフト面の文字、文字→キーの 3 つを持つ設計だったが、後ろ 2 つは同じ事実の読み替えである（1 つのキーのシフト面の文字は 1 つ）。二重に持てば片方だけ直す事故が起きるので、`needs_shift`（文字→キー）だけを持ち、シフト面の文字は逆引きする。

**表示を 2 系統に分けた**（ADR §8）。`Display for KeyCombo` はキーボードを問い合わせられないので別名（`C-Oem1`）を出し、配列が分かる場所では `combo_notation` が刻印（`C-;`）を出す。**設定ウィンドウのルール表・その行のコメント・ファイルの文字列が同じ綴りで一致する必要がある**ためで、当初案にはこの区別が無かった。

#### 見つけた副産物

**`C--`（マイナスキー）が従来まったく書けなかった。** `-` は修飾子の区切りと同じ文字で、パーサーは `C--` を「`C` の後に空の修飾子名」と読んで `UnknownModifier("")` を返していた。記号キー以前の問題であり、**書けないことすら分からない**形の不具合だった。

#### 実機で確認できなかったこと

**動作中のアプリでの打鍵確認は行えていない。** 開発機ではオーナーの WinRemap が常駐しており、単一インスタンス防止のため 2 つ目が起動しない。リマップの実動作は Phase D の受け入れ（S-1〜S-5）でオーナーが確認する。**「テストは通ったが実際に打っていない」ことは受け入れまで解消しない**ので、ここに明示しておく。

## 7. フェーズ順序と依存関係

```
Phase A（記号キー対応）───┐
                          ├──▶ Phase C（ドキュメント反映）──┐
Phase B（winapp CLI 移行）─┘                                 ├──▶ Phase E（リリース）
                          └──────────────────────────────▶ Phase D（受け入れ）─┘
```

- **A と B は互いに独立**。並行して進められる（A は Rust、B は PowerShell と VM）
- **C は A の完了後**。書けるようになった記法が確定しないと書けない
- **D は A・B の両方の後**。受け入れの自動側は B の成果物そのものである
- **C は E より前に完了していること**（v0.4 の教訓。リリース後に文書を直すと、公開された版の記述が嘘のまま残る）
